## 2. 질문에 대한 답

### 2-1. Q4 — `real[]` 캐시는 Q3과 충돌하는가? 청킹을 다시 하면 어떻게 달라지는가?

**Q3과 충돌하지 않는다.**
- `real[]`은 PostgreSQL 기본 타입이라 pgvector 확장이 없어도 된다.
- 지금 캐시는 `vector` 타입이라 새 표가 필요하다. `real[]` 표를 새 마이그레이션(V2 이후)으로 만든다.
- 이미 적용된 V1은 고치지 않는다.

**청킹을 다시 하면 바뀐 조각만 새로 임베딩한다.**

캐시 키는 `(모델, 모델 버전, 차원, preprocessing_hash, content_hash)`다(코드 확인).
- `content_hash` = 임베딩 입력(절 경로 + 본문)의 sha256이다. 따라서 **조각의 글자가 하나라도 바뀌면 그 조각만** 캐시에 없어서 다시 임베딩한다.
- `preprocessing_hash`는 `"ollama-embed|raw-document|query-instruct:" + 질문 지시문`으로만 만든다(`OllamaDescribedEmbeddingModel.java:19`). **청킹 설정은 들어가지 않는다.** 그래서 청킹 규칙을 바꿔도 캐시 전체가 무효가 되지는 않는다.

| 바뀌는 것 | 다시 임베딩하는 조각 |
|---|---|
| 1,024토큰 상한 적용(표 분할) | 넘는 조각 52개가 나뉜 결과만. 나머지 약 97%는 캐시를 쓴다(실측 2026-11-18) |
| 문서 내용 일부 수정 | 바뀐 문단이 든 조각만 |
| 절 제목 변경 | 그 절의 조각 전부(절 경로가 입력에 들어감) |
| 문서 제목을 임베딩 입력에 붙이기 | **전부**(모든 입력이 바뀜) |
| 임베딩 모델·디지스트·질문 지시문 변경 | **전부** |

같은 입력이면 같은 벡터를 주는 캐시이므로, 구조가 바뀌어도 틀린 벡터가 섞이지는 않는다. 오래 안 쓰인 캐시 행을 지우는 규칙은 아직 없다. 지금 크기는 1,700행 × 4KB 정도라 급하지 않다.

### 2-2. Q10 — 왜 임베딩 모델의 토크나이저를 쓰지 못하는가? 추천 라이브러리

**임베딩 모델의 토크나이저를 쓴다. 문제는 그것을 Java에서 돌리는 방법이다.**
- 토크나이저는 임베딩 모델(Qwen3-Embedding-0.6B)에 딸려 있다. 지금은 PC 2 Ollama 안의 GGUF 파일 속에만 있다.
- **Ollama가 토큰화 결과를 밖으로 주지 않는다.** PC 2 Ollama 0.40.10에 `POST /api/tokenize`를 보내면 **404**다(2026-11-18 확인).
- `/api/embed` 응답의 `prompt_eval_count`로 토큰 수를 알 수는 있지만 문제가 있다.
  - 임베딩을 다 계산한 뒤에야 나온다.
  - 청크를 나누는 도중에 "이 블록을 붙이면 넘는가"를 물을 때마다 임베딩을 돌려야 해서, 재색인 시간이 크게 늘어난다.
- 그래서 **같은 토크나이저 파일(`tokenizer.json`)을 서비스 안에서 직접 돌린다.** 이것이 (a) 방향이다. Java에는 BPE 토크나이저가 내장되어 있지 않아 라이브러리가 필요하다.

**실측: HF 토크나이저와 Ollama의 개수 차이는 정확히 1이다** (2026-11-18, PC 2 Ollama에 2회 호출)

| 입력 | HF `tokenizer.json`(특수 토큰 없음) | Ollama `prompt_eval_count` |
|---|---|---|
| `hello world` | 2 | 3 |
| 한국어 + 표 기호 한 줄 | 25 | 26 |

Ollama는 끝에 EOS 토큰을 하나 붙인다. 그래서 상한 검사는 **HF 개수 + 1 ≤ 1,024**로 한다.

**추천: DJL HuggingFace Tokenizers** (`ai.djl.huggingface:tokenizers`)

| 항목 | 내용 |
|---|---|
| 무엇 | HuggingFace `tokenizers`(Rust)를 Java에서 부르는 바인딩. `tokenizer.json`을 그대로 읽으므로 위 실측과 같은 결과가 나온다 |
| 버전 | **0.40.0**(Maven Central 2026-10-30, 2주 넘음). 직전 0.39.0(2026-10-20) |
| 라이선스 | Apache-2.0 |

**구현 전에 확인할 것** (아직 확인하지 않음)
1. 컨테이너(리눅스 x86_64)와 개발 PC(윈도우)에서 쓸 네이티브 라이브러리가 jar에 들어 있는가, 아니면 실행할 때 인터넷에서 내려받는가. 내려받는다면 LAN에서 실패할 수 있다.
2. Java 결과가 Python HF 결과와 같은가. 실제 문서 65개의 모든 조각을 양쪽으로 세서 비교한다.

### 2-3. Q12 — `RankingPolicy`를 쓸 수 있는가

**쓸 수 있다. 다만 무엇을 점수로 넣는지와 값은 바꿔야 한다.**

`RankingPolicy`가 하는 일은 두 가지다.
1. **합격선으로 거르기**: `similarity ≥ threshold`
2. **정렬**: `similarity + 지위 가중 + 우선순위 가중`으로 정렬해 top-k

이 구조는 그대로 쓸 수 있다. 하지만 지금 값을 RRF 점수에 그대로 쓰면 두 가지 문제가 생긴다.

| 문제 | 이유 | 해결 |
|---|---|---|
| **합격선이 의미를 잃는다** | RRF 점수는 순위만으로 계산한다(1위라도 1/(60+1) ≈ 0.016). 관련 없는 문서도 1위면 같은 점수를 받는다. 그래서 RRF 점수로는 "근거 없음"을 판정할 수 없다 | 합격선은 **질문 벡터와의 cosine**으로 건다. 후보마다 cosine을 계산하고(BM25로만 들어온 후보도 저장된 벡터로 계산), 기준값은 평가로 다시 정한다. 발췌로 바꾸는 하한(지금 0.45)도 같은 cosine으로 바꾼다 |
| **지위 가중이 순위를 뒤집는다** | 지위 가중(LAN 확정 0.03 등)이 RRF 점수 범위(약 0~0.03)와 같거나 더 크다. 지위만으로 순위가 정해진다 | 가중값을 RRF 척도에 맞춰 다시 정한다(평가로) |

**정리**
- `RankingPolicy` 클래스와 "합격선 → 지위 가산 → top-k" 흐름은 유지한다.
- 입력은 둘로 나눈다: 합격선용 `cosine`, 정렬용 `RRF 점수`.
- 값(합격선, 가중)은 새 방식으로 평가해서 다시 정한다. 그 전까지 LAN 값은 바꾸지 않는다.

- 스냅숏 ID에 만든 시각(UTC)이 들어 있어 이름만 봐도 순서를 안다.

지금 스냅숏 ID는 `IDX-yyyyMMddHHmmss-<8자>` 형식이다. ES 인덱스 이름은 소문자만 되므로 소문자로 바꿔 쓴다.

### 2-6. Q14 — digest 고정 방법

Ollama는 `model@sha256:…`처럼 digest로 모델을 부를 수 없다. 그래서 **설정에 기대 digest를 적고, 서비스가 확인한다.**

**지금 PC 2의 digest** (2026-11-18 `/api/tags`)

| 모델 | 양자화 | digest |
|---|---|---|
| `qwen3-embedding:0.6b` | Q8_0 | `ac6da0dfba84a81fdbfbaf330198c33cd77c4cdfc53e8bc50eb581914a15621d` |
| `qwen3:4b` | Q4_K_M | `359d7dd4bcdab3d86b87d73ac27966f4dbb9f5efdfcc75d34a8764a09474fae7` |

**방법**
- pmart-config에 두 digest를 적는다.
- 서비스는 기동할 때와 색인할 때 `/api/tags`의 digest와 비교한다.
- 다르면 그 작업만 `CONFIG_REQUIRED`로 멈춘다. 다른 모델로 몰래 답하지 않는다.
- 임베딩 스냅숏의 `embedding_model_version`에도 digest를 남긴다. 모델이 바뀐 뒤에는 기존 캐시와 스냅숏이 섞이지 않는다.

### 2-7. 추가 질문 — 재색인할 때 PostgreSQL과 ES의 상태(버전)가 다르면 어떻게 맞추는가

**원칙: Postgres `index_snapshot`이 정본이고, ES는 따라간다.**
- 두 저장소를 한 트랜잭션으로 묶을 수 없다(2PC 금지 규칙). 그래서 한쪽을 기준으로 정하고, 순서와 되맞추기(reconcile)로 맞춘다.

**재색인 순서**
1. Postgres에 새 스냅숏을 `BUILDING`으로 넣는다.
2. ES에 새 인덱스 `rag-ops-<id>`를 만든다(매핑·분석기). 조각을 bulk로 넣고 refresh한다.
3. **검증**: ES 문서 수가 Postgres `chunk_count`와 같은지 본다. 고객용은 `faq_entry` 행도 확인한다.
   - 다르면 Postgres를 `FAILED`로 바꾸고 ES 인덱스를 지운다. 지금 ACTIVE는 그대로 둔다.
4. Postgres 트랜잭션 하나에서 옛 ACTIVE를 `RETIRED`로, 새 스냅숏을 `ACTIVE`로 바꾼다. 지금의 잠금 규칙(`AdvisoryLocks.SNAPSHOT`)을 그대로 쓴다.
5. ES 별칭을 한 번의 `_aliases` 요청으로 옛 인덱스에서 새 인덱스로 옮긴다(원자적).

**검색은 별칭이 아니라 Postgres ACTIVE ID로 실제 인덱스를 직접 부른다.**
- 이렇게 하면 4와 5 사이에 서비스가 죽어도 검색은 늘 Postgres가 ACTIVE라고 한 스냅숏을 본다.
- 답변에 남는 `snapshot_id`와 검색한 인덱스도 늘 맞는다.
- 별칭(`rag-ops`, `rag-customer`)은 사람이 Kibana나 수동 점검에서 쓰는 이름으로 두고, 뒤에서 맞춘다.

**되맞추기 (기동할 때, 색인을 시작하기 전, 정리 작업 때)**

| 어긋난 상태 | 처리 |
|---|---|
| 별칭이 ACTIVE가 아닌 인덱스를 가리킴 | 별칭을 ACTIVE 인덱스로 옮긴다 |
| Postgres는 ACTIVE인데 ES 인덱스가 없음 | 검색을 `CONFIG_REQUIRED`로 멈추고 재색인을 요구한다. 지어내지 않는다 |
| Postgres에 행이 없는 ES 인덱스(`rag-*-idx-*`) | 지운다(실패한 색인의 잔재) |
| `RETIRED`·`FAILED` 스냅숏의 ES 인덱스 | 처리 중(`PROCESSING`) 답변이 그 스냅숏을 쓰지 않을 때 ES 인덱스부터 지우고, 그다음 Postgres 행을 지운다. 지금의 `pruneSnapshots` 규칙과 같다 |

**설정이 달라졌을 때**
- 분석기(nori + n-gram), 매핑, 청킹 규칙, 임베딩 모델이 바뀌면 옛 인덱스와 섞어 쓸 수 없다.
- 그래서 `index_snapshot`에 **ES 매핑·분석기 해시**와 **청킹 설정 해시**를 함께 남긴다(새 마이그레이션 열).
- 서비스 설정과 ACTIVE 스냅숏의 해시가 다르면 재색인을 요구한다. 지금 `preprocessing_hash` 검사(`Retriever.java:49`)와 같은 방식이다.
- PostgreSQL 17과 ES 8.18 **소프트웨어 버전 자체**는 서로 독립이라 맞출 필요가 없다. ES 판을 올리면 매핑 해시와 같이 기록하고 재색인한다.

### 3-1. Q2 "Java에서 RRF 직접 구현"과 Q9 "RRF 제외"
두 답이 서로 맞지 않는다. 제 해석은 이렇다.
- **ES 내장 RRF 파라미터**(`rank_window_size` 등)는 쓰지 않으니 뺀다.
- **RRF 자체는 Java에서 한다.**

이 해석이 맞다면 Java RRF에도 값이 하나 필요하다.
- **추천: RRF `k`(rank_constant) = 60.** ES 기본값이자 논문 값이다.
- 각 목록에서 BM25 40개, kNN 40개를 받아 결합한다.

**확인 필요**: 이 해석과 `k` = 60으로 할까요?

### 3-2. Q3 "pgvector 없는 Postgres"와 이미 적용된 V1 마이그레이션
두 서비스의 `V1__init.sql`에는 이것들이 들어 있다.
- `CREATE EXTENSION vector`
- `vector` 타입 열(`doc_chunk.embedding`, `embedding_cache.embedding`)

그래서 컨테이너 이미지를 pgvector가 없는 `postgres:17`로 바꾸면 **새 DB에서 V1이 실패한다**(통합 시험, 새 환경). 이미 적용된 마이그레이션은 고치지 않는다는 규칙 때문에 V1을 바꿀 수도 없다.

| 선택지 | 영향 |
|---|---|
| **(a) 이미지는 `pgvector/pgvector:pg17` 그대로 두고 pgvector 기능만 안 씀 (추천)** | V1은 그대로 돈다. V2 이후에 `doc_chunk`와 `vector` 캐시 표를 지운다(새 방식이 검증된 뒤, expand → contract). 벡터 저장·검색은 하지 않으므로 "pgvector 사용 안 함"을 지킨다. 확장 설치 흔적만 남는다 |
| (b) `postgres:17`로 바꾸고 마이그레이션을 새로 시작(Flyway baseline) | 이미지에서도 pgvector가 완전히 빠진다. 하지만 LAN DB의 Flyway 이력을 맞추는 작업과 시험용 새 V1이 필요하고, 규칙상 위험이 크다 |

**확인 필요**: (a)로 할까요?
