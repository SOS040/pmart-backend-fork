- 대상: [`2026-11-27-es-hybrid-rag-proposal.md`](2026-11-27-es-hybrid-rag-proposal.md) — 사용자가 준 원문. 고치지 않고 둔다.
- 대조한 것: origin/main 의 코드와 설정, 11-27 실측(`docs/rag/verification/2026-11-27/`), 11-18 ES Basic 실측(`docs/rag/verification/2026-11-18/es-basic-license-check.md`), ADR-0083·0088.

## 1. 총평

**방향은 타당하다.** 다음은 모두 맞다.

- PostgreSQL 을 정본으로, ES 를 검색용 사본으로 두는 책임 분리
- "pgvector 를 빼는 것과 PostgreSQL 정본을 유지하는 것은 다르다"는 구분
- "ES 로 바꾼다고 품질·속도가 자동으로 좋아지지 않는다"는 주의
- 병렬 비교 뒤 전환하는 단계(§8)
- "인용 검사 실패로 원문이 나가는 문제는 검색 엔진을 바꿔도 해결되지 않는다"(§7.3)

**지금 결정과는 다르다.** 2026-11-19 사용자 결정은 "ES 개편 안 함, 오류만 고침"이다. 채택하려면 사용자 결정과 새 ADR 이 필요하다. 원문 첫머리의 "11-18 계획을 재승인하는 문서가 아니다"는 정확하다.

**보완할 것:** 고칠 사실 3개, 빠진 설계 6개. 가장 큰 것은 두 가지다.

- §3-A 근거 없음 판정 기준 — 원문의 RRF 로는 판정할 수 없다.
- §3-F **답 가로채기 단계** — 지금 RAG 는 검색과 생성 사이·뒤에 LLM 답을 가로채거나 바꾸는 단계가 여럿이고, 11-27 측정에서 품질 문제의 상당수가 여기서 나왔다. 원문 흐름(§4)에는 이 단계들이 없고, ES 로 바꾸면 이 단계들의 기준값이 깨진다.

## 3. 빠진 설계

### A. 근거 없음 판정 기준

- 지금은 혼합 점수(0.6 × 코사인 + 0.4 × trgm)의 **절대값**으로 판정한다. 운영자 LAN 임계값 0.425 는 11-27 실측으로 맞춘 값이다(답 없는 질문 14개 중 12개를 거르고, 답 있는 질문은 잃지 않음).
- 원문 §4·§7.2 의 **RRF 는 순위만 쓰므로 점수에 절대 의미가 없다** — 근거 없음 판정에 쓸 수 없다. BM25 점수도 상한이 없어 기준값 하나로 정하기 어렵다.
- 필요한 것: 순위는 RRF(또는 점수 합)로 정하되, 근거 없음은 kNN 코사인 같은 **절대값 신호로 따로** 판정하고 다시 보정한다. 상품 검색(ADR-0088)도 RRF 가 아니라 "한 검색 안의 점수 합 + kNN `similarity` 기준값"을 쓴다.

### B. 권한·지위를 ES 질의에 넣는 방법

- 지금은 접근 범위 필터와 지위 가중이 SQL 한 번 안에 있다.
- ES 로 가면 필터를 **BM25 와 kNN 양쪽에** 걸어야 한다(가져온 뒤 거르면 상위 k 가 빈다 — 11-18 계획에서도 짚음). 지위 가중은 `function_score` 등으로 다시 구현해야 한다.
- 원문 §2 의 "검색 뒤 PostgreSQL 에서 권한·활성 스냅숏 확인"은 이중 확인으로 좋지만 검색 단계 필터를 대신하지 못한다.

### C. 어느 ES 에 둘 것인가

- 지금 ES 는 `es-search`(PC 3, 상품, nori 설치)와 `es-logs` 둘이다. RAG 묶음(서비스·rag-pgvector·Ollama)은 PC 2 에 있다.
- 기존 ES 를 같이 쓰면 용도와 장애 범위가 섞이고, 새로 띄우면 PC 메모리가 문제다. 원문에 결정이 없다 — 채택 전에 PC 1 과 정해야 한다.

### D. 청킹·인용 검사는 앱에 남는다는 것

- `MarkdownChunker`(제목 경로, 표·목록 통째)와 인용 검사(`CitationVerifier`·`EvidenceAlignment`)는 짝이다. ES 로 가도 청킹은 앱이 하고 ES 에는 결과만 넣어야 한다. 원문 §3 1단계 "수집 및 청킹"의 주체를 앱으로 명시하는 것이 좋다.
- ES 색인에 넣을 벡터는 정본 쪽 `embedding_cache` 의 것을 그대로 쓰면 PC 2 Ollama 를 다시 부르지 않는다(전체 임베딩 11-27 실측 652초 — PC 2 는 상품 의미 검색·꼬리표 생성과 함께 쓴다). 원문의 흐름과 같은 뜻이며, 구현할 때 이 재사용을 명시해 두면 된다.

### E. 시험·장애 경로

- 통합 시험이 Testcontainers pgvector 에서 ES(8.18 + nori, Basic)까지 늘어난다. 시험 시간과 CI 부담을 적어야 한다.
- 원문 §7.3 "ES 실패 시 별도 승인된 폴백 경로"가 무엇인지 정해야 한다. pgvector 를 폴백으로 남기면 검색 경로가 둘이 되어 시험·평가할 조합이 늘어난다.

### F. 답 가로채기 단계 (가장 중요)

RAG 가 고도화되면서, 검색과 생성 사이·뒤에 **LLM 답을 가로채거나 다른 답으로 바꾸는 단계**가 여럿 생겼다. 원문 §2·§4 흐름은 "검색 → 생성 → 검증"뿐이라 이 단계들이 빠져 있다.

#### F-3. ES 제안과의 관계

- ES 로 바꿔도 1~4·6·8단계는 그대로 남는다 — 이 단계에서 나는 문제(옳은 답 거절, 규칙 판정 오류)는 ES 와 관계없다.
- **5·7단계의 기준값(0.425·0.45)은 지금 혼합 점수 척도에 묶여 있다.** 검색 점수가 RRF·BM25 로 바뀌면 두 기준값이 의미를 잃고, 근거 없음 판정과 발췌 전환을 처음부터 다시 맞춰야 한다(§3-A 와 같은 문제).
- 따라서 원문 §4 흐름에 이 8단계를 넣고, 각 단계가 ES 전환 뒤 무엇을 입력으로 쓰는지(특히 5·7단계의 점수) 정해야 한다.

#### F-4. 제안 (ES 채택과 관계없이 먼저)

1. **가로채기 관측**: 단계별로 몇 번 가로챘는지 남긴다(예: 검사 실패 규칙별 횟수, 다시 생성 횟수, 발췌 전환 횟수). 질문 원문은 남기지 않는다.
2. **부정 검사 마무리**: 연결어미 뒤에서 조각을 나누는 수정(작업 중)으로 옳은 답 거절 4 → 2. 남은 2건(조건문 "-면", 꾸미는 "없는")은 "부정이 걸린 낱말이 양쪽에 있을 때만 비교" 규칙으로 고칠지 사용자 결정 대기.
3. **발췌 하한(0.45) 다시 보기**: N01 처럼 생성이 두 번 거절된 질문은 근거가 약하다는 신호다. 발췌로 넘어가는 기준을 임계값보다 충분히 높게 둘지, 두 번 거절이면 근거 없음으로 볼지 검토한다.
4. **평가셋에 3·4단계 질문 추가**: 상품·주문·경계 질문("라면 반품 기준")을 넣어 규칙 판정 오류를 잰다.

## 4. 권하는 다음 순서

1. **§3-F-4 (가로채기)를 먼저 한다.** ES 와 관계없이 품질에 바로 영향을 주고, 측정으로 문제가 확인된 곳이다.
2. 원문 §8 4단계(병렬 비교)는 사용자 결정 대기. 한다면 PC 4 에서만:
   - PC 4 에 ES 8.18 + nori 를 띄우고, 지금 청크 642개와 `embedding_cache` 의 벡터를 그대로 넣는다(Ollama 호출 거의 없음).
   - 같은 평가 질문(검색 24 + 답변 19)으로 비교한다.

     | 비교 대상 | 지금 결과 |
     |---|---|
     | 지금 방식(pgvector + trgm) | 절 적중 24/24, 17/19 |
     | ES BM25(nori)만 | 재 봐야 함 |
     | ES BM25 + kNN(점수 합 또는 앱 RRF) | 재 봐야 함 |

   - 답 없는 질문 14개의 점수 분포도 같이 본다(§3-A, §3-F-3).
3. 결과가 같거나 나쁘면 이 제안은 "검토 끝, 채택 안 함"으로 닫는다. 확실히 좋아지면 §3 의 A~F 를 채운 새 ADR 을 쓰고 사용자 결정을 받는다.
