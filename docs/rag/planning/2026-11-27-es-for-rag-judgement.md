# RAG 에 Elasticsearch 를 쓸지 — 판단 기록 (2026-11-27, PC 4)

사용자 질문(2026-11-27) 두 가지에 대한 판단과 근거. **결정 기록이 아니라 판단 기록**이다 — 실행한 것은 없다.
2026-11-19 사용자 결정("ES 개편 계획은 진행하지 않는다, 기존 방식 그대로 오류만 고친다")과 같은 결론이며, 그 뒤에 생긴 근거(11-27 실측, ADR-0088)를 더했다.

| 질문 | 판단 |
|---|---|
| 1. RAG 문서를 Elasticsearch 에 적재할 것인가 | **하지 않는다** — pgvector 유지 |
| 2. Qwen3 임베딩으로 가는 청크(모든 문서)가 Elasticsearch 를 통과할 것인가 | **통과시키지 않는다** — 서비스가 Ollama 를 직접 부른다 |

## 0. 지금 구조 (origin/main, 2026-11-27 확인)

- RAG 서비스 둘: `ai-assistant-service`(운영자, 8508), `customer-assistant-service`(고객, 8509).
- 저장소: PostgreSQL + pgvector(코사인) + pg_trgm(키워드). 혼합 점수 = 0.6 × 코사인 + 0.4 × trgm word_similarity, SQL 한 번. RRF·리랭커 없음.
- 모델: LAN PC 2 Ollama — 임베딩 `qwen3-embedding:0.6b`(1024차원, CPU), 생성 `qwen3:4b`(GPU). 외부 유료 API 없음.
- 청크: 직접 짠 `MarkdownChunker`(제목 경로, 표·목록 통째). 서비스가 `/api/embed` 를 직접 부른다.
- 색인: 스냅숏(BUILDING → 한 트랜잭션으로 ACTIVE → RETIRED) + 임베딩 캐시(바뀐 청크만 다시 임베딩).
- 규모: 운영자 문서 75개 · 642청크, 고객 답변 근거 문서 16개.
- Elasticsearch 는 상품 검색(`es-search`)과 로그(`es-logs`)에 쓴다. 8.18.0, Basic(무료).

## 1. 문서를 Elasticsearch 에 적재할 것인가 → 하지 않는다

### 이유 ① 검색은 지금 병목이 아니다 (2026-11-27 실측)

- 실제 Qwen3 임베딩으로 잰 검색: 검색 평가 24문항에서 정답 절이 상위 5개 안에 든 것 **24/24**, 답변 평가 질문에서 **17/19**.
  (`docs/rag/verification/2026-11-27/answers-eval-qwen3-embedding/`)
- LAN 답변 평가(35문항, 임계값 0.425 반영 뒤 27/35)에서 틀린 8개의 원인:

| 원인 | 개수 | 질문 | ES 로 바꾸면 고쳐지나 |
|---|---|---|---|
| 근거는 맞게 가져왔는데 모델이 핵심을 빠뜨림 | 4 | A05·A06·B02·B05 | 아니요 — 생성 단계 문제 |
| 비슷한 주제의 다른 조항을 가져옴 | 3 | A13·A15·B01 | 재 본 적 없음 |
| 답이 없어야 하는데 발췌로 답함 | 1 | N01 | 아니요 — 임계값·인용 검사 문제 |

  (`docs/rag/verification/2026-11-27/answer-eval-threshold-0.425/`)
- 검색 실패 3건은 rag-docs 에 독자별로 비슷한 문서가 나란히 있어서 생긴다(직원용·라이더용 수행료 문서 등).
  ES 의 키워드 검색(BM25 + nori)이 이것을 더 잘 가를지는 **측정한 적이 없다** — 측정 없이 저장소를 바꿀 근거가 되지 않는다.

### 이유 ② 규모가 작다

- 642청크에서는 pgvector 가 모든 청크와 정확히 비교한다. ES 의 근사 검색(HNSW)·분산 처리가 주는 이득이 없다.

### 이유 ③ ES Basic(무료)에서는 핵심 기능을 못 쓴다

- 2026-11-18 로컬 ES 8.18.0 Basic 실측: `rrf`·`linear` retriever, `text_similarity_reranker`, inference API, ML 모델이 모두 403.
  (`docs/rag/verification/2026-11-18/es-basic-license-check.md`)
- 되는 것은 BM25, kNN, 필터뿐이다. ES 로 옮겨도 점수 결합은 앱에서 직접 짜야 하고, 그것은 지금 SQL 한 줄로 이미 한다.

### 이유 ④ 지금 구조의 장점을 잃는다

- 색인 전환이 Postgres 트랜잭션 한 번이다. 답변 기록(`policy_answer`)·채팅 세션·임베딩 캐시·FAQ 의견이 같은 DB 에 있다.
- 권한(접근 범위)·지위 가중이 같은 쿼리 안에 있다.
- ES 로 가면 저장소가 둘로 갈라져 서로 맞추는 일이 생긴다(별칭 전환 ↔ DB 기록). 11-27 에 고친 "남은 BUILDING 스냅숏 정리"(#553) 같은 문제를 ES 쪽에서 다시 풀어야 한다.
- 운영: RAG 묶음이 있는 PC 2 에는 주문·결제, Ollama(CPU 4·메모리 6GB 상한), rag-pgvector 가 함께 있다. RAG 용 ES 를 더 띄우면 메모리를 다툰다.
  기존 `es-search`·`es-logs` 를 같이 쓰면 용도와 장애 범위가 섞인다.

### "상품 검색은 ES 인데 RAG 는 왜 아닌가"

- 상품 검색(ADR-0088)이 ES 에 벡터(`semanticVector`, dense_vector)를 넣은 것은 맞는 선택이다. 상품은 이미 ES 에 있고, 형태소 분석(nori)·동의어·오타 교정·필터·정렬이 모두 ES 기능이다.
- RAG 문서는 반대다. 이미 Postgres 에 있고, 필요한 것은 트랜잭션과 정확한 비교다.
- **각자 데이터가 원래 있는 곳에 벡터를 더한 것**이고, 지금 구조가 이미 그렇게 되어 있다.

## 2. Qwen3 로 가는 청크가 Elasticsearch 를 통과할 것인가 → 통과시키지 않는다

1. **ES 를 거쳐 임베딩하는 무료 방법이 없다.** ES 안에서 청크를 나누고 임베딩하는 기능(`semantic_text`, inference)은 Basic 에서 막혀 있다(위 실측). 결국 앱이 Ollama 를 직접 불러야 한다.
2. **우리 조직의 선례도 같다.** ADR-0088 결정 6 — 상품 벡터도 Logstash·ES 가 아니라 search-service 의 뒤 작업이 Ollama 를 직접 불러 만든 뒤 ES 에 저장만 한다. ES 를 쓰는 서비스조차 임베딩은 ES 를 통과시키지 않는다.
3. **청크를 자르는 규칙이 인용 검사와 묶여 있다.** `MarkdownChunker` 의 제목 경로, 표·목록을 통째로 두는 규칙은 인용 검사(`EvidenceAlignment` 의 표 행 "머리글: 값")와 짝이다. ES ingest 로는 이 구조를 표현할 수 없다.
4. **ES 를 거쳐도 임베딩 품질은 그대로다.** ES 분석기(nori)는 BM25 용 토큰을 만들 뿐이고, Qwen3 입력은 원문이다.
   (모델 설정 확인 2026-11-27: `pooling_type 3`(LAST), `add_eos_token true`(`<|endoftext|>`) — Ollama 가 처리하며 우리 코드는 EOS·pooling 을 직접 하지 않는다.)
5. **공유 자원이 병목이다.** PC 2 Ollama 는 한 대이고 RAG·상품 의미 검색(질문 임베딩 제한 1.5초)·꼬리표 생성이 함께 쓴다. 전체 임베딩 642청크에 652초(11-27 실측).
   지금은 임베딩 캐시로 바뀐 청크만 다시 임베딩해 이 부담을 줄인다. 중간에 ES 를 두면 단계만 늘고 이 제어가 어려워진다.

## 3. code-and-pick 에 권하는 적용 — 바꿀 것이 없다

| 영역 | 저장소 | 임베딩 호출 | 상태 |
|---|---|---|---|
| 상품 검색 | Elasticsearch(BM25 + kNN) | search-service → Ollama 직접 | 지금 그대로(ADR-0088) |
| RAG 문서 | pgvector + trgm | RAG 서비스 → Ollama 직접 | 지금 그대로(ADR-0036·0051) |
| RAG 가 상품을 물을 때 | search-service API 호출 | — | 지금 그대로(ADR-0083) |

RAG 품질을 올릴 곳은 저장소가 아니라 11-27 측정이 가리킨 곳이다.

1. 생성 단계의 핵심 빠뜨림 4건 — 프롬프트에서 다룰 수 있다.
2. 부정 검사의 잘못 거절 — 고치는 중(브랜치 `rag/c2-citation-measure`, `docs/rag/verification/2026-11-27/c2-citation-measure/`).
3. 비슷한 문서끼리 헷갈리는 3건 — 임베딩 입력에 문서 제목 붙이기(사용자 결정 대기)가 ES 전환보다 훨씬 싸고 직접적인 시도다(전체 재임베딩 필요).

## 4. 다시 검토할 조건

- 문서가 수천 개를 넘어 검색 시간이 실제로 문제가 될 때.
- 제목 붙이기·가중 조정까지 해도 "키워드로 찾아야 할 청크를 놓친다"가 측정에서 주된 실패 원인으로 남을 때.
- 그때도 순서는 ① Postgres 안에서 조정 → ② 그래도 안 되면 ES(BM25 + nori, 점수 결합은 앱에서) 검토.

## 5. 한계

- 답변 평가는 35문항(답 있는 질문 19개)이라 숫자는 경향으로만 본다.
- 고객 RAG 는 답변 평가셋이 없어 위 숫자는 운영자 RAG 기준이다.
- ES 로 바꿨을 때의 검색 품질은 재 보지 않았다 — "ES 가 더 나쁘다"가 아니라 "바꿀 근거가 측정에 없다"는 판단이다.
