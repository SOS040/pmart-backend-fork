## 0. 이 문서가 말하는 구조

**데이터 적재**

- 상품 DB → ES 상품 인덱스.
- 지식 원본 DB(공개 FAQ·정책, 내부 매뉴얼 — 발행·개정·폐기 상태를 함께 저장) → ES 문서 인덱스(고객용·직원용 분리).
- 공통 임베딩 워커가 상품(SKU 단위)·문서(규정·절차 단위)를 임베딩해 **PostgreSQL + pgvector** 에 저장한다(상품 벡터·공개 정책 청크·내부 매뉴얼 청크 표 분리).
- 재고·가격·주문·배송은 색인하지 않고 검색할 때 업무 API 로 현재 값을 조회한다.

**검색 요청**

- 고객 앱·직원 콘솔 → **공통 검색 API**(인증 정보로 공개 범위·매장·직무 권한 확정).
- 주문·배송 현재 값 → 업무 API.
- 상품·문서 → ES 키워드·필수 조건 검색 → **"ES 결과로 요청이 충족됐나?"**

| 종료 지점 | 언제 | 돌려주는 것 |
|---|---|---|
| ① ES 에서 종료 | 조건에 맞는 카드나 승인 FAQ 답변이 있을 때 | 상품·문서 카드, 승인 FAQ |
| ② 벡터 검색으로 종료 | ES 후보가 부족하면 질문 임베딩 → pgvector → ES 후보와 병합 | 검증된 상품·문서 카드 |
| ③ Qwen-Thinking | 비교·규정 설명·절차 조합이 필요하고 근거가 충분할 때 | 고객 답변 / **직원용 초안**(인용·권한 재검증) |
| 그 밖 | 필수 조건 미충족·근거 부족 | 결과 없음 · 조건 확인 · 담당 부서 안내 |

- 원칙: "벡터 검색은 후보를 찾는 것, LLM 은 확보된 정보를 비교·설명하는 것".

## 1. 총평

- 앞의 ES 중심 제안(PR #558 리뷰 대상)보다 **지금 우리 구조에 훨씬 가깝다.** 벡터를 pgvector 에 두고, ES 는 키워드·조건 검색에 쓴다. "싼 단계에서 끝낼 수 있으면 끝내고 LLM 은 마지막"은 지금의 질문 분류 → 상품 정해진 답 → 문서 RAG 순서와 같은 방향이다.
- 앞 리뷰에서 문제로 본 **답 가로채기**를 숨기지 않고 **설계의 중심(종료 지점 ①②③)으로 드러냈다** — 좋은 점이다. 대신 "언제 끝낼지" 판단이 많아지는데 그 기준이 문서에 없다. 이것이 가장 큰 보완점이다.
- 우리 결정과 부딪치는 곳이 셋이다: 상품 벡터를 pgvector 로(ADR-0088 과 다름), 공통 검색 API(서비스 경계), Qwen-Thinking(지금 생각 끔).
- 통째로 채택하기보다 **우리 구조에 없는 좋은 조각을 골라 넣는 것**을 권한다(§5).

## 2. 잘한 점

1. **단계별 종료와 비용 순서** — ES → 벡터 → LLM. 대부분의 요청이 LLM 없이 끝난다. PC 2 의 GPU 하나를 RAG·상품 꼬리표 생성이 함께 쓰는 우리 사정에 맞는다.
2. **역할 분명** — "벡터 = 후보 찾기, LLM = 설명". LLM 이 사실을 만드는 여지를 구조로 줄인다.
3. **현재 값은 업무 API** — 재고·가격·주문을 색인 사본이 아니라 조회 시점에 원천에서.
4. **원본 DB 가 발행·개정·폐기 상태를 가짐** — 조회할 때 적용 개정판·공개 상태를 확인한다. 우리는 스냅숏 단위뿐이고 문서별 버전·상태가 없다(11-20 확인).
5. **독자별 분리** — 고객용·직원용 인덱스·표를 나누고 결과마다 권한을 다시 검증한다.
6. **"문서 찾기" 요청을 따로 봄** — "오배송 매뉴얼 찾아줘"에 답을 지어 주지 않고 **문서 카드**를 돌려준다. 지금 우리에게 없는 유형이다.
7. **직원 답은 "초안"** — 확정 답이 아니라 근거가 붙은 초안으로 보여 준다.

## 4. 보완이 필요한 점

### A. "요청이 충족됐나?"의 기준이 없다 (가장 중요)

- 품질이 갈림길 두 개(①에서 끝낼지, ②에서 끝낼지 ③으로 갈지)에 달려 있는데 기준이 없다.
- 11-27 측정에서 본 문제가 더 많은 곳에서 생긴다.
  - 틀린 것으로 끝냄: N01 처럼 점수만 넘은 관계없는 근거로 끝냄 — ①에서 "부분만 맞는 FAQ"를 승인 답으로 돌려주면 같은 일이 생긴다.
  - 옳은 것을 막음: 검사가 옳은 답을 거절(생성 시도 25개 중 4개).
  - 규칙 판정 오류: "라면 반품 기준"을 상품 카드로 끝냄 — 지금 평가에 이런 질문이 없다.
- 필요한 것: 종료 지점마다 판정 신호(점수·조건 일치·질문 유형)와 기준값, 그 지점 전용 평가 질문("잘못 끝냄"·"끝낼 수 있었는데 넘김"), 운영에서 종료 지점별 비율 기록(지금은 최종 `answerMode` 만 남고 검사 실패 사유는 안 남는다).

### B. ES 결과와 pgvector 결과를 합치는 방법

- ②의 "ES 후보와 병합"은 BM25 와 코사인처럼 척도가 다른 점수를 합치는 일이다. RRF 같은 순위 결합이 필요한데, RRF 점수에는 절대 의미가 없어 "근거 부족" 판정에 못 쓴다(앞 리뷰 §3-A 와 같은 문제).
- 지금은 SQL 한 번의 혼합 점수 절대값으로 임계값 0.425·발췌 하한 0.45 를 맞춰 두었다 — 구조가 바뀌면 다시 맞춰야 한다.

### C. 상품 벡터를 pgvector 로 옮기면 ADR-0088 과 부딪친다

- 상품 의미 검색은 11-25 에 ES `semanticVector` 로 승인됐고, 같은 검색 안에서 BM25 와 점수를 더한다.
- PDF 대로면 상품 검색이 ES 와 pgvector 두 곳을 거친다 — 상품 검색 주인(PC 1)의 결정을 바꾸는 일이다.
- 권함: 상품은 ADR-0088 그대로. PDF 원칙(벡터는 후보 찾기)은 이미 지켜진다.

### D. 공통 검색 API 는 서비스 경계를 바꾼다

- 지금은 운영자 RAG·고객 RAG·search-service 가 따로이고, 두 RAG 는 DB 권한부터 나뉘어 있다.
- 하나로 모으면 서비스를 합치거나 새로 만드는 일이다 — 요청 없이 경계를 합치지 않는 규칙상 service-map·ADR 결정이 필요하다.
- 권한을 한 곳에서 정하는 장점은 지금도 각 서비스가 같은 규칙(출처 확인·운영자 범위)을 따르는 것으로 대부분 얻는다.

### E. Qwen-Thinking 은 지금 설정과 반대다

- 지금 생성은 `qwen3:4b` 생각 끔. LAN 응답 중앙 1.7초·최대 9.7초, Ollama 호출 제한 25초(다시 생성 포함).
- 생각 모드는 답 앞에 긴 추론을 생성해 느려진다. 켰을 때 시간을 **잰 기록이 없다.** GPU 를 상품 꼬리표 생성과 함께 쓴다.
- 권함: ③에서만 생각 모드를 켜는 실험을 하되, 응답 시간·정답률을 지금 평가셋으로 잰 뒤 정한다.

### F. 임베딩 워커가 "ES 에서 대상 버전을 확인"한다

- 정본은 지식 원본 DB 인데 버전을 사본인 ES 에서 확인하면 순서가 뒤집힌다 — ES 색인이 늦거나 실패하면 임베딩도 어긋난다.
- 버전 확인은 원본 DB 에서 하는 것이 맞다(ES 를 말뭉치로 읽는 것은 괜찮다).

### G. 직원 "초안"과 고객 "답변"의 차이를 정해야 한다

- 같은 ③을 거쳐도 직원에게는 초안, 고객에게는 답이다. 고객 쪽 검증을 더 엄하게 할지(지금 고객 추가 검사 있음), 직원 초안은 발췌로 떨어지는 대신 경고를 붙여 보여 줄지 정해야 한다.

## 5. 우리 구조에 넣을 만한 조각 (ES 로 옮기지 않고도 가능)

| 순위 | 조각 | 어떻게 | 효과 |
|---|---|---|---|
| 1 | **문서 찾기 → 문서 카드** | "~매뉴얼 찾아줘"·"~문서 어디 있어?"를 분류해 생성 없이 상위 문서 카드(제목·조·위치). 검색은 지금 pgvector 그대로 | 모델 호출 0, 지어낼 여지 없음. 직원 질문에 많은 유형 |
| 2 | **종료 지점별 기록** | 분류·상품·임계값·검사 실패 규칙·다시 생성·발췌 전환마다 횟수(질문 원문 없이) | §4-A 의 바탕(앞 리뷰 F-4 의 1번과 같음) |
| 3 | **가격은 원천 조회** | 상품 정해진 답의 가격을 search-service 사본 대신 가격 서비스에서 읽을지 검토 | 사본 지연으로 가격이 틀릴 위험 감소. 필요하면 요청서로 |
| 4 | **직원 답에 "초안" 표시** | 운영자 응답에 근거 붙은 초안 표시(백오피스 화면 협의) | 직원이 답을 확정 정책으로 오해하지 않게 |
| 5 | **고객 승인 FAQ 바로 답** | 질문이 FAQ 와 거의 같으면 생성 없이 FAQ 답 | 빠르고 안전. 11-20 결정("FAQ 는 목록 화면 전용") 변경이라 사용자 확인 필요 |

지금은 넣지 않을 것: 정책·매뉴얼 ES 적재(측정 근거 없음 — PR #557 판단 기록, 계획의 P3 관문에서 다시 봄), 상품 벡터 pgvector 이전(ADR-0088), 공통 검색 API(서비스 경계), Qwen-Thinking(측정 전 — 계획의 P5).

## 6. 앞 리뷰(PR #558)와의 관계

- 앞 리뷰의 "답 가로채기" 지적이 이 PDF 에서는 설계의 중심이다 — §4-A(종료 기준과 측정)가 두 문서 공통의 최우선 과제다.
