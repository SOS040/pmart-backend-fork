# 인용 검사 기준 평가와 다시 설계 (2026-11-21, PC 4)

요청(사용자 2026-11-21): "기준선 모드가 반복되는 이유" → "인용 검사 기준이 적절한지 평가" → "고친다면 1·2·3 진행, 4(부정 검사)는 다시 설계, 5·6 은 맨 뒤로".

## 무엇을 쟀나
- 실제 검사 코드(`CitationVerifier`, 고객 `CustomerAnswerChecks.numbersWhole`)에 실제 rag-docs 조문 8개(배달팁·구매 상한·취소 시점·회수비·리뷰·인계 허가·원문 열람·전달 실패)를 근거로 넣고, **사람(Claude)이 쓴** 옳은 답 12개·틀린 답 10개를 돌렸다.
- **한계**: 실제 모델(qwen3:4b) 답이 아니고 표본이 작다. 아래 수는 이 22개에 대한 결과이지 운영 발생률이 아니다.
- 의미 유사도 기준값: PC 2 Ollama `qwen3-embedding:0.6b`(LAN 과 같은 모델)로 답 문장 20개 ↔ 근거 단위 76개를 임베딩해 문장마다 최대 코사인을 쟀다(생성 모델은 부르지 않음).

## 바꾼 것 (운영자·고객 같은 코드)
1. **프롬프트 규칙 3·4(운영자)**: 근거의 지위·생애·구현 날짜를 답에 밝히라던 것을 "옮겨 쓰지 않는다"로. rag-docs 에는 지위 표시가 없어 근거에 없는 문장("확정된 정책입니다")이 생겨 문장 검사에 떨어졌다. 고객 프롬프트에는 이 규칙이 없었다.
2. **숫자 검사(다시 설계)** `EvidenceAlignment` + `CitationVerifier.numbersSupported`
   - 근거를 단위(문장·목록 항목·표 행 — 행은 "머리글: 값, …")로 나누고 목록 번호("1.")를 뗀다.
   - 답 문장을 구절(", ")로 나누고, 구절의 낱말 줄기(앞 두 글자)를 가장 많이 덮는 **숫자 있는 근거 단위**에 같은 값이 있어야 한다(동점이면 그 중 하나에라도).
   - 값으로 비교: "4,000"="4천", "3만"=30000, "1만 5천"=15000, 온전한 수만("200" 안의 "20" 아님).
3. **문장 뒷받침**: bigram 겹침 0.5 이상 **또는** 의미 유사도 0.65 이상(ollama 일 때만, `EmbeddingSentenceSimilarity` — 답 문장과 근거 단위를 한 번에 임베딩, 실패하면 의미 검사 없이 bigram 결과대로). 해시 기준선(local·시험)은 bigram 만.
4. **부정 검사(다시 설계)** `CitationVerifier.negationMismatch`
   - 구절 줄기 3개 이상, 가장 잘 덮는 근거 단위의 덮는 비율 0.6 이상, 다음 단위보다 0.1 이상 높을 때만 검사(짝이 분명하지 않으면 건너뜀 — 바꿔 말한 답을 버리지 않게).
   - 표 행이면 구절과 낱말이 겹치는 머리글의 가능·불가 칸으로, 없으면 구절을 가장 잘 덮는 칸 조각으로 긍정·부정을 본다(한 행에 "취소: 불가"와 "반품 안내"가 같이 있어도 구별).
   - 시험 표본에서 부정 뒤집기·잘못된 결합을 잡고, 옳은 답을 잘못 거절하지 않았다.
