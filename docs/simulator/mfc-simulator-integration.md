# MFC 시뮬레이터 ↔ 실서버·실제 앱 연결 — 목표와 결정 기록

> 시작 2026-11-09. **결정이 생기면 이 문서에 날짜와 함께 적는다**(결정 표의 상태 + 항목의 "결정" 줄 + 맨 아래 "결정 이력"). "추천"은 제안일 뿐 결정이 아니다. "임시 통과"는 지금은 그렇게 가되 나중에 다시 볼 결정이다.
> 시뮬레이터 저장소: `../pmart-mfc-simulation`(백엔드 작업에서는 읽기만). 시뮬레이터 → 백엔드 요청은 그 저장소 `docs/backend-requests.md`(R-01~), 백엔드 → 시뮬레이터 회신·공지는 `docs/handoff/simulator/`.

## 1. 목표 (사용자 2026-11-09)

- 개발 환경에는 실제 MFC 현장이 없다 → **시뮬레이터가 현장을 대신해 눈으로 보여 준다.**
- 시뮬레이터는 평소 **가짜 데이터**(가상 주문·가상 작업자·가상 라이더)로 돈다.
- 여기에 **우리가 만든 실제 앱**(고객 앱 주문, PDA 앱 작업 등)에서 생기는 사건도 같은 화면에서 처리·표시되게 한다.
- 시뮬레이터 안의 **특정 작업자는 실제 PDA 앱이 조종**한다 — 그 작업자는 시뮬레이터 스크립트가 움직이지 않는다.
- 백엔드 계약이 정본이다. **시뮬레이터와 안 맞는 부분은 시뮬레이터 쪽에서 맞춘다.**

### SIM-1. 시간 — 임시 통과(2026-11-09)

- **결정(임시)**: 실서버에 붙은 모드에서는 **1× 실제 시간만**. 배속은 MOCK(가짜 데이터) 모드 전용. 고객 앱은 바꿀 것 없음.
- 이유: 백엔드는 모든 서비스가 실제 시계로 판단한다 — 예약 만료(Hold TTL), 인계 허가 만료, 약속 준비 시각·늦음, 근무·휴게, 배정 추천 구간, 슬롯(Asia/Seoul). 시뮬레이터만 빠르게 돌리면 화면과 서버가 어긋난다.
- 다시 볼 때: 배속을 실서버 모드에도 쓰고 싶어지면 SIM-1a 의 방식과 함께 다시 정한다.

### SIM-1a. 센터 시간 설정 — 안 함(2026-11-09)

- **결정**: 고칠 곳이 많아(아래) **시간 판단은 현재 실제 시각 기준**으로 둔다. 센터 시간 설정 기능은 만들지 않는다. 시간대별 동작을 보고 싶으면 그 시간에 보거나, 시간 규칙 설정값(입고 창·슬롯 마감 등, pmart-config)을 바꿔 확인한다.
- 아래는 그때 검토한 내용(다시 필요해지면 여기서부터).


- **요구**: 배속은 아니어도 **센터 시간을 정할 수 있어야** 한다 — 예약 배송이 어느 시각에 막히는지, 시간대별로 센터가 어떻게 운영되는지(오전 입고 창, 근무, 마감 등) 볼 수 있게.
- **어려운 점**: 시각 판단이 여러 서비스(mfc-capacity 슬롯·입고 창·근무·배정 추천, mfc-fulfillment 인계 허가·늦음, delivery-capacity 슬롯, order·storefront 의 배송 시간 표시)에 흩어져 있고, 만료 정리(TTL)는 DB 시각으로 돈다. 한 서비스만 바꾸면 서로 어긋난다.
- **선택지**
  - (가) **시험 센터 전용 시각 차이(offset)**: 설정(pmart-config, LAN·local 만)에 `센터 → 시각 차이` 를 두고, 그 센터의 판단에 쓰는 시계만 그만큼 민다. 서비스마다 "센터 시계"를 쓰게 고쳐야 한다(공통 라이브러리 + 각 서비스). 운영 설정에는 없어서 운영에서는 동작하지 않게.
  - (나) **시간 규칙 자체를 지금 시각에 맞게 바꿔서 보기**: 예) 입고 창·슬롯 마감 설정값을 지금 시각 근처로 바꿔 동작을 확인. 코드 변경 없음, 대신 "그 시각의 센터"가 아니라 "그 규칙"만 확인.
  - (다) 시뮬레이터 화면에서만 시각을 바꿔 보여 주기(MOCK) — 실서버 판단은 안 바뀜.
- 그때 추천: 먼저 (나), 자주 필요하면 (가)를 별도 설계(ADR)로.

### SIM-2. 실제 PDA 앱이 조종하는 작업자 — 결정(2026-11-09)

- **결정**: 로그인 + 권한으로 구분. 시뮬레이터는 **자기가 움직이는 가상 작업자 계정만** 따로 갖고(SIM-3), 그 밖의 작업자는 전부 실제 사람으로 본다 — 백엔드 변경 없음.
- 실제 작업자도 **다음 작업 받기**로 받으므로 가상 작업자와 같은 작업 풀을 나눠 가진다(현장과 같게, 따로 떼어 두지 않음).
- 실제 PDA 앱(`pmart-clients/apps/mfc_app`)은 지금 작업 목록·포장 화면만 있다 — 다음 작업 받기·피킹 화면 연결은 클라이언트 쪽 일(`docs/handoff/clients/`).

### SIM-2a. PDA 버튼 기준 실제 작업자 추적 — 결정(2026-11-09)

- **결정**: **마지막으로 누른 버튼 기준**으로 따라간다 — 시뮬레이터가 지금 API(아래)로 조합, 백엔드 변경 없음. 실제 작업자는 마지막 버튼의 칸 앞에 두고, 다음 버튼까지는 그 칸들 사이를 걷게 그린다. 조회가 무거워지면 (나)를 다시 본다.


- **요구**: PDA 버튼이 눌린 것을 보고 실제 작업자를 어느 정도 따라가게.
- **지금 백엔드에서 알 수 있는 것**: 배정(누가 어떤 작업을 받았나 — `GET /assignments`), 작업 상태(시작·진행·완료 — `GET /tasks`), 작업 상세의 피킹 실적(어느 칸에서 몇 개 — 작업 상세 `lines[].picks`), 이동 지시의 집기·내려놓기(`GET /move-orders`). 이것으로 "마지막으로 누른 버튼과 그 칸"을 알 수 있다 → 시뮬레이터가 그 칸 앞에 작업자를 두고, 다음 버튼까지 그 칸 사이를 걷게 그리면 된다.
- **모자란 것**: 작업자 한 명 기준으로 "최근 행동 목록(언제 어느 칸에서 무엇을)"을 한 번에 주는 조회가 없다 — 지금은 작업마다 상세를 따로 읽어야 한다.
- **선택지**: (가) 지금 API 로 시뮬레이터가 조합(백엔드 변경 없음) / (나) 백엔드에 "작업자 최근 행동" 읽기 API 추가(fulfillment·inbound 실적을 모아 줌 — 새 계약).
- 결정: (가).

### SIM-3. 가상 작업자 인증 — 결정(2026-11-09)

- **결정**: 시뮬 센터 전용 **실제 운영자 계정**을 가상 작업자마다 하나(그 센터 권한·`MFC_WORKER` 만). 로그인 API 로 토큰을 받는다. 백엔드 변경 없음.
- 비밀번호는 시뮬레이터 실행 PC 의 비밀 파일(Git·브라우저에 두지 않음, SIM-11). LAN 서명 키로 토큰을 직접 만들지 않는다.

### SIM-4. 가짜 주문 — 임시 통과(2026-11-09)

- **결정(임시)**: 실서버 모드에서는 **가짜 주문을 넣지 않는다** — 실서버 모드의 주문은 고객 앱에서 온 실제 주문만, 가짜 주문은 MOCK 모드에서만.

### SIM-4a. 가짜 주문 실서버 투입 — 요구(사용자 2026-11-09), 방식 미결

- **요구**: 나중에는 **가짜 주문도 실서버에 필요하다** — 사람이 모든 주문을 만들 수 없으니, 실제로 돌아가는 모습(여러 주문이 동시에 흐르는 센터)을 확인하려면.
- **선택지**
  - (가) 주문 조정 서비스가 부르는 MFC 내부 API 를 시뮬레이터 서비스 신원으로 직접(LAN E2E 방식) — 빠르지만 주문·결제 서비스를 안 거쳐 고객 앱·주문 조회에는 안 보이고, 시뮬레이터 원칙("`/internal/*` 안 부름")과 충돌.
  - (나) 고객 시험 계정 + Toss 시험 결제로 진짜 경로를 자동으로 — 가장 실제와 같지만 느리고 결제 시험 키·고객 로그인(Google) 자동화가 필요.
  - (다) 백엔드에 "시험 센터 전용 가짜 주문 입구"(결제 없이 주문을 만드는 LAN 전용 경로) — 주문 이후 흐름은 진짜. 새 기능·운영 차단 장치 필요.
- 정할 때 같이: 가짜 주문 표시(SIM-8), 시간당 주문 수 상한(SIM-10).

### SIM-5. 실서버 변화 받기 — 결정(2026-11-09): 주기 조회

- **결정**: 지금 있는 API 를 주기적으로 다시 읽는다(서버 변경 없음). 지켜야 할 것: 조회 간격 몇 초(시작 3초), 재고는 작업에 나온 SKU 만·바뀌었을 때만(SKU 전체 반복 조회 금지). 화면 반응이 1~3초 늦는 것이 문제가 되면 밀어 주기(SSE 등)를 그때 검토.

- 브라우저는 Kafka 를 직접 못 본다. 지금 있는 API 를 몇 초마다 다시 읽는 방식(주기 조회)과, 서버가 바뀔 때 밀어 주는 방식(SSE 등, 새 기능) 중 고른다.
- **성능**(2026-11-09 추정, 측정 아님):
  - 조회 대상: 센터 작업 목록(`GET /tasks?mfcId&state=`, 한 번에 수십 건), 배정 목록(`GET /assignments`), 이동 지시(`GET /move-orders`). 3초마다 3개면 **초당 1건 정도** — LAN 서비스 한 개가 감당하는 양(수백 건/초)에 비해 아주 작다. 게이트웨이 처리율 제한은 계정당 초당 20건이라 걸리지 않는다.
  - **피해야 할 것**: 재고를 SKU 마다 조회(`GET /mfcs/{id}/stock?sku=` 는 SKU 1개씩, 시뮬레이터 SKU 900개). 재고는 작업에 나온 SKU 만, 바뀌었을 때만 읽는다.
  - 가상 작업자도 각자 자기 일을 API 로 하므로(받기·시작·피킹) 그 요청이 더해진다 — 작업자 10명이면 초당 수 건 수준.
  - 로그: 요청마다 게이트웨이·서비스 로그가 남는다. 초당 1~5건이면 하루 수십~수백 MB — 로그 저장소(상한 있음)가 더 빨리 돈다. 필요하면 시뮬레이터 계정의 조회 로그를 줄이는 설정을 따로 검토.
- 그래서 **성능 저하는 거의 없다**(재고 전체 반복 조회만 피하면). 밀어 주기(SSE)는 화면 반응이 1~3초 늦는 것이 문제가 될 때 검토.

### SIM-6. 센터·위치·재고 — 결정(2026-11-09)

- **결정**: 백엔드 구현 기준. 시뮬레이터가 LAN 시험 센터 `MFC-SEED-01` 의 위치(`A-S9-01-1-01` 형식)·재고·작업을 읽어 그 코드로 그린다. 시뮬레이터 평면(가정)·칸 코드(`C01-03-205`)는 시뮬레이터가 맞춘다.

### SIM-7. 라이더 — 결정(2026-11-09)

- **결정**: 지금은 시뮬레이터가 "출하 대기"까지 실서버로, 라이더 인계는 MOCK 으로만 그린다. 배송 서비스(DD-1·DE-1) 구현 뒤 가상 라이더 = 라이더 시험 계정(SIM-3 과 같은 방식).

### SIM-8. 가짜 실적 구분 — 결정(2026-11-09)

- **결정**: 시뮬 센터·시뮬 계정으로 구분한다(별도 필드 없음). 원장 출처 필드는 운영 전 필요해지면 계약 추가로 다시 본다.

### SIM-9. 정리 — 결정(2026-11-09)

- **결정**: 실행이 끝나면 시뮬레이터가 API 로 정리한다 — 열린 작업 중지·취소 복귀, 이동은 되돌리는 이동(LAN E2E 가 매번 재고를 처음 수치로 되돌리는 방식). DB 직접 수정 금지.

### SIM-10. LAN 부하·PC 배치 — 결정(2026-11-09): 지금 옮기지 않음

- **결정**: 지금 서비스를 다른 PC 로 옮기지 않는다. 아래 신호가 오면 다시 정한다.

- 2026-11-09 메모리 여유: pc2 11.2GB, pc3 7.2GB, pc4 약 5GB(cardcapture 묶음을 멈춘 뒤). 각 PC 의 Docker 할당 약 23.5GB 중 컨테이너 사용 8~11GB.
- 시뮬레이터 자체는 브라우저 앱이라 LAN 서버 PC 에 올라가지 않고, 서버에 더해지는 부하는 SIM-5 의 요청 정도다 — **지금 서비스를 옮길 필요는 없다.**
- 옮길 때가 오는 신호: 어느 PC 의 여유가 3GB 아래로 떨어질 때, 또는 배송 서비스 5개(pc3)가 실제로 구현돼 데이터가 쌓일 때. 그때 후보는 pc4 의 로그 계열(가장 빠듯)이나 pc3 → pc2(여유 최대). 옮기는 것은 `deploy/lan` 배치 변경이라 따로 정한다.

### SIM-11. 접속 경로·비밀번호 보관 — 결정(2026-11-09): (가) Vite 프록시

- **결정**: 시뮬레이터는 Vite 개발 서버 프록시로만 게이트웨이에 붙는다(게이트웨이 CORS 변경 없음). 가상 작업자 비밀번호는 Vite 서버 쪽 비밀 파일(Git 금지)에서 읽어 로그인하고, 브라우저에는 토큰만 간다.

- **무엇을 정하는가**: 시뮬레이터(브라우저 화면)가 게이트웨이에 어떻게 붙고, 가상 작업자 비밀번호를 어디에 두는가.
- **배경**: 브라우저는 다른 주소의 서버를 부를 때 그 서버가 "이 주소는 허용"이라고 답해야 한다(CORS). 게이트웨이는 허용 목록(ADR-0018)에 등록된 화면 주소만 받는다. 시뮬레이터는 Vite 개발 서버(그 PC 의 작은 웹 서버)가 화면을 주고, 그 서버가 `/api` 요청을 게이트웨이로 대신 넘겨 줄 수 있다(프록시) — 이러면 브라우저 입장에서는 같은 주소라 CORS 가 필요 없다.
- **선택지**: (가) 프록시로만 붙음 — 게이트웨이 설정 변경 없음, 비밀번호는 Vite 서버 쪽 비밀 파일에서 읽어 로그인하고 브라우저에는 토큰만 / (나) 게이트웨이 허용 목록에 시뮬레이터 주소 추가 — 브라우저가 직접 부름, 비밀번호나 토큰을 브라우저가 들고 있어야 함.
- **추천**: (가). 백엔드 변경 없고 비밀번호가 브라우저로 나가지 않는다. 시뮬레이터를 여러 PC 에서 띄울 때도 각 PC 의 비밀 파일만 있으면 된다.
