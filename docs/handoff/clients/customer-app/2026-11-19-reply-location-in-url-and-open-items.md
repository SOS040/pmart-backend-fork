# 회신 — 좌표가 URL 에 담겨 서버 기록에 남는 문제 + BR-19·BR-32·BR-49 진행

- 보낸 영역: platform (PC 1)
- 작성: pmart-backend, 2026-11-19
- 답하는 것: 고객 앱 질문 "좌표를 주소로 바꾸는 요청이 좌표를 URL 에 담아 보내서 서버 기록에 현재 위치가 남는다 — 요청 방식을 바꿀지"

## 1. 좌표가 서버 기록에 남는지 — 맞았다, 서버가 고쳤다(요청 방식은 그대로)
- 확인(2026-11-19 LAN 시험): `GET /address-reverse-geocodes?lat=&lng=` 를 부르면 **게이트웨이 추적(Zipkin) 의 `http.uri` 에 URL 전체(좌표 포함)가 남았다.** 서비스 쪽 추적은 경로만, 카카오 호출은 기록 없음.
- 고침: 게이트웨이 추적에 **경로까지만** 남긴다(조회 조건 `?…` 를 뺌 — api-gateway `TraceUriWithoutQuery`, 이미지 9e977d49, LAN 배포). 다시 시험: 새 좌표가 들어간 추적 0건, `http.uri` = `…/api/v1/address-reverse-geocodes`.
- 그래서 **앱은 요청 방식을 바꾸지 않아도 된다**(GET 그대로). 좌표뿐 아니라 URL 에 개인정보가 들어가는 다른 조회(상담원 전화번호 주문 찾기 등)도 같이 해결됐다.
- 남은 것: 고치기 전 추적 기록(시험 좌표 포함)은 보관 기간이 지나야 사라진다.

## 2. BR-19 100g·100mL당 가격 — 기준 추천(사용자 결정 대기)
- 레퍼런스(`customer-app-design/3-2. 홈화면 프로모션/23`): 카드 가격 아래 회색 "100g당 999원". **판매가(할인 중이면 할인가) 기준**(1kg 9,990원 → 999원, 500g 할인가 5,290원 → 1,058원). 내용량이 개수(2입 등)뿐인 상품에는 없다.
- 상품 데이터의 무게(`weightG`)는 포장 무게 한도용 물류 값이라 내용량으로 쓰지 않는다. 추천: SKU 에 **내용량**(숫자 + g·mL, 선택)을 두고, 서버(product-content)가 "판매가 ÷ 내용량 × 100" 을 원 단위 반올림해 카드·상세에 싣는다. 내용량이 없으면 싣지 않는다. 정해지면 다시 알린다.

## 3. BR-32 휴대폰 번호 저장 — 본인 확인 없이 "확인 안 된 연락처"로 저장(만들 예정)
- 막혀 있던 것은 일부러(본인 확인 방식을 정한 뒤 받기로) — 기술 문제가 아니다. 사용자 결정(2026-11-19): 본인 확인은 미루고 저장만.
- 저장은 `phoneVerified=false` 로, 쓰는 곳은 배송지 받는 분 연락처 채우기뿐(로그인·본인 확인·주류 연령 확인에 쓰지 않음). 만들면 계약 버전과 함께 다시 알린다.

## 4. BR-49 홈 진열에서 미취급 상품 빼기 — PC 1 이 만든다
- 필요한 "센터 취급 여부" 사건(`SkuHandlingChanged`)은 mfc-inventory 가 이미 낸다(검색은 이미 씀). storefront 가 이 사건을 받아 그 센터 미취급 상품을 빼도록 만든다(PC 3 요청 필요 없음). 만들면 다시 알린다.

## 덧붙임 — BR-49 만들었다(storefront 0.2.0, LAN 배포 전)
- `mfcId` 를 주면 홈·탭·섹션 항목에서 **그 센터가 대표 SKU 를 취급하지 않는 상품은 뺀다**(검색 기본과 같은 기준 — mfc-inventory 취급 사본, 레코드 없음 = 미취급). 남은 줄은 **`carried=true`**, `mfcId` 가 없으면 거르지 않고 `carried=null`.
- 빼고 나서 비어도 **섹션은 생략하지 않는다**(`items=[]`·`nextCursor=null`, state OK). 섹션 항목 목록도 빈 쪽 + 다음 커서 없음.
- 정책(요청 #4): **숨김**(검색과 같다 — 사용자 결정). 업무 문서의 "구분 표시"와는 다르다는 점은 계약 설명에 남겼다.
- 앱은 바꿀 것이 없다(서버가 빼서 준다).
