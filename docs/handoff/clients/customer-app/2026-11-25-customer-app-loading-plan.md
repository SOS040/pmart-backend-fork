# 고객앱 로딩 개선 계획 (2026-11-25)

- 근거: `docs/apps/customer-app-loading-structure.md` (로딩 구조·의심 지점 S1~S10)
- 전제: 서버 API 응답은 이미 빠름(홈 0.07~0.09초). 느린 원인은 주로 **앱 구조와 이미지**.
- 주의: 아래 항목은 코드를 읽고 고른 후보이며, 아직 기기에서 측정한 결과는 아니다.

## 1. 진행 순서

| 순서 | 할 일 | 관련 지점 | 기대 효과 |
|---|---|---|---|
| 1 | **profile 빌드로 화면별 시간 재기** | S1 | 지금 APK 는 debug 빌드라 화면 그리기가 몇 배 느림. 진짜 병목부터 확인 |
| 2 | **홈 배너 이미지 압축** (PNG 약 2.2MB → WebP/JPG, 화면 크기에 맞춤) | S2, BR-99 | 장당 수백 KB 이하로 줄어 홈 첫 화면이 빨라짐 |
| 3 | **이미지 디스크 캐시 도입** (`cached_network_image` 등) | S3 | 두 번째 실행부터 사진이 바로 뜸 |
| 4 | **시작 단계 병렬화** | S4 | 프로모션(최소 1.5초) → 세션 → 주소록 → 홈의 순차 대기 축소 |
| 5 | 이미지 S3 + CDN(CloudFront 등) 이전 | S2, S3 | 이미지 다운로드 가속, API 서버 부담 감소 |

### 4번 상세 — 시작 단계
- 프로모션 최소 노출 1.5초를 줄이거나 다른 단계와 겹쳐서 진행한다.
- 서로 기다릴 필요가 없는 단계(처음 실행 여부, 세션 확인 등)는 동시에 시작한다.

## 2. 그 밖의 개선 후보

- **상품 상세 요청 2번 → 1번** (S5): 콘텐츠를 받은 뒤 가격을 또 받는다. 백엔드에 둘을 합친 응답을 요청하거나, 가격 없이 본문을 먼저 그린다.
- **리뷰 자격 목록 최대 10쪽 순차 조회 정리** (S6)
- **autoDispose 화면에 짧은 유지 시간** (S7): 주문내역·리뷰 등
- **주문 목록 `imageUrl` 확인** (S9): 없으면 상품마다 요청이 2번씩 나간다.

## 3. S3 + CDN 에 대해

지금 이미지는 게이트웨이 `/api/v1/content-images/{imageId}` 를 통해 내려간다. S3 에 올리고 앞에 CDN 을 두면:

- 사용자와 가까운 서버에서 캐시된 이미지를 주니 다운로드가 빠르고, API 서버 부담이 줄어든다.
- 긴 캐시 헤더, 리사이즈, WebP 변환을 붙이기 쉽다.

**한계**
- 2.2MB 이미지는 CDN 을 거쳐도 2.2MB → 압축(2번)이 먼저다.
- 앱에 디스크 캐시가 없으면 재실행할 때마다 다시 받는다 → 디스크 캐시(3번)도 필요하다.
- debug 빌드, 순차 요청, 상세 2단 요청 같은 구조 문제에는 효과가 없다(API 는 이미 빠름).

## 4. 캐시 정책

### 4-1 이미지 (가장 중요)
먼저 백엔드에 확인할 것: **`content-images/{imageId}` 는 같은 ID 에서 내용이 바뀔 수 있는가?**

- **안 바뀜** (새 이미지는 항상 새 ID):
  `Cache-Control: public, max-age=31536000, immutable` — 1년 캐시. CDN·앱 모두 다시 받지 않는다.
- **바뀔 수 있음**: URL 에 버전을 붙인다(`?v=해시`). 바뀌면 주소가 달라지게 한 뒤 위와 같이 길게 캐시한다. 짧은 캐시보다 낫다.

### 4-2 앱 디스크 캐시
- `cached_network_image` 기본값(보통 30일, 개수 제한)이면 충분하다.
- 서버가 캐시 헤더를 제대로 주면 앱에서 따로 설정할 것이 거의 없다.

### 4-3 API 데이터 (가격·재고·주문 등)
- **CDN 에 캐시하지 않는다.** 가격·재고가 틀리게 보이면 사고가 난다.
- 앱 메모리(Riverpod)에서만 화면별 유지 시간을 정한다.

| 데이터 | 유지 시간 | 비고 |
|---|---|---|
| 홈 | 1분 | 지금처럼(`homeStaleAfter`) |
| 상품 상세 | 5분 | 지금처럼(`productDetailKeep`) |
| 카테고리 | 길게(하루 정도) | 자주 안 바뀜 |
| 주문내역·리뷰 | 30초~1분 | 지금은 화면을 나가면 바로 버림 |

### 4-4 한 줄 요약
- **이미지: URL 이 안 바뀌면 영원히 캐시.**
- **데이터: 앱에서 짧게 유지.**
- 첫 할 일: 백엔드에 이미지 ID 의 내용이 바뀔 수 있는지 묻기.

## 5. 백엔드 답 (pmart-backend 2026-11-25 — 위 4-1 "첫 할 일"과 2번)
- **`content-images/{imageId}` 는 같은 ID 에서 내용이 바뀌지 않는다** — 내용 주소(sha256) 기반, 새 사진은 새 ID. 이미 `Cache-Control: public, max-age=31536000, immutable`·ETag `<sha256>`(축소본 `?w=240|480|720` 은 `<sha256>-w<폭>`). 배너 `storefront/banner-images/{imageId}` 도 같다(이미지 ID 마다 불변, 1년 immutable).
- **2번(배너 압축)은 끝** — BR-99 storefront 0.16.0 LAN 배포: `?w=` 를 붙이면 360·720·1080·1440 단계 JPEG(2.1~2.3MB PNG → 1080 은 98~112KB, 720 은 51~59KB). 회신 `2026-11-25-reply-br99-banner-image-width.md`. 앱은 배너 주소에 `w` 만 붙이면 된다.
- 그래서 앱은 이미지에 디스크 캐시(3번)만 붙이면 두 번째 실행부터 다시 받지 않는다 — 서버 쪽 버전 쿼리(`?v=`)는 필요 없다.
- 상세 2번 요청(S5): product-content 상세는 이미 옵션 가격(`price`)·평점·가용(mfcId)을 함께 준다 — 앱이 따로 부르는 가격 요청이 무엇인지 알려 주면 확인한다.
