# 요청: 검색어 교정 문구 표시 (`correctedQuery`·`suggestedQuery`·`noCorrection`)

- 보낸 영역: platform (PC 1)
- 작성: pmart-backend, 2026-11-20
- 근거: ADR-0073 동의어·오타 교정 단계 D(사용자 2026-11-20 "그럼 그렇게 해줘")
- 받는 곳: customer-app (`apps/customer_app/lib/features/catalog` 검색 결과 화면)
- 서버 상태: search 0.4.0~0.5.1 **LAN 배포됨**. 0.5.1(다음 쪽)은 같은 날 배포한다(아래 '상태' 줄).

## 서버가 주는 것 (`GET /search/products` 결과)
교정은 다음 조건을 모두 만족할 때만 한다.
- 첫 쪽이다.
- 검색어가 있다.
- 초성 검색(예 "ㅅㄷㅂ")이 아니다.
- `noCorrection=true`를 보내지 않았다.

| 경우 | 응답 | 결과 목록 | 앱 문구(예) |
|---|---|---|---|
| 원래 검색어 결과 0건 → 고친 검색어로 찾음 | `correctedQuery: "순두부"`, `query: "순두뷰"` | **고친 검색어**의 결과 | "**'순두부'** 검색 결과예요" + 작은 링크 "'순두뷰'로 검색하기" |
| 결과가 적음(지금 3건 이하) + 고친 검색어가 더 많이 찾음 | `suggestedQuery: "순두부"` | **원래 검색어**의 결과 | "혹시 **'순두부'**를 찾으셨나요?" (누르면 q=순두부로 새 검색) |
| 그 밖 | 둘 다 null | 원래 결과 | 없음 |

- "'순두뷰'로 검색하기"는 같은 검색에 `noCorrection=true`를 붙여 부른다. 그러면 원래 검색어 결과 0건이 그대로 온다. 빈 결과 화면을 보여 주면 된다.
- **다음 쪽(0.5.1):** `correctedQuery`가 있던 검색의 다음 쪽은 **같은 원래 `q` + `cursor`**로 부르면 서버가 고친 검색어로 이어 준다. 다음 쪽 응답에도 `correctedQuery`가 실린다. `q`를 고친 검색어로 바꿔 불러도 결과는 같다.
- 자동완성(`/search/suggestions`)은 일치하는 후보가 없으면 서버가 이미 고친 검색어 후보를 준다. 앱이 할 것은 없다.
- 고치는 낱말은 실제 상품명에 있는 낱말뿐이다. 숫자·영문 모델명은 고치지 않는다.

## 요청
1. 검색 결과 화면 위에 위 표의 문구 두 가지를 띄운다(배민·쿠팡 검색 결과 상단 안내처럼).
2. "'원래 검색어'로 검색하기"를 누르면 `noCorrection=true`로 다시 찾는다. 이 화면에서는 교정 문구를 띄우지 않는다.
3. 최근 검색어에는 사용자가 친 원래 검색어를 남긴다. 서버 기록도 원래 검색어다.
4. 목 데이터에 두 경우를 넣어 화면을 확인한다. LAN 예: "순두뷰", "샹크림".
