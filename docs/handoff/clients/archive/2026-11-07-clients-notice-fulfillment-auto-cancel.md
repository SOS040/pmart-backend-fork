## 1. 무엇이 바뀌었나
주문이 확정되면 백엔드가 MFC 에 작업(피킹·패킹)을 요청한다. MFC 가 작업을 받지 못하면(재고 예약 불일치·센터 운영 중단·작업 여력 부족 등) **고객에게 묻지 않고 주문 전체를 자동 취소하고 결제액 전액을 환불**한다(사용자 결정 D6-4). 다른 MFC 로 옮기지 않는다.

- 재고 불일치·운영 중단은 같은 MFC 에서 **최대 10분 동안 1분마다 다시 확인**하고, 되찾으면 작업을 다시 요청한다(최대 2번). 그동안 주문 상태는 `CONFIRMED` 그대로다.
- 예약 배송은 슬롯 시작 시각이 지나면 기다리지 않고 바로 자동 취소한다.
- 자동 취소의 뒤 흐름은 고객 취소와 같다: 클레임 `STOP_PENDING` → 주문 `CANCELLED` → 환불 → 클레임 `CLOSED`.
- 2026-11-07 00:00(UTC) 전에 확정된 주문은 대상이 아니다.

## 2. 고객 앱이 할 일
| # | 할 일 | 내용 |
|---|---|---|
| C1 | **클레임 사유 `FULFILLMENT_REJECTED` 표시** | `GET /api/v1/claims/{claimId}` 의 `reason` 에 새 값이 온다. 모르는 값으로 화면이 깨지지 않게 하고, 문구는 예: "상품 준비가 어려워 주문이 자동 취소되었어요. 결제하신 금액은 전액 환불됩니다." 고객이 접수한 클레임이 아니므로 "취소 요청하신" 같은 문구를 쓰지 않는다 |
| C2 | **취소된 주문에서 사유 찾기** | 주문 상세 `GET /orders/{id}` 의 `claims` 는 아직 빈 배열이다. 주문이 `CANCELLED` 이면 `GET /api/v1/claims?orderId=<주문ID>`(본인 것만) → 가장 최근 `CANCEL` 클레임의 상세로 `reason` 을 본다. 자동 취소 클레임도 고객 본인 계정으로 만들어지므로 목록에 보인다 |
| C3 | **환불 상태** | 고객 취소와 같다 — `GET /api/v1/claims/{claimId}/refunds`. 환불 `COMPLETED` 전에는 "환불 완료"로 보이지 않는다 |
| C4 | **고객 취소와 겹칠 때** | 자동 취소가 이미 진행 중인 주문에 고객이 취소를 누르면 `POST /claims` 가 422 `DUPLICATE_CLAIM` 을 준다 → "이미 취소가 진행 중이에요"로 안내하고 클레임 상세로 보낸다. 반대로 고객이 먼저 취소했으면 자동 취소는 새로 만들지 않는다(고객 클레임 그대로) |
| C5 | **상태 갱신** | 자동 취소 알림(푸시)은 아직 없다. 주문 목록·상세를 열 때 다시 조회해서 `CANCELLED` 를 보여 준다. 확정 직후 최대 약 10분 안에 `CONFIRMED` → `CANCELLED` 로 바뀔 수 있다 |

변경 없음: 결제 진입·승인, 고객 취소 접수(`POST /claims` 본문·검증), 주문 상태 값 목록. 주문 상태 `PREPARING`(상품준비)은 아직 나오지 않는다 — 첫 피킹 시작 때(다음 단계 6b) 생긴다. 그 전까지 고객 취소는 계속 열려 있다.
