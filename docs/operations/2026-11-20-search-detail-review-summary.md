### 1-2. 순위 정렬 (ADR-0072, products-v6)
- **storefront가 순위 신호의 정본이다.**
  - 판매 원장은 `sku_sales_line`이다. 주문 확정에서 출고 전 취소와 반품을 뺀다.
  - 리뷰 사본으로 베이지안 별점을 계산한다. 사전 개수 20, 사전 평균 4.0이다.
  - 값이 바뀔 때만 `ProductRankingSignalsChanged`를 낸다. 매일 04:40에 전부 다시 계산한다.
- Logstash가 받아 색인에 넣는다.
- 정렬 `POPULAR`·`RATING`·`REVIEW_COUNT`가 실제로 동작한다. 신호가 없는 상품은 맨 뒤로 간다.
- 결과에 `rating`·`reviewCount`가 실린다. 커밋 06f1d33b·31207d5a, 계약 search 0.3.0이다.
- **조정:** 처음에는 리뷰 1개짜리 5.0점이 리뷰 480개의 4.1점보다 위로 올라갔다. 사전 개수를 5에서 20으로 올렸다(사용자 결정).

### 1-3. 동의어·오타 교정 (ADR-0073)

**A단계 (509ed49e, products-v7):**

| 기능 | 내용 |
|---|---|
| 동의어 | 상품명 검색 분석기에 synonym_graph를 넣었다. ES 동의어 집합(`pmart-product-synonyms`)을 쓰므로 바뀌어도 재색인이 필요 없다 |
| 오타 사전 | 상품명 낱말과 자모로 10분마다 다시 만든다 |
| 결과 0건 | 고친 검색어로 다시 찾는다(`correctedQuery`) |
| 결과가 적을 때 | 3건 이하면 다른 검색어를 제안한다(`suggestedQuery`) |
| 자동완성 | 교정한 후보를 준다 |
| 0건 검색어 API | MD·운영 관리자만 볼 수 있다 |

- **B단계 (2dd97d4e):**
  - 승인 유형 `SEARCH_SYNONYM`. MD나 운영 관리자가 요청하고, 운영 관리자가 승인한다. 자기 승인은 막는다.
  - search-service는 DB가 없다. 승인 ID와 규칙 버전으로 같은 승인을 두 번 반영하지 않는다.
  - 기준 버전이 같을 때만 규칙 전체를 반영하고 회신한다.
  - 운영 조회는 `/search/synonym-rules`와 `/search/synonym-rule-applications`다.
- **배포:** A단계는 PR 세션이 배포했다(cc99fe73). B단계는 config 7b2b18c, 이미지 3ef008b3이다.
- **남은 것:**
  - C: 백오피스 동의어 관리 화면
  - D: 고객 앱 교정 문구
  - E: 처음 동의어 목록
  - 예전 색인 products-v5·v6 지우기

## 2. 상품 상세 (목록 카드 포함)

| 단계 | 결과 |
|---|---|
| 상세 API (상세 + 가격) | 50~90ms. 원인이 아니다 |
| 사진 거절(게이트웨이) | 앱 사진은 토큰 없이 와서 IP 단위 익명 한도에 걸렸다. 카테고리 들어가기 22건 중 2건, 스크롤 21건 중 11건, 상세(API 4 + 설명 사진 16~20장)도 같은 문제 |
| 처음 보는 상품의 설명 사진 | 축소본을 요청 때 동시 2장씩 만들어 16~20장에 0.7~1.5초. 다시 보면 0.1초 |
| 용량 | 축소본(w720)으로도 상품 하나에 1.5~1.7MB |

고친 것:
- **게이트웨이:** `/api/v1/content-images/*`·`/api/v1/review-photos/*`를 처리율 제한에서 뺐다(pmart-config 50bc343). 같은 재현에서 429가 0건이 됐다.
- **축소본:**
  - product-content 0.3.0 `?w=240|480|720`(5687c41a)
  - 뒤에서 미리 만들기 `VariantPreparer`(V4), 요청 때 만들기 동시 2 → 4(4460c4d1)
  - 기존 사진 일괄 처리는 배포 뒤 뒤에서 돌았다.
- **평점:** BR-63(8f43c02b). 상세·카드·홈 진열에 평점·리뷰 수를 실었다. product-content 0.3.0, storefront 0.4.0·V6.
- **흐름 설명 문서:** `docs/architecture/product-image-variants.md`
- **앱 쪽:** 이미 축소본, 화면 크기 디코딩, 보일 때만 받기를 하고 있다(요청서 11-19 두 건이 반영됨).

## 3. 리뷰 보기

- **측정:** 리뷰 API는 10~50ms다. 문제는 사진이다.
  - 앱은 2048px·화질 85로 올리고, 실제 고객 사진은 300~550KB였다.
  - 서버가 원본만 준다.
  - 앱 썸네일 세 곳이 원본 해상도로 디코딩한다(`cacheWidth` 없음).
- **시험 데이터:** 당근 상품(`PRD-1c4fa477…`)에 리뷰 120개, 사진 리뷰 67개, 사진 129장(폰 크기 2048×1536, 약 0.5MB)을 넣었다.
  - `deploy/lan/seed/review_bulk.py`로 넣었다. 옵션은 `--photos`, `--texts=carrot`, `--replace-photos`다.
- **고친 것:** review-service 0.4.0 `?w=240|480|720`, `ReviewPhotoPreparer`(V3 `variants_at`), 고아 사진 정리 때 축소본도 지운다(3f8bad3f).
- **결과:** 앱이 `?w=`를 붙이면 아래와 같다.

| 화면 | 사진 | 고치기 전 | 고친 뒤 |
|---|---|---|---|
| 리뷰 목록 첫 쪽 | 15장 | 7.9MB | 146KB |
| 사진 리뷰만 | 35장 | 18.3MB | 353KB |
| 크게 보기(w720) | 35장 | 18.3MB | 2.2MB |

- **앱 요청:** `docs/handoff/clients/customer-app/2026-11-20-request-review-photo-thumbnails.md`
  - 썸네일은 `?w=240`, 크게 보기는 `?w=720`을 붙인다.
  - 썸네일에 `cacheWidth`를 준다.
  - **앱이 반영하기 전까지 폰 화면은 그대로다.**

## 5. 리뷰 결과 (2026-11-20, 별도 검토 에이전트 읽기 전용 + PC 1 이 1·2·3 코드로 다시 확인)

**조치(2026-11-20, 사용자 "너가 말한 순서대로해줘"):**

| # | 상태 | 고친 내용 |
|---|---|---|
| 1 | 고침 | 두 `JpegResizer` 가 풀기 전에 머리말로 가로·세로를 읽어 4천만 화소를 넘으면 풀지 않는다. 목표의 네 배 이상이면 덜 풀어 읽는다(subsampling). 리뷰 사진 올리기는 4천만 화소를 넘으면 422 PHOTO_INVALID(계약 review 0.4.1). 미리 만들기는 `Throwable` 을 잡는다 |
| 5 | 일부 고침 | 요청 때 만들기가 5초 안에 차례를 못 받으면 원본을 준다(`tryAcquire`). 풀 수 없는 사진의 표시는 아직 |
| 2 | 고침 | 원래 검색어 + 커서로 오고 원래 결과가 0건이면 고친 검색어로 다음 쪽을 준다(계약 search 0.5.1) |
| 3 | 고침 | storefront V8 `sku_sales_line.returned_qty` 를 둔다. 사건에 `returnedQty` 가 없으면 마지막 반품 수를 쓴다 |
| 4·6~10 | 남음 | — |

시험: review 단위 11·통합 4, product-content 21·8, search 26·16, storefront 4·9. **LAN 배포 전.**

| # | 심각도 | 내용 | 실패 상황 | 고칠 방법 |
|---|---|---|---|---|
| 1 | **높음** | 리뷰 사진의 픽셀 수를 검사하지 않는다(`ReviewRules` 는 10MB·형식만). 미리 만들기는 `RuntimeException` 만 잡는다 | 단색 20000×20000 PNG 는 수 KB 라 올라간다. 5초 뒤 미리 만들기가 전부 풀다 `OutOfMemoryError` 가 난다. 이미지에 `-XX:+ExitOnOutOfMemoryError` 가 있어 **review-service 가 죽는다.** 그 사진은 `variants_at` 이 비어 있어 재시작 30초 뒤 다시 집어 → **재시작 반복**(고아 정리 24시간까지). product-content 도 같은 구조(운영자 업로드·20MB 라 중간) | 업로드 때 `ImageReader` 로 가로·세로를 읽어 상한(예 40MP) 넘으면 422. 줄이기 전에도 같은 검사(또는 subsampling). 미리 만들기는 `Throwable` 을 잡고 실패 횟수를 남겨 건너뛴다 |
| 2 | 중간 | 오타 교정으로 바꾼 결과의 다음 쪽 | 0건이라 고친 검색어로 45건을 주면 `nextCursor` 는 고친 검색어 기준이다. 앱이 원래 q + 커서로 부르면 커서가 있어 교정을 건너뛰고(`CorrectedSearch` `cursor != null`) 빈 쪽 | 다음 쪽은 `correctedQuery` 로 부르라고 계약에 적고 앱에 알린다. 또는 커서에 검색어를 넣는다 |
| 3 | 중간 | 인기순 판매 집계에서 반품이 되돌아감 | order 는 `returnedQty` 를 RETURN 사건에만 싣는다. 반품 뒤 재배송 등 다른 줄 사건이 오면 `asInt(0)` 으로 반품 0 → 순 판매가 다시 늘어난다(`RankingSignals`) | 필드가 없으면 저장된 반품 수를 유지(`sku_sales_line` 에 returned 칸), 또는 order 가 늘 싣게 |
| 4 | 중간·추정 | ES 가 동의어 규칙을 거절하면(4xx) 회신이 나가지 않음 | 예외 → 재시도 → DLT, 승인은 실행 축이 계속 비어 있음 | `putSynonymRules` 4xx 를 REJECTED(INVALID_TERMS)로 기록·회신, 요청 단계에서 `_analyze` 로 미리 확인 |
| 5 | 중간 | 요청 때 만들기의 `Semaphore.acquire()` 에 시간 상한이 없음 + 사진은 이제 처리율 제한 밖 | 축소본 없는 사진에 요청이 몰리면 요청 스레드가 줄을 선다. 풀 수 없는 JPEG/PNG 는 저장이 안 돼 요청마다 다시 읽고 다시 푼다 | `tryAcquire(시간)` 실패면 원본을 준다. 풀 수 없음을 표시해 다시 시도하지 않는다. 게이트웨이 제외를 GET 으로만 좁히기(지금은 그 경로에 GET 뿐이라 새는 것 없음) |
| 6 | 중간·추정 | EXIF 회전 정보를 버림 | 앱이 회전을 반영하지 않고 올린 세로 사진은 축소본만 옆으로 누워 보인다 | Orientation 을 읽어 돌린 뒤 줄이기, 또는 앱 업로드가 회전을 반영하는지 확인 |
| 7 | 낮음·추정 | 동의어 승인 사건이 순서 바뀌어 다시 올 때 | A 가 state 저장 뒤·기록 전에 멈추고 그 사이 B 가 반영되면, 다시 온 A 가 STALE_VERSION 거절 회신(실제로는 반영됨) | 기록을 state 보다 먼저(PENDING) 남기거나 state 에 최근 승인 목록 |
| 8 | 낮음 | 오타 사전이 상품 1만 개까지만 읽음 | 상품이 1만을 넘으면 뒤 상품 낱말이 빠짐 | `search_after`/PIT 로 끝까지 |
| 9 | 낮음·추정 | 304 응답 때 저장소 스트림이 닫히지 않음(`ContentImagesController`) | If-None-Match 로 304 면 연 S3 스트림이 새어 나갈 수 있음 | ETag 비교를 저장소 열기 전에 |
| 10 | 낮음 | `requester-roles` 설정이 없으면 막지 않음 | 지금은 설정이 있어 영향 없음 | SEARCH_SYNONYM 은 설정 없으면 CONFIG_REQUIRED |
