# MFC 시뮬레이터 ↔ 실서버·실제 앱 연결 — 목표와 결정 기록

> 시작 2026-11-09. **결정이 생기면 이 문서에 날짜와 함께 적는다**(결정 표의 상태·결정 칸 + 아래 "결정 이력"). 결정 전 항목의 "추천"은 제안일 뿐 결정이 아니다.
> 시뮬레이터 저장소: `../pmart-mfc-simulation`(백엔드 작업에서는 읽기만). 시뮬레이터 쪽 요청 목록은 그 저장소 `docs/backend-requests.md`(R-01~R-12).

## 1. 목표 (사용자 2026-11-09)

- 개발 환경에는 실제 MFC 현장이 없다 → **시뮬레이터가 현장을 대신해 눈으로 보여 준다.**
- 시뮬레이터는 평소 **가짜 데이터**(가상 주문·가상 작업자·가상 라이더)로 돈다.
- 여기에 **우리가 만든 실제 앱**(고객 앱 주문, PDA 앱 작업 등)에서 생기는 사건도 같은 화면에서 처리·표시되게 한다.
- 시뮬레이터 안의 **특정 작업자 한 명(또는 몇 명)은 실제 PDA 앱이 조종**한다 — 그 작업자는 시뮬레이터 스크립트가 움직이지 않는다.
- 백엔드 계약이 정본이다. **시뮬레이터와 안 맞는 부분은 시뮬레이터 쪽에서 맞춘다**(백엔드 계약을 시뮬레이터에 맞춰 바꾸지 않는다).

### SIM-1. 시간 (사용자 제기)

- **문제**: 시뮬레이터는 가짜 시계 + 배속(일시정지~120×). 백엔드는 모든 서비스가 실제 시계로 판단한다 — 예약 만료(Hold TTL), 인계 허가 만료(fence), 약속 준비 시각·늦음 표시, 근무·휴게, 배정 추천 구간, 슬롯(Asia/Seoul). 고객 앱도 실제 시간 슬롯을 보여 준다. 실서버에 붙은 상태에서 시뮬레이터만 빠르게 돌리면 화면 시간과 서버 시간이 어긋난다.
- **선택지**
  - (가) **실서버 연결 모드에서는 1× 실제 시간만**. 배속은 MOCK 모드 전용. 가장 단순하고 백엔드 변경 없음.
  - (나) 섞어 쓰기: 실제 앱 사건은 실제 시간, 가짜 주문은 실서버에 넣지 않고 MOCK 에서만 배속 — 화면에 두 시간축이 섞인다.
  - (다) 백엔드에 "센터별 가상 시계"를 넣어 시뮬 센터만 빠르게 — 모든 서비스의 시간 판단·TTL·Kafka 순서에 손이 가는 큰 변경. 운영 코드에 시험용 시계가 들어간다.
- **추천**: (가). 배속이 필요한 시연·부하 관찰은 MOCK 모드로. 고객 앱은 바꿀 것 없음(실제 시간).

### SIM-2. 실제 PDA 앱이 조종하는 작업자 (사용자 제기)

- **방향(사용자)**: 로그인 + 권한으로 구분.
- **정할 것**
  1. 시뮬레이터가 "이 작업자는 실제 사람"을 아는 방법 — (가) 시뮬레이터 설정에 작업자 ID 목록 / (나) 백엔드 작업자 정보에 표시(새 필드, 계약 변경) / (다) 시뮬레이터가 스크립트로 움직이는 가상 작업자 계정만 따로 갖고, 그 밖의 작업자는 전부 실제로 본다. **추천: (다)** — 백엔드 변경 없음.
  2. 3D 화면에서 실제 작업자의 **위치**: 실제 위치 추적은 없다. 마지막 스캔·작업 칸(작업 상세의 칸, 다음 작업 받기 `detail.fromLocation`)으로 그 칸 앞에 놓는 정도. 이동 경로는 그리지 않는다(추천).
  3. 실제 작업자도 **다음 작업 받기**로 받으므로, 가상 작업자와 같은 작업 풀을 나눠 가진다 — 실제 사람이 받을 작업을 남겨 둘지(예: 특정 유형·특정 주문만 실제 사람에게) 정해야 한다. 추천: 따로 두지 않음(현장과 같게).
  4. 실제 PDA 앱(`pmart-clients/apps/mfc_app`)은 지금 작업 목록·포장 화면만 있다 — 다음 작업 받기·피킹 화면 연결은 클라이언트 쪽 일(공지는 `docs/handoff/` 에 있음).

### SIM-3. 가상 작업자·라이더 인증 (시뮬레이터 R-02)

- **문제**: 시뮬레이터 한 대가 작업자 N명을 연기한다. 백엔드는 작업자 본인 토큰만 받는다(다음 작업 받기는 본인만).
- **선택지**
  - (가) 시뮬 센터 전용 **실제 운영자 계정 N개**(가상 작업자마다 하나, 시뮬 센터 권한·MFC_WORKER만) — 로그인 API 로 토큰을 받는다. 백엔드 변경 없음. 비밀번호 보관은 시뮬레이터 실행 PC 의 비밀 파일(Git 금지).
  - (나) `mfc-simulator` 서비스 신원 + "대행 작업자" 헤더 — 인증 체계 변경, 운영에서 막는 장치 필요.
  - 금지: LAN 서명 키로 토큰을 직접 만드는 것(고객 토큰 금지 원칙과 같은 이유).
- **추천**: (가). 라이더는 SIM-7 과 함께.

### SIM-4. 가짜 주문을 실서버에 넣는 길

- **문제**: 진짜 주문 경로는 고객 로그인(Google) + Toss 결제 → 주문 → 사가 → MFC. 가짜 주문을 많이 넣기엔 맞지 않는다.
- **선택지**
  - (가) LAN E2E 처럼 주문 조정 서비스가 부르는 MFC 내부 API 를 시뮬레이터 서비스 신원으로 직접 부름 — 주문·결제 서비스는 거치지 않음(고객 앱·주문 조회에는 안 보임). 시뮬레이터 원칙 "`/internal/*` 은 부르지 않는다"와 충돌.
  - (나) 고객 시험 계정 + Toss 시험 결제로 진짜 경로 — 느리고 결제 시험 키 의존.
  - (다) 실서버 연결 모드에서는 **가짜 주문을 넣지 않음** — 실서버 모드의 주문은 고객 앱에서 온 실제 주문만, 가짜 주문은 MOCK 모드에서만.
- **추천**: 처음에는 (다), 부하 표현이 필요해지면 (가)를 시뮬 센터 한정으로 검토.

### SIM-5. 실서버 변화를 받는 방법 (시뮬레이터 R-04)

- **문제**: 실제 앱이 만든 변화(새 PICK 작업, 실제 작업자의 시작·피킹·밀봉, 취소)를 시뮬레이터가 알아야 그린다. 브라우저는 Kafka 를 직접 못 본다.
- **선택지**: (가) 주기 조회 — 센터 전체 `GET /tasks?mfcId&state=`·`GET /assignments`·센터 재고 조회를 몇 초마다 / (나) 게이트웨이에 SSE 등 알림 경로 신설(새 기능, 백엔드 변경).
- **추천**: (가)로 시작(지금 있는 API). 조회 간격·부하는 SIM-10 과 함께.

### SIM-6. 시뮬레이터 전용 센터·위치·재고

- **문제**: 시뮬레이터 평면·칸 코드(`C01-03-205`)는 가정이고, LAN 시험 센터 `MFC-SEED-01` 의 칸 코드(`A-S9-01-1-01`)·재고와 다르다. 실제 앱 주문도 어느 센터로 가는지에 따라 시뮬레이터에 보이거나 안 보인다.
- **정할 것**: (가) 시뮬레이터가 `MFC-SEED-01` 의 위치·재고를 읽어 그 코드로 평면을 그림(시뮬레이터가 맞춤) / (나) 시뮬 전용 센터를 새로 만들고 시뮬레이터 평면대로 위치를 API 로 등록. 고객 앱 시험 주소가 그 센터로 배정되는지도 함께(배송 가능 지역 설정).
- **추천**: (가) — 사용자 원칙(시뮬레이터가 맞춘다)과 같고, 실제 앱 주문이 이미 그 센터로 간다.

### SIM-7. 라이더

- **문제**: 배송 배정·라이더 서비스가 뼈대라, 인계에 필요한 배송 배정 사건(`DeliveryCreated`·배정)과 라이더 토큰이 없다. 지금 E2E 도 라이더 인계는 빠져 있다.
- **선택지**: (가) 배송 서비스(DD-1·DE-1) 구현을 기다림 — 그때 가상 라이더 = 라이더 시험 계정 / (나) 그 전까지 시뮬레이터는 "출하 대기"에서 멈추고 인계는 MOCK 으로만 그림.
- **추천**: (나) 지금, (가) 배송 구현 뒤.

### SIM-8. 가짜 실적 구분 (시뮬레이터 R-03)

- **문제**: 시뮬레이터가 실서버에 남긴 피킹·포장·재고 변동이 실제 실적과 섞이면 지표·예측 학습(나중)에 쓰면 안 된다.
- **추천**: 시뮬 센터·시뮬 계정으로 구분(SIM-3 (가), SIM-6)하면 별도 필드 없이도 걸러진다. 원장 출처 필드는 운영 전 필요해지면 계약 추가로.

### SIM-9. 초기화·정리

- **문제**: 반복 실행하면 시뮬 센터에 작업·재고 변동이 쌓인다. DB 직접 수정은 금지(데이터는 API 로).
- **정할 것**: 실행 끝에 열린 작업 취소·재고 원복을 API 로 하는 정리 절차(E2E 스크립트가 하는 방식) / 주기적으로 시험 센터를 새로 만드는 방식.

### SIM-10. 부하·운영 소음

- 조회 간격·가상 작업자 수가 LAN PC 메모리(pc4 여유 약 5GB, 2026-11-09)·로그 저장량(es-logs 2GB 상한)에 영향. 알림 규칙은 Slack 으로 가므로 시뮬레이터 때문에 규칙을 추가하지 않는다.
- **정할 것**: 실서버 모드의 최대 가상 작업자 수·조회 간격.

### SIM-11. 실행 위치·CORS·토큰 보관

- 시뮬레이터는 브라우저 앱(Vite 개발 서버 프록시 → 게이트웨이). 게이트웨이 CORS 허용 목록(ADR-0018)에 시뮬레이터 주소를 넣을지, 프록시로만 붙을지. 가상 작업자 비밀번호·토큰을 브라우저에 둘지 Vite 서버 쪽에 둘지.
- **추천**: 프록시로만 붙고(CORS 변경 없음), 비밀번호는 Vite 서버 쪽 비밀 파일(브라우저에 보내지 않음).

## 4. 실제 앱 사건 중 시뮬레이터가 처리해야 할 것 (처음 목록)

| 실제 앱 동작 | 백엔드에 생기는 것 | 시뮬레이터 표시 |
|---|---|---|
| 고객 앱 주문·결제 | 예약 → PICK(READY)·PACK(WAITING) | 새 작업 등장 |
| 고객 취소(준비 전) | 작업 중지·취소 | 작업 사라짐 |
| PDA 다음 작업 받기 | 배정(source SYSTEM) | 그 작업자에게 작업 표시 |
| PDA 시작·피킹·결품 보고 | 작업 진행·재고 변동·결품 | 선반 수량 변화, 결품 표시 |
| PDA 포장·밀봉·배차 요청 | 포장 READY·`DispatchRequested` | 출하대기 랙 |
| 센터 관리자 이동 지시·배정 | 이동 지시·배정 | 이동 작업 |
| (배송 구현 뒤) 라이더 QR·인계 | `PackageHandedOver` | 라이더가 가져감 |
