# Keycloak 인증 추천 글 확인 (2026-11-10)

원문: 사용자가 준 "PMart 최종 인증 아키텍처 추천"(2026-11-10). 원문 파일은 사용자 요청으로 같은 날 저장소에서 삭제했다. 상태: **이 글(첫 번째 글)은 채택하지 않음 — 사용자가 원문 삭제, 결정은 두 번째 글 기준 ADR-0054(라이더는 Keycloak 아님).** 이전 표기: 결정됨 2026-11-10 — 사용자 "키클록 구성을 따를거야" → [ADR-0054](../../adr/0054-auth-split-keycloak-staff-rider-auth-service.md)**. 아래 §3·§5 의 남은 점은 ADR-0054 '정할 것'으로 옮겼다.

## 1. 지금 PMart 인증(원문이 전제한 것과 다른 점)
| 항목 | 지금 | 원문 |
|---|---|---|
| 직원(운영자) 로그인 | **auth-service** 아이디·비밀번호, 이미 LAN 운영 중(ADR-0018), 접근 토큰 15분·갱신 12시간 | Keycloak `pmart-staff` Realm 으로 옮김 |
| 고객 로그인 | auth-service Google 로그인(ADR-0019·0025), 고객 토큰 1시간·갱신 30일 | 그대로(같음) |
| 라이더 로그인 | 없음. 시험은 LAN 서명키로 만든 `typ=RIDER` 토큰 | Keycloak `pmart-rider` Realm + Google |
| 토큰 발급자 | **하나**(auth-service RS256, `iss=http://auth-service:8501`). 게이트웨이·서비스는 JWKS 하나(`/api/v1/internal/jwks`)로 검증 | 발급자 3개(staff Realm·rider Realm·auth-service) — 게이트웨이·서비스 모두 여러 발급자 검증으로 바꿔야 함 |

| Keycloak | ADR-0011·0018 대안에서 **"새 플랫폼이라 도입 안 함"**으로 기록 | 도입 |

## 2. 원문에서 맞는 점
- 같은 사람인지는 이메일이 아니라 **Google `sub`** 로 판단 — 이미 `social_identity` 가 그렇게 하고 있고, Commerce 4.9 "이메일만 같다고 계정을 합치지 않는다"와도 맞다.
- 고객 가입이 라이더 자격을 주지 않고, 라이더 정지가 고객 계정을 막지 않게 **권한·상태를 따로** 두는 것.
- 라이더 승인·정지·배차 가능 상태는 rider-service 가 정본(service-map 과 같음).
- 토큰을 바로 막아야 하면 짧은 수명 + 서버 쪽 상태 확인이 필요하다는 것.

## 3. 맞지 않거나 확인이 필요한 점
1. **업무 원문과 다르다**: `Delivery-business-logic.md` §1.1 라이더 가입은 "전화번호 인증·본인인증·아이디·비밀번호 입력", §1.2 "고유성으로 중복가입 불가, 가입완료 → 즉시 운행승인". 원문(추천 글)은 **Google 로그인 + 라이더 승인 심사**다. "같은 Google 계정으로 고객 앱과 라이더 앱 로그인"도 업무 원문에 없는 요구다 → 어느 쪽인지 사용자 결정 필요.
2. **직원 로그인을 Keycloak 으로 옮길 이유가 원문에 없다**: 결론("같은 Google 계정은 서버 분리 이유가 아니다")은 라이더 얘기인데, 이미 운영 중인 운영자 로그인·계정 관리·역할·센터 권한(ADR-0018, `claude-*` 시험 계정, BO-01 grant 계획)까지 옮기는 비용(데이터 이전, 게이트웨이·50개 서비스 검증 설정, 백오피스 화면 로그인 변경)을 따지지 않았다.
3. **연결 계층의 주인이 없다**: service-map 에 없는 새 책임이다. 지금 구조라면 Google `sub` 를 이미 가진 auth-service 가 자연스럽다. 별도 서비스로 두면 서비스 경계 추가(요청 없이 금지)다.
4. **Keycloak 이 준 라이더 토큰의 `sub` 는 Google `sub` 가 아니다**(원문도 인정). 연결하려면 Keycloak 관리 API 로 연동 신원을 조회하는 서버 경로가 필요 — 운영 구성요소(Keycloak 컨테이너·DB·관리자 비밀·버전 관리·모니터링)가 늘어난다.
5. **토큰 클레임이 달라진다**: 서비스들은 지금 `typ`·`roles`·`centers` 클레임으로 권한을 판단한다. Keycloak 토큰은 기본 형태가 달라(`realm_access.roles` 등) 매퍼 설정이나 공통 라이브러리 변경이 필요 — `libraries/` 변경이면 영향 서비스 전부.

## 4. 더 작은 대안(비교용, 결정 아님)
- **auth-service 하나로 라이더 로그인 추가**: 고객과 같은 Google 로그인 코드에 `typ=RIDER` 토큰을 발급하는 경로를 더한다. 같은 `social_identity`(Google sub)로 "같은 사람"을 알 수 있고, 고객 계정과 라이더 계정·상태는 따로 둔다(라이더 업무 상태는 rider-service). 발급자·JWKS·게이트웨이 설정은 그대로. 새 플랫폼 없음.
- 업무 원문대로라면 Google 대신 **아이디·비밀번호 + 전화번호 중복 확인**(본인인증 API 없음 — clients BR-02) 로그인을 auth-service 에 추가.
- Keycloak 은 위 둘로 안 되는 요구(직원 SSO·MFA·외부 IdP 여러 개 등)가 생길 때 다시 본다.

## 5. 결정할 것
1. 라이더 가입·로그인 방식: 업무 원문(전화번호·아이디·비밀번호) / Google / 둘 다.
2. 고객·라이더 같은 사람 연결이 실제로 필요한지(필요하면 무엇에 쓰는지).
3. Keycloak 도입 여부와 범위(라이더만 / 직원까지) — 도입하면 새 ADR.
