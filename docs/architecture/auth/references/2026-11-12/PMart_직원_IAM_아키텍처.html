방식별 장단점

R-1 · BFF 세션

토큰은 employee-auth에만
장점
  • 브라우저·PDA에 Keycloak 토큰이 없다. XSS나 기기 분실로 토큰이 새지 않는다
  • Client Secret과 refresh token이 서버 한곳에만 있어 관리가 쉽다
  • "employee-auth가 로그인 Client"라는 합의와 가장 잘 맞는다
  • 퇴사 시 employee-auth 세션을 지우면 그 즉시 막힌다. 차단 목록 없이도 1분 목표에 다가간다
  • Gateway가 Keycloak 토큰을 붙여 보내면 업무 API는 기존안 검증(iss·aud·ptyp·acr)을 그대로 쓴다
단점
  • employee-auth가 상태를 가진다. 여러 대로 띄우면 세션 저장소(Redis 등) 공유가 필요하다
  • 모든 업무 요청마다 세션 → 토큰 변환이 필요해 Gateway와 employee-auth가 핵심 경로에 놓인다
  • employee-auth가 멈추면 로그인뿐 아니라 업무 요청도 멈춘다
  • 쿠키를 쓰므로 CSRF 대비가 필요하다
  • PDA는 브라우저 쿠키를 그대로 못 쓰므로 앱용 세션 값을 따로 설계해야 한다 (U-04)

잘 맞는 경우 보안을 우선하고, 세션 저장소를 운영할 수 있을 때

R-2 · 토큰 전달

토큰은 앱에
장점
  • employee-auth에 상태가 없어 단순하고 수평 확장이 쉽다
  • Gateway·업무 API가 기존안 §8.1 방식으로 Keycloak 토큰을 바로 검증한다
  • 업무 요청 경로에 employee-auth가 끼지 않는다
단점
  • 토큰이 브라우저 메모리·PDA 저장소에 놓인다. 서버측 Client로 만든 이점이 대부분 사라진다
  • 토큰을 받은 쪽(employee-auth)과 쓰는 쪽(앱)이 달라 OAuth 표준 흐름에서 벗어난다
  • refresh를 앱이 하면 Client 자격이 필요하고, employee-auth가 하면 결국 상태가 생긴다
  • 퇴사 즉시 차단에는 차단 목록이 따로 필요하다
  • 공용 PDA에 이전 직원 토큰이 남을 위험이 커진다 (N-05)

잘 맞는 경우 빨리 붙여야 하고, 토큰 노출 위험을 받아들일 수 있을 때

R-3 · 자체 토큰

앱엔 PMart JWT
장점
  • 앱·Gateway가 보는 토큰 형식을 PMart가 정한다. Keycloak을 바꿔도 앱 계약은 유지된다
  • 업무 요청마다 employee-auth를 부르지 않는다 (공개키 캐시로 검증)
  • Keycloak 토큰은 서버에만 둔다
단점
  • 발급자가 3개(Keycloak · auth-service · employee-auth)가 되어 Gateway 규칙이 복잡해진다 (N-02)
  • acr·centerRoles·emp 같은 Keycloak 정보를 새 토큰에 옮겨 담아야 한다. 누락되면 OTP 우회 위험 (N-01)
  • 서명키 관리·교체·JWKS 공개를 employee-auth가 새로 맡는다
  • 퇴사 때 끊을 곳이 Keycloak · employee-auth · 차단 목록 셋으로 늘어난다
  • 기존안 §8.1 검증 설정을 다시 써야 한다

잘 맞는 경우 IdP를 갈아낄 가능성이 크거나 토큰 형식을 PMart가 꼭 통제해야 할 때

추천안 · R-1 기반, 웹과 PDA만 앱 보관값을 다르게

제안 결정 아님. 아래 확인 조건을 통과하면 ADR-B·ADR-E 후보로 올린다.

  1. Keycloak 토큰은 employee-auth만 보관한다. access · refresh 모두 서버 세션 저장소에 둔다.
  2. 앱이 받는 값만 다르게 한다. 웹(React)은 HttpOnly · Secure · SameSite 세션 쿠키, PDA는 쿠키 대신 보안 저장소에 두는 불투명 세션 토큰(의미 없는 랜덤 값)을 Authorization 헤더로 보낸다.
  3. Gateway가 세션 값을 Keycloak access token으로 바꿔 업무 API에 붙인다 (token relay). 업무 API는 기존안 §8.1의 iss · aud · ptyp · acr 검증을 그대로 쓴다.
  4. 퇴사 · 로그아웃은 employee-auth 세션 삭제 + Keycloak 비활성화로 처리한다. 다음 요청부터 바로 막힌다.
현재 구조에 맞는 이유
  • 합의된 "employee-auth = 서버측 로그인 Client"를 끝까지 살린다. code를 받은 서버가 토큰도 지킨다
  • 앱을 Keycloak Client로 등록하지 않는다는 합의(C-01·C-02)와 충돌이 없다
  • 업무 API는 Keycloak 토큰을 그대로 받으므로 기존안의 검증·acr·centerRoles 설계를 버리지 않는다. R-3의 발급자 3개 문제가 없다
  • 공용 PDA에는 의미 없는 세션 값만 남는다. 교대 시 서버에서 지우면 끝이다 (N-05 완화)
  • 퇴사 즉시 차단을 차단 목록 없이도 세션 삭제로 달성할 수 있다 (U-14·N-04 단순화)
채택 전 확인할 것
  • U-12 Gateway가 요청마다 세션 → 토큰을 바꿀 수 있는가. employee-auth 호출 또는 공유 세션 저장소(Redis) 직접 조회 중 무엇으로 할지 [확인]
  • 성능·가용성 세션 조회 지연과 employee-auth·세션 저장소 장애 시 영향 (N-07)
  • U-04 PDA가 시스템 브라우저 로그인 뒤 세션 토큰을 안전하게 받는 방법 (08 §1 P-1)
  • N-01 백오피스 세션에 acr=2가 기록되는지, PDA 세션으로 백오피스 경로를 못 부르는지
  • refresh access token 만료 시 employee-auth가 갱신하는 시점과 동시 요청 처리
  • CSRF 웹 쿠키 요청의 CSRF 방어 방식

R-2와 R-3을 추천하지 않는 이유: R-2는 토큰을 다시 기기에 내려보내 서버측 Client로 바꾼 의미가 줄고, R-3은 발급자와 클레임 재전달 문제를 새로 만든다. 기존안의 "SPA·PDA가 직접 토큰 보관" 방식은 앱이 Keycloak Client가 아니게 되면서 쓸 수 없다 (C-01 · C-02).

4. 한눈에 보는 핵심 (5문장)

  1. 합의 직원 로그인은 employee-auth(Spring Boot)가 Keycloak pmart-staff의 서버측 OIDC Client로 중개하며, React 백오피스와 Flutter PDA는 Keycloak에 각자 Client로 직접 등록하지 않는다.

  3. 합의 HR의 Admin API 자격은 서비스 계정 Client hr-provisioner + realm-management 역할(manage-users·view-users·query-users) + Client Credentials 세 가지로 구성한다. employee-auth의 로그인 Client 자격과 분리하며 최고 관리자 개인 계정은 쓰지 않는다. 역할 매핑 허용 여부만 U-11로 남는다 (02 §3.1).

  5. 미확정 PDA 인증 화면·앱 복귀·결과 바인딩, React의 SPA/BFF 형태, 토큰 보관·세션 형태, 소셜 IdP, 퇴사 반영 시한은 정하지 않았으며, 특히 구성안의 LoA(acr)·azp 기반 OTP 강제 설계가 단일 employee-auth Client 구조에서 그대로 성립하는지가 새로 드러난 핵심 검증 과제다(N-01, 07 문서).

운영 규칙:

  • 합의 master realm 최고 관리자 계정을 쓰지 않는다. pmart-staff realm의 서비스 계정으로 그 realm만 관리한다 (C-14).
  • 합의 hr-provisioner는 employee-auth 로그인 Client와 별개다. 같은 Token Endpoint를 쓰지만 grant 종류와 목적이 다르다.
  • 기존안 Secret은 암호화 설정 저장소({cipher})에 두고 교체 절차를 정한다. Admin 이벤트 저장을 켠다 (§6.6).
  • 합의 HR Service는 Keycloak 내부 주소로 직접 호출하고, /admin 경로는 API Gateway로 노출하지 않는다 (06 S-3).
  • 제안 관리용 토큰은 수명이 짧으므로 만료 전까지 캐시해 재사용하고, 401 수신 시 1회 재발급 후 재시도한다.
  • 미확정 U-11 (이번 범위 제외) manage-users가 역할 매핑·그룹 가입까지 허용하는지는 고정 버전에서 확인한다. 결과에 따라 08 §3 A-2·A-3을 추가할지 정한다.
  • Endpoint 경로와 역할 이름은 일반적인 Keycloak 기준이며, 고정할 26.x 버전 공식 문서로 재확인한다 확인.

4. 위협·예외·반례

T-01 중복 계정 발급

  • 전제: 인사 담당자가 같은 직원을 두 번 제출하거나 HR이 재시도한다.
  • 실패 조건: "검색 후 생성"이 없거나 중복 판정 키(U-09)가 일관되지 않다.
  • 영향: 한 사람에게 두 sub, 권한·감사 기록 분산, 퇴사 시 한쪽만 비활성화.
  • 불변식: 사번당 활성 Keycloak 사용자 1개(04 §2.2).
  • 검증 질문: 중복 판정 키는 username인가 사번 속성인가? 사번 속성 검색이 정확 일치로 동작하는가 확인?

T-02 동일 사번 충돌 (재입사·오입력)

  • 전제: 퇴사 후 재입사, 또는 다른 사람에게 잘못된 사번 입력.
  • 실패 조건: 비활성 계정을 무조건 재활성화하거나 덮어쓴다.
  • 영향: 과거 행위자 기록 오염, 이전 권한 부활.
  • 불변식: 재활성화는 명시적 절차이며 이전 권한은 자동 복원되지 않는다 제안.
  • 검증 질문: 재입사 시 같은 sub를 재사용하는가? 권한 정본(U-13)은 이를 어떻게 처리하는가?

T-03 Keycloak 생성 성공 후 HR 응답 유실

  • 전제: Admin API 201 응답 전 네트워크 단절.
  • 실패 조건: HR이 실패로 판단하고 사용자에게 "실패"를 반환, 재요청 시 409 또는 중복.
  • 영향: 인사 원장과 Keycloak 불일치, 매핑 없는 고아 계정.
  • 불변식: 확인 전 완료·실패 단정 금지, 반영미확인 상태 유지 제안.
  • 검증 질문: 대사 주기와 고아 계정 처리 책임자는?

T-04 HR 관리 자격의 과도한 권한

  • 전제: HR Service가 realm-admin 또는 최고 관리자 자격을 쓴다.
  • 실패 조건: HR Service 침해 또는 SSRF.
  • 영향: 역할 자가 부여, Client Secret 열람·변경, realm 전체 장악.
  • 불변식: S-1·S-3, 관리 자격은 realm-management 역할 3종으로 제한 합의 (02 §3.1), 역할 매핑 허용 여부는 U-11.
  • 검증 질문: manage-users가 역할 매핑을 허용하는지, 고정 버전의 Fine-Grained Admin Permissions로 그룹/속성 범위를 좁힐 수 있는지 보충확인.

T-05 일반 직원에게 Admin API 경로 노출

  • 전제: Gateway에 Keycloak 관리 경로 라우트가 존재하거나 HR 발급 API의 인가가 약하다.
  • 실패 조건: 인사 역할 없는 직원이 HR 발급 API를 호출.
  • 영향: 임의 계정 생성(내부자 백도어).
  • 불변식: HR 발급 API는 인사 역할과 (결정 시) 승인 상태를 서버측에서 확인 제안·U-08.
  • 검증 질문: 인사 담당자 역할은 어디에 정의되며 누가 부여하는가(U-13)?

T-06 React/PDA 인증 결과 혼동 (로그인 CSRF·결과 탈취)

  • 전제: employee-auth가 콜백 후 결과를 앱에 넘기는 방식이 미정(U-04).
  • 실패 조건: state 미검증, 결과 핸들이 재사용 가능, 커스텀 스킴 탈취(다른 앱이 같은 스킴 등록) 보충 RFC 8252.
  • 영향: 다른 기기·다른 사용자 세션으로 로그인, 공격자 계정으로 피해자 로그인.
  • 불변식: 로그인 결과는 시작한 앱 인스턴스에만 1회 전달된다.
  • 검증 질문: App Link(검증된 HTTPS) 사용 가능 여부, 결과 핸들의 수명·1회성, 앱이 보관하는 검증값 존재 여부.

T-07 공용 PDA에서 이전 직원 세션 잔존

  • 전제: 교대 시 같은 PDA를 넘김.
  • 실패 조건: 앱 세션 또는 시스템 브라우저의 Keycloak SSO 쿠키가 남는다.
  • 영향: 다음 작업자의 작업이 앞 사람 이름으로 기록.
  • 불변식: 새 근무 시작은 항상 재인증 기존안 D4.
  • 검증 질문: 단일 employee-auth Client에서 PDA 요청에만 prompt=login을 강제하는 방법은? 기존안 §15.2의 쿠키 잔존 시험을 새 구조에서 다시 수행해야 하는가?

T-08 OTP 우회 (LoA 혼동)

  • 전제: 백오피스와 PDA가 같은 Client(employee-auth)를 쓴다.
  • 실패 조건: 비밀번호만으로 만든 SSO 세션이나 acr=1 토큰이 백오피스 경로에서 수용된다.
  • 영향: OTP 없는 백오피스 접근(기존안 §6.3이 막으려던 구멍).
  • 불변식: 백오피스 경로는 수준 2 인증 결과만 수용 기존안.
  • 검증 질문: 요구 수준을 employee-auth가 요청마다 지정할 때 Keycloak이 이를 강제하는지, Gateway가 앱 세션에 acr을 어떻게 반영받는지(N-01).

T-09 잘못된 Issuer/Audience/사용자 유형 수용

  • 전제: 다중 발급자 검증.
  • 실패 조건: iss만 보고 aud·ptyp을 보지 않음, 또는 사내 도구용 토큰 수용.
  • 영향: 고객 토큰으로 직원 API 호출, 다른 Client 토큰 재사용.
  • 불변식: 발급자별 aud·ptyp 허용 목록 기존안 §8.1.
  • 검증 질문: employee-auth 발급 토큰(만약 존재)의 iss·aud·ptyp은?

T-10 Gateway 우회

  • 전제: 업무 서비스가 내부망에서 직접 접근 가능.
  • 실패 조건: 서비스가 Gateway가 넣은 헤더만 신뢰하고 토큰을 재검증하지 않는다.
  • 영향: 위조 헤더로 권한 획득.
  • 불변식: 서비스도 토큰을 재검증 기존안 §4. ADR-0026(서비스간 인증 없음)과의 관계 확인 필요 미열람.
  • 검증 질문: employee-auth가 서버 세션 모델을 택하면 업무 서비스는 무엇을 재검증하는가(U-12)?

T-11 퇴사·비활성화와 기존 토큰 유효기간 차이

  • 전제: access 15분, refresh 회전, (가능하면) employee-auth 세션.
  • 실패 조건: 차단 목록 없음, employee-auth 세션 무효화 없음.
  • 영향: 퇴사 후 최대 access 수명 또는 앱 세션 수명 동안 접근.
  • 불변식: 퇴사 반영 시한 내 모든 계층(Keycloak, employee-auth, Gateway) 거절 — 시한은 U-14.
  • 검증 질문: 1분 목표(기존안)를 유지하는가? 차단 목록 등록 주체는(N-04)?

T-12 Keycloak 장애

  • 전제: Keycloak 단일 노드(LAN) 또는 클러스터 일부 장애.
  • 실패 조건: 신규 로그인·refresh·계정 발급 불가.
  • 영향: 교대 시작 시 현장 로그인 불가, 신규 입사 처리 지연.
  • 불변식: 계정 발급 요청은 유실되지 않는다 제안. 기존 세션 유지 범위는 미정.
  • 검증 질문: JWKS 캐시로 기존 access token 검증이 계속되는가? employee-auth 세션이 있으면 Keycloak 장애 중 얼마나 유지할 것인가(N-07)?

T-13 메일 없는 직원

  • 전제: 현장 작업자는 메일 없음 기존안 D5.
  • 실패 조건: 비밀번호 재설정이 메일 기반만 존재, 또는 Draft의 xxx@pmart.com이 필수값.
  • 영향: 계정 생성 실패, 임시 비밀번호의 비보안 전달.
  • 불변식: 메일 유무와 무관하게 계정 발급·초기화 경로가 존재 제안.
  • 검증 질문: U-09·U-10, 초기화 실행 주체(N-08).

T-14 소셜 IdP 미사용 또는 사용 시 계정 연결

  • 전제: U-05로 외부 IdP 도입 가능성.
  • 실패 조건: 외부 IdP 이메일 일치만으로 기존 직원 계정 자동 연결(First Broker Login 자동 링크) 보충.
  • 영향: 외부 계정 탈취 = 직원 계정 탈취, 고객 Google 계정이 직원으로 연결.
  • 불변식: 직원 계정은 인사 발급으로만 생성되며 외부 IdP는 기존 계정에 명시적 절차로만 연결 제안. 고객 Google과 섞지 않는다(I-3).
  • 검증 질문: 도입 시 자가 가입 차단, 이메일 검증 신뢰 여부, OTP 요구 수준 유지 방법.

T-15 employee-auth 침해

  • 전제: employee-auth가 Client Secret과 (U-02에 따라) 직원 Refresh Token을 보관.
  • 실패 조건: 서버 침해.
  • 영향: 모든 직원 세션 탈취 가능(중앙 집중 위험).
  • 불변식: 보관 최소화·암호화 저장·관리 자격 미보유(S-1) 제안.
  • 검증 질문: U-02 결정 시 저장소·암호화·수명은?

1. PDA 인증 결과 전달 (U-01, U-03, U-04, U-07)

옵션 개요 장점 단점·위험 합의 정합
P-1 서버측 Client + 앱 복귀 핸들 PDA가 시스템 브라우저로 Keycloak 로그인 → 콜백은 employee-auth → employee-auth가 1회성 결과 핸들을 App Link로 앱에 전달 → 앱이 핸들 + 앱이 시작 시 만든 검증값으로 교환 Keycloak 토큰이 기기로 가지 않을 수 있음, Client Secret 서버 보관 설계 자체가 비표준 확장: 핸들 1회성·수명·검증값 바인딩을 직접 설계해야 함. App Link 검증 도메인 필요 정합
P-2 서버측 Client + 토큰 전달 P-1과 같으나 employee-auth가 Keycloak 토큰(또는 일부)을 앱에 넘김 업무 API가 Keycloak 토큰을 그대로 검증(기존안 §8.1 재사용) Client가 employee-auth인데 토큰 사용자는 앱 → 토큰 수령 주체와 사용 주체 불일치. refresh 처리 주체 모호 정합(세부 미정)
P-3 employee-auth가 ID/비밀번호 수신 (ROPC) PDA 화면에서 입력, employee-auth가 Direct Access Grant로 Keycloak 인증 화면 전환 없음, 바코드 입력 UX 단순 OAuth 보안 BCP가 금지 권고 보충, OTP·외부 IdP·Keycloak 잠금/필수 작업 처리 제약, Credential이 Keycloak 밖을 지남(S-4 위반) 형식상 정합, Draft §6 해석과 충돌
P-4 PDA 공개 Client + PKCE (기존안) 앱이 직접 Authorization Code + PKCE 표준(RFC 8252), 기존안 시험 계획 재사용 최신 합의 위반 합의 변경 필요
P-5 Device Authorization Grant PDA가 코드 표시, 다른 기기에서 인증 입력 어려운 기기에 적합 현장 교대 UX 부적합, 다른 기기 필요 형식상 정합, 실효성 낮음
  • 공통 검증 조건: 공용 기기에서 매번 재인증(N-05), 결과 1회성, 기종별 시스템 브라우저 동작 확인.
  • 제안 비교 우선순위는 P-1 → P-2 순으로 검토하고, P-3은 S-4 불변식을 바꾸는 결정이 있을 때만 다룬다. 최종 선택은 미확정.

2. React 인증 형태 (U-03, U-06, U-12)

옵션 개요 장점 단점·위험 합의 정합
R-1 employee-auth = BFF 세션 employee-auth가 Keycloak 토큰 보관, 브라우저엔 HttpOnly·Secure·SameSite 세션 쿠키 (SS 그림과 같은 모양) 브라우저 토큰 노출 없음, Client Secret 서버 보관 employee-auth가 상태 보유(세션 공유·확장), Gateway가 쿠키 세션을 검증하는 방법 필요(U-12), CSRF 대응 필요 정합
R-2 employee-auth가 토큰을 SPA에 전달 로그인 후 access token을 SPA 메모리로 Gateway가 Keycloak 토큰 직접 검증(기존안 재사용) XSS 시 토큰 노출, 수령 주체 불일치(P-2와 동일) 정합(세부 미정)

3. HR 관리 자격 최소 권한 (U-11)

옵션 개요 장점 단점·위험
A-1 서비스 계정 + realm-management 일부 역할 (manage-users, view-users, query-users) 기존안 hr-provisioner 권장 · 채택 합의 2026-11-12 단순, 기존안과 일치 manage-users의 실제 허용 범위(역할 매핑·그룹 가입·사용자 사칭 등)가 버전별로 다를 수 있음 확인
A-2 A-1 + Fine-Grained Admin Permissions로 범위 축소 특정 그룹·동작으로 제한 최소 권한 근접 고정 버전에서의 기능 상태·설정 복잡도 보충확인
A-3 Keycloak 앞에 HR 내부 허용 목록 HR 코드가 호출 가능한 Admin API 종류를 제한 Keycloak 권한과 이중 방어 HR 침해 시 무력화, Keycloak 측 권한이 실질 경계
A-4 최고 관리자 자격 — — 배제 [Draft 제안]

합의 2026-11-12 A-1을 기본 구성으로 채택한다 (02 §3.1). A-2·A-3을 더할지는 U-11 확인 결과로 정하며, 이번 범위에서 다루지 않는다.

  • 공통: Client Secret은 암호화 설정 저장소(기존안 {cipher}), Secret 교체 절차, Admin 이벤트 감사 활성화 기존안 §6.6.
  • 검증 질문: "HR은 업무 권한을 주지 않는다"를 권한으로 막을지, 코드 규칙으로만 막을지.
