① 이메일은 어떻게 전달될까: 우편에 비유하기

메일 시스템은 우편 제도와 구조가 같습니다. 편지를 쓰는 사람(MUA), 편지를 분류해 옮기는 우체국(MTA), 편지를 보관하는 우편함(사서함)이 각각 다른 프로그램입니다. Docker Mailserver는 우체국과 우편함을 한 건물에 넣어 둔 것이고, Roundcube는 사람이 쓰는 편지지와 우편함 열쇠에 해당합니다.

보내기

SMTP

메일을 서버로 밀어 넣는 규약입니다. 앱이나 Roundcube가 메일을 제출할 때(587), 서버끼리 메일을 넘길 때(25) 씁니다. SMTP로는 메일을 읽을 수 없습니다.

② IAM과 Keycloak

IAM은 "누가 누구인지 확인하고, 그 사람이 무엇을 할 수 있는지 정하는" 체계입니다. 둘은 서로 다른 질문입니다.

Authentication

인증: 당신은 누구인가?

④ 도메인과 DNS

DNS는 인터넷의 전화번호부입니다. 이름(gmail.com)을 물으면 IP 주소나 메일 서버 주소를 알려 줍니다. .test는 국제 표준(RFC 2606)에서 테스트 전용으로 예약한 최상위 도메인이어서 누구도 실제로 등록할 수 없습니다. 그래서 실습에 써도 실제 회사 도메인과 충돌하지 않습니다.

레코드하는 일비유실습 필요
A이름에 대응하는 IP 주소건물 주소hosts로 대체
MX이 도메인의 메일을 받을 서버회사 우편 수발실 위치불필요
SPF이 도메인으로 메일을 보내도 되는 서버 목록공식 발송처 명단불필요
DKIM메일에 전자 서명을 붙여 위조·변조 확인봉투의 인감불필요
DMARCSPF·DKIM 검증 실패 메일 처리 정책위조 편지 처리 규칙불필요
PTRIP 주소로 이름을 찾는 역방향 조회주소로 거주자 확인불필요

실습에서 mail.baropick.test 같은 이름을 쓰려면 DNS 대신 각 PC의 hosts 파일(C:\Windows\System32\drivers\etc\hosts)에 다음 한 줄을 추가합니다.

hosts (관리자 권한으로 편집)
192.168.0.10   mail.baropick.test

⑤ 인증 코드 보안이 필요한 이유

1,000,000

6자리 숫자 코드의 경우의 수입니다. 시도 횟수를 제한하지 않으면 자동화 프로그램이 무차별 대입으로 금방 맞힙니다.

0.0005%

시도를 5회로 제한하면 코드를 우연히 맞힐 확률이 이 정도로 떨어집니다. 횟수 제한이 핵심 방어선입니다.

≤ 10분

만료 시간을 짧게 두면, 메일이 유출되더라도 코드를 쓸 수 있는 시간이 짧아집니다. (값은 정책으로 결정)

정책막는 공격·사고
보안 난수 사용코드 생성 규칙을 추측해 다음 코드를 예측하는 공격
일회성 처리이미 쓴 코드를 다시 제출하는 재사용(재전송) 공격
해시로 저장DB가 유출되었을 때 유효한 코드가 그대로 노출되는 사고
목적·계정 함께 검증이메일 확인용 코드로 비밀번호를 바꾸거나, 남의 계정에 코드를 쓰는 공격
재전송 제한메일 폭탄, 메일 서버 과부하
로그에 원문 금지로그 열람 권한만 있는 사람이 코드나 비밀번호를 알아내는 사고

05

신규 직원 계정 발급

회사 메일함이 메일을 받을 수 있는 상태가 된 뒤에야 인증 메일을 보낼 수 있습니다. 이 순서가 가장 중요합니다.

그림 2. 신규 직원 계정 발급 흐름

  1. 직원 정보 등록 관리자직원 ID, 이름, 회사 메일 주소(staff01@baropick.test)를 정합니다.
  2. 메일 사서함 생성 Spring Boot → Mailserver실습 단계에서는 관리자가 setup email add로 직접 만들어도 됩니다.
  3. Keycloak IAM 계정 생성 Admin REST APIemail 속성에 회사 메일을 등록합니다.
  4. 생성 결과 기록과 수신 가능 상태 확인한쪽만 성공한 경우 재시도하거나 보상 처리할 수 있도록 결과를 남깁니다.
  5. 회사 메일 주소와 최초 접속 방법 안내사서함 초기 비밀번호는 아래 주의 사항대로 별도 경로로 전달합니다.
  6. 직원이 Roundcube에서 회사 메일함에 로그인로그인 후 사서함 비밀번호를 바로 변경합니다.
  7. 인증·활성화 메일 발송 Keycloak 또는 Spring Boot일회용 활성화 링크나 만료 시간이 짧은 인증 코드를 보냅니다.
  8. 인증 완료 후 최초 IAM 비밀번호 설정인증이 끝나야 로그인과 비밀번호 설정을 허용합니다.
초기 비밀번호 전달 시 주의

아직 로그인할 수 없는 사서함으로 그 사서함의 초기 비밀번호를 보내면 직원은 확인할 수 없습니다. 관리자가 안전한 별도 경로로 전달하거나 첫 접속을 직접 도운 뒤 바로 변경하게 합니다. 공용 문서나 메신저 공개 채널에 적지 않습니다.

메일 본문에 비밀번호 금지

IAM 초기 비밀번호를 메일 본문에 평문으로 보내지 않습니다. 일회용 활성화 링크나 짧은 만료 시간의 인증 코드를 쓰고, 최초 로그인 때 비밀번호를 새로 설정하게 합니다.

06

이메일 인증과 비밀번호 변경

직원이 인증을 요청하면 코드를 만들어 회사 메일로 보내고, 직원이 입력한 코드를 검증합니다.

그림 3. 인증 메일 발송과 코드 검증 흐름

Keycloak과 Spring Boot의 역할 구분

먼저 검토

방법 A · Keycloak 내장 기능

  • Keycloak의 Realm SMTP 설정에 Docker Mailserver 정보를 등록합니다.
  • 내장된 이메일 확인과 비밀번호 재설정 기능을 그대로 씁니다.
  • 인증 메일 발송과 인증 절차를 Keycloak이 처리합니다.
업무 요구가 있을 때

방법 B · Spring Boot 자체 구현

  • 코드 생성, 저장, 만료, 검증을 Spring Boot가 맡습니다.
  • Spring Boot가 SMTP로 메일을 보냅니다.
  • 인증에 성공하면 Keycloak Admin REST API로 계정 작업을 합니다.
  • 권한 확인, 토큰 검증, 재설정 권한 검증을 엄격하게 처리해야 합니다.
권장

처음부터 두 방법을 모두 만들 필요는 없습니다. Keycloak 내장 기능으로 어디까지 되는지 먼저 확인하고, 바로픽만의 정책이나 업무 흐름이 필요할 때 Spring Boot 인증 기능을 추가합니다.

인증 코드 보안 정책

  • 예측하기 어려운 보안 난수(SecureRandom 등)로 코드 생성
  • 짧은 만료 시간 설정
  • 한 번 사용한 코드는 다시 쓸 수 없게 처리
  • 검증 실패 횟수 제한
  • 인증 메일 재전송 횟수와 간격 제한
  • 인증 목적(활성화, 비밀번호 변경 등)과 대상 계정을 함께 검증
  • DB에는 원문 대신 해시값 저장
  • 로그에 인증 코드, 비밀번호, SMTP 자격 증명을 남기지 않음
  • 인증에 성공한 뒤에만 비밀번호 변경 등 보호된 작업 허용

compose.yaml을 쓸 때 확인할 점
  • 버전 고정: latest는 업데이트에 따라 동작이 바뀔 수 있습니다. 팀 실습을 똑같이 재현하려면 검증한 버전 태그로 고정합니다.

  • Keycloak·PostgreSQL: 기존 바로픽 개발 환경에 이미 있다면 새로 만들지 말고 같은 Docker 네트워크에 연결해 재사용합니다.

③ 메일 발송 서비스 예시

MailService.java
@Service
@RequiredArgsConstructor
public class MailService {

    private final JavaMailSender mailSender;

    public void sendVerificationCode(String recipient, String code) {
        SimpleMailMessage message = new SimpleMailMessage();

        message.setFrom("auth-service@baropick.test");
        message.setTo(recipient);
        message.setSubject("[바로픽] 이메일 인증 코드");
        message.setText(
            "인증 코드는 " + code + "입니다.\n" +
            "인증 코드는 제한된 시간 동안만 유효합니다."
        );

        mailSender.send(message);
    }
}

이 코드는 발송만 보여 주는 기본 예시입니다. 코드 생성, 저장, 만료, 검증, 재사용 방지, 요청 제한은 인증 코드 보안 정책에 따라 따로 구현합니다.

통신사가 SMTP 25번 포트를 막거나 PTR 레코드를 설정할 수 없는 경우가 많습니다. 외부 수신 서버가 발신 IP 평판을 이유로 메일을 거부하거나 스팸으로 분류할 수도 있습니다. 실제 운영에서는 직접 메일 서버를 운영하는 것보다 전문 메일 호스팅을 쓰는 편이 안정적일 수 있습니다.

구축 전에 추가로 확인할 점

TLS 미설정 상태

예시 compose에는 인증서 설정(SSL_TYPE 등)이 없습니다. 그런데 Spring은 starttls.enable: true로 설정되어 있고 Roundcube는 587로 인증 발송을 합니다. 이 상태에서는 STARTTLS나 SMTP 인증이 실패할 수 있으니 실습용 self-signed 인증서를 쓸지 미리 정합니다.

환경변수 지원 여부

ONE_DIR, DMS_DEBUG는 최신 Docker Mailserver에서 지원이 중단되었거나 LOG_LEVEL로 대체되었을 수 있습니다. 고정할 버전의 공식 문서에서 확인합니다.

첫 계정은 바로 생성

Docker Mailserver는 계정이 하나도 없으면 Dovecot이 정상적으로 기동하지 않습니다. up -d 직후에 바로 setup email add를 실행합니다.

포트 공개 모순

원본 본문은 외부 공개가 필요 없다고 하지만 예시 compose는 메일 포트 다섯 개를 모두 호스트에 바인딩합니다. 내부 실습이라면 8080만 공개해도 됩니다.

최종 정리

Docker Mailserver는 직원 사서함과 SMTP·IMAP을 제공하고, Roundcube는 웹메일 화면을 제공합니다. Keycloak은 직원 IAM 계정과 인증을 관리하고, Spring Boot는 계정 발급과 두 시스템 연계를 맡습니다. Keycloak은 메일 사서함까지 관리하지 않으므로, 두 시스템의 계정은 따로 만들고 직원 ID와 회사 메일 주소로 연결합니다. 먼저 무료 내부 실습 환경에서 @baropick.test 메일과 Keycloak 연동, 직원 간 송수신, 회사 메일을 통한 인증 절차를 검증합니다.
