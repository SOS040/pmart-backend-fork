🚨 중요

Keycloak 토큰은 앱에 내려가지 않습니다. Keycloak 토큰은 서버(Employee Auth Service) 안에서만 쓰고 끝납니다. 앱이 들고 다니는 것은 PMart 직원 JWT뿐입니다. ChatGPT 보완: "Keycloak이 발급한 토큰을 Flutter에 자동으로 전달하는 것은 아니다"

1-4. JWT · 개인키 · 공개키 · JWKS

JWT는 머리.내용.서명으로 된 문자열입니다. Employee Auth Service는 개인키(Private Key)로 서명하고, 공개키(Public Key)는 JWKS 주소로 공개합니다. 게이트웨이와 서비스는 그 공개키를 받아 두고 요청마다 스스로 서명을 확인합니다. 매번 Employee Auth Service에 물어보지 않습니다.

이 검증 기능은 직접 만들지 않습니다. Spring Security OAuth2 Resource Server가 제공하고, 안에서 Nimbus JOSE + JWT 라이브러리를 씁니다. PMart는 이미 이 의존성을 쓰고 있습니다.

⚠️ 필기 정정

공개키는 "서비스를 쓰려는 앱을 검증"하는 용도가 아니라 토큰의 서명과 발급자를 검증하는 용도입니다. Resource Server를 쓰는 주된 이유도 "Nimbus를 간접으로 들여오려고"가 아니라 JWT 검증과 HTTP 보안 처리를 표준대로 하려고입니다.

1-5. 기밀 클라이언트와 client_secret

기밀 클라이언트(Confidential Client)는 서버처럼 비밀값을 숨길 수 있는 쪽입니다. Employee Auth Service와 HR Service는 서버라서 client_secret을 안전하게 보관할 수 있습니다. 그래서 둘을 기밀 클라이언트로 등록합니다.

반대로 PDA 앱(APK)과 React 앱은 코드가 공개되어 비밀을 숨길 수 없습니다. 이 설계에서 앱을 클라이언트로 등록하지 않는 이유 중 하나입니다. 앱에는 client_secret이 전혀 없습니다.

03PMart에 적용한 구조도

초록 = 새로 생기는 서비스, 보라 = Keycloak, 파랑 = 기존 정문(게이트웨이)입니다.

🔑 통신 경로는 두 종류입니다 ChatGPT 보완
  1. 브라우저 리디렉션: 직원이 비밀번호를 치는 Keycloak 로그인 화면은 브라우저가 닿을 수 있어야 합니다. Keycloak이 내부망에 있으므로 게이트웨이가 /iam/**로 Keycloak의 OIDC 경로만 중계합니다.
  2. 서버끼리 직접: Employee Auth Service → Keycloak /token, HR Service → Keycloak Admin API는 내부망에서 바로 통신합니다. 게이트웨이를 다시 거칠 필요가 없습니다.

강의 질문 "API 게이트웨이에서 Keycloak으로 바로 갈 수 없는 이유는?"의 답: 기술적으로는 갈 수 있습니다. 진짜 문제는 HTTP가 닿느냐가 아니라 인가 코드를 누가 받고 누가 토큰으로 교환하느냐입니다. 이 설계에서는 그 일을 Employee Auth Service가 맡으므로 게이트웨이는 길만 열어 줍니다.

05흐름 ① 직원 PDA 로그인 — 핵심 흐름

강의 설계(백엔드 중심 로그인) 그대로입니다. 강의에서 "Employee Auth Service가 처리함"이라고 한 부분을 실제 HTTP 단계로 풀었습니다.

단계별 자세한 설명

A. 로그인 시작

  1. PDA 앱→시스템 브라우저

    직원이 로그인 버튼을 누르면 앱이 시스템 브라우저(Custom Tabs)를 엽니다. 앱에는 아이디·비밀번호 입력칸이 없습니다. 일반 내장 WebView 금지

  2. 브라우저→Gateway

    브라우저가 여는 첫 주소는 Keycloak이 아니라 Employee Auth Service의 로그인 시작 주소입니다.

    GET http://192.168.0.40:8080/api/v1/employee-auth/oauth2/authorization/keycloak
    ?app=mfc        ← 로그인이 끝나면 어느 앱으로 돌려보낼지 (PMart 맞춤)
  3. Gateway→Employee Auth

    게이트웨이가 /api/v1/employee-auth/**를 Employee Auth Service로 보냅니다. 이 경로는 아직 토큰이 없는 단계이므로 인증 없이 열린 공개 경로입니다.

  4. Employee Auth

    Spring Security OAuth2 Client가 위조 방지용 state와 PKCE code_verifier를 만들어 브라우저 세션에 저장합니다.

  5. Employee Auth→브라우저

    302 응답으로 브라우저를 Keycloak 인가 주소로 보냅니다.

🔑 왜 앱이 아니라 "브라우저"가 로그인을 시작하나요? PMart 맞춤

④에서 저장한 state는 브라우저 세션 쿠키에 묶입니다. ⑩에서 콜백을 받을 때 "같은 브라우저가 시작한 로그인인지" 확인해야 하므로, 시작(②)과 콜백(⑩)을 같은 브라우저가 해야 합니다. ChatGPT 대화의 "Employee Auth Service가 로그인 URL을 만들어 주면 Flutter가 브라우저로 연다"를 Spring 기본 동작에 맞게 구체화한 것입니다.

B. Keycloak 인증과 코드 교환

  1. 브라우저→Gateway /iam→Keycloak
    GET http://192.168.0.40:8080/iam/realms/pmart-staff/protocol/openid-connect/auth
    ?client_id=employee-auth-service          ← ★ 앱이 아니라 서비스 이름
    &response_type=code
    &scope=openid
    &redirect_uri=http://192.168.0.40:8080/api/v1/employee-auth/login/oauth2/code/keycloak
    &state=…&code_challenge=…&code_challenge_method=S256
  2. Keycloak→브라우저

    Keycloak 로그인 화면이 PDA 화면에 뜹니다. 앱 화면처럼 보여도 실제로는 Keycloak 페이지입니다. 강의 질문 "PDA에서 Keycloak 사이트 화면에서 바로 로그인하는 게 맞나?"의 답은 맞습니다. 다만 그 화면을 연 주체가 OAuth 클라이언트가 되는 것은 아닙니다.

  3. 직원→Keycloak

    IAM 계정(employee01@pmart.com)과 비밀번호를 입력합니다. 이 비밀번호는 Keycloak만 봅니다. PDA 앱, 게이트웨이, Employee Auth Service는 보지 않습니다. 첫 로그인이면 Keycloak이 비밀번호 변경 화면을 띄웁니다.

  4. Keycloak→브라우저

    인증에 성공하면 등록된 콜백 주소로 302를 보냅니다.

    HTTP/1.1 302 Found
Location: http://192.168.0.40:8080/api/v1/employee-auth/login/oauth2/code/keycloak?code=abc123&state=…

    인가 코드를 받는 곳은 Flutter가 아니라 Employee Auth Service의 콜백입니다.

  5. 브라우저→Gateway→Employee Auth

    브라우저가 콜백 주소로 이동하면 Employee Auth Service가 code를 받고, 세션의 state와 비교합니다.

  6. Employee Auth→Keycloak 내부망 직접
    POST http://keycloak:8080/realms/pmart-staff/protocol/openid-connect/token
grant_type=authorization_code
code=abc123
redirect_uri=…/login/oauth2/code/keycloak
client_id=employee-auth-service
client_secret=…            ← 서버만 아는 비밀
code_verifier=…
  7. Keycloak→Employee Auth

    Keycloak이 ID Token과 Access Token(설정에 따라 Refresh Token)을 줍니다. Keycloak이 공식 지원하는 Authorization Code Flow입니다.

C. PMart JWT 받기와 업무 시작

  1. Employee Auth

    Keycloak JWKS로 ID Token을 검증합니다(서명, iss, aud=employee-auth-service, 만료). 그다음 pmart_operator_id로 PMart 직원을 찾아 상태(재직 중인지)와 역할·센터를 확인하고, 60초짜리 일회용 로그인 티켓을 만듭니다.

  2. Employee Auth→브라우저

    브라우저를 앱 딥링크로 보냅니다. 예: pmart-mfc://login?ticket=T-9f2…. 토큰 자체는 주소에 싣지 않고, 아무 데도 못 쓰는 짧은 티켓만 싣습니다.

  3. 브라우저→PDA 앱

    딥링크로 브라우저 탭이 닫히고 앱으로 돌아옵니다.

  4. PDA 앱→Gateway→Employee Auth
    POST /api/v1/employee-auth/tokens
X-Device-Id: PDA-0012
{ "ticket": "T-9f2…" }      ← 한 번 쓰면 사라짐
  5. Employee Auth→PDA 앱

    PMart 직원 Access Token(15분)과 Refresh Token을 발급합니다. 앱은 이것을 기기 보안 저장소에 둡니다.

  6. PDA 앱→Gateway

    이제 피킹·패킹 API를 Authorization: Bearer <PMart JWT>로 부릅니다. → 7장

⚠️ C 단계(앱에 결과 전달)는 강의에서 비어 있던 부분

ChatGPT도 "여기에는 추가 설계가 필요하다. 예를 들어 일회용 로그인 티켓으로 Flutter가 토큰을 안전하게 받아오게 할 수 있다"고 했습니다. 이 문서는 그 제안을 PMart에 맞춰 구체화했습니다(티켓 60초·1회용·발급 기기 확인). Access Token을 딥링크 주소에 직접 싣는 방식은 쓰지 않습니다. 주소는 기록에 남거나 다른 앱이 가로챌 수 있기 때문입니다.

✅ React 백오피스도 같은 흐름

백오피스는 이미 브라우저라서 ①이 "로그인 페이지로 이동"이 되고, ⑭~⑯은 딥링크 대신 백오피스 주소로 redirect + 티켓 교환이 됩니다. Keycloak에 등록하는 클라이언트는 여전히 employee-auth-service 하나입니다.

06Employee Auth Service 안쪽

강의 필기 "이걸 쓰려면 OAuth2 클라이언트 디펜던시가 붙어야 함"을 PMart 규칙(Gradle, pmart-config)에 맞춰 보여 줍니다. PMart 맞춤 예시

6-1. 의존성 — 두 역할에 두 가지

의존성왜 필요한가
spring-boot-starter-oauth2-clientKeycloak에 대한 OAuth2 클라이언트 역할. 로그인 주소 만들기, 콜백 받기, 코드 교환, ID Token 검증을 대신 해 줍니다

spring:

⚠️ iss 주소를 하나로 맞추기

Keycloak은 토큰의 iss를 "자기가 아는 외부 주소"로 씁니다. 브라우저가 게이트웨이(/iam)로 들어오므로 Keycloak에 KC_HOSTNAME=http://192.168.0.40:8080/iam, KC_PROXY_HEADERS=xforwarded를 설정해 브라우저가 본 주소와 iss를 같게 해야 합니다. 서버끼리 부르는 내부 주소(192.168.0.101:8180)와 달라도 iss 검증이 깨지지 않게 하려는 설정입니다. ChatGPT 보완: "외부 URL, redirect URI, 프록시 설정을 일치시켜야"

6-3. Employee Auth Service가 발급하는 PMart 직원 JWT

{
  "iss": "http://employee-auth-service:8520",   ← 발급자 = Employee Auth Service (Keycloak 아님)
  "sub": "OP-45e6ce65-…",                        ← PMart 직원 ID
  "aud": ["pmart-api"],
  "typ": "OPERATOR",                             ← PMart 사용자 종류
  "roles": ["MFC_WORKER"],
  "centers": ["MFC-SEED-01"],
  "sid": "ES-…", "jti": "…",
  "iat": …, "exp": …                             ← 15분
}
✅ 이 설계의 큰 장점: 업무 서비스는 거의 그대로

이 토큰 모양은 예전 auth-service 운영자 토큰과 같습니다(sub=OP-…, typ=OPERATOR, roles, centers). 그래서 50개 업무 서비스의 권한 판단 코드는 바꿀 필요가 없고, 발급자 표의 한 줄만 바뀝니다. Keycloak 토큰의 특이한 모양(typ="Bearer", realm_access.roles, UUID sub)은 Employee Auth Service 안에서만 처리하면 됩니다.

07흐름 ② 로그인 뒤 업무 API 호출

PDA 앱이 피킹 작업을 가져오는 상황을 예로 듭니다. 이 부분은 PMart에 이미 있는 검증 구조를 그대로 씁니다.

  1. PDA 앱→Gateway

    GET /api/v1/mfc/pick-tasks?center=MFC-SEED-01 + Authorization: Bearer <PMart 직원 JWT>

  2. Gateway

    발급자 고르기: iss가 Employee Auth Service인지 확인합니다. 발급자 표에 없으면 401

  3. Gateway

    서명 확인: Employee Auth Service JWKS 공개키로 서명과 만료를 확인합니다. 공개키는 처음 한 번 받아 두고 재사용합니다.

  4. Gateway

    대상·종류 짝: aud=pmart-api여야 하고, 이 발급자는 OPERATOR만 낼 수 있습니다. 고객 토큰으로 직원 API를 부르면 막힙니다.

  5. Gateway↔Redis

    차단 목록: 퇴사·정지된 직원의 토큰이면 401 SUBJECT_BLOCKED → 9장

  6. Gateway→mfc 서비스

    경로에 맞는 서비스로 전달합니다.

  7. mfc 서비스

    다시 검증: common-security가 같은 발급자 표로 한 번 더 확인합니다. 게이트웨이를 믿고 건너뛰지 않습니다.

  8. mfc 서비스

    업무 권한: roles에 MFC_WORKER가 있고 centers에 MFC-SEED-01이 있어야 합니다. 아니면 403

발급자 표 변화 (pmart-config application-lan.yml)

pmart:
  security:
    issuers:
      - id: staff                                   # ★ 직원 — Keycloak 대신 Employee Auth Service
        issuer-uri: 'http://employee-auth-service:8520'
        jwk-set-uri: 'http://employee-auth-service:8520/api/v1/internal/jwks'
        audiences: [pmart-api]
        user-types: [OPERATOR]
      - id: auth-service                            # 고객·비회원·서비스 (그대로)
      - id: rider                                   # 라이더 (그대로)
🔑 401과 403

401 = 토큰이 없거나 가짜이거나 만료됨(인증 실패) · 403 = 누군지는 알지만 이 일은 할 수 없음(인가 실패)

🔑 SSO와 인가는 다릅니다

같은 Keycloak 계정으로 PDA와 백오피스에 모두 로그인할 수 있지만(SSO), 무엇을 할 수 있는지는 PMart JWT의 역할·센터로 앱과 서비스마다 따로 판단합니다. MFC 작업자가 인사 화면에 들어가지 못하는 것은 SSO와 상관없이 인가에서 막히기 때문입니다.

08흐름 ③ 신규 직원 등록 — HR Service

강의 필기: "인사팀이 사용할 백오피스 React 앱 요청을 처리할 HR 서비스를 API 게이트웨이 뒤에 만든다. HR 서비스가 Keycloak에 IAM 계정 생성을 요청한다."

  1. 인사팀→Gateway→HR Service

    인사팀이 백오피스에서 신규 직원의 이름, 쓸 메일 아이디, 소속 센터, 직무를 입력합니다. 인사팀 직원도 자기 PMart 직원 JWT로 로그인한 상태입니다.

    POST /api/v1/hr/employees
{ "name": "홍길동", "mailId": "gildong", "center": "MFC-SEED-01", "job": "MFC_WORKER" }
  2. HR Service

    요청한 사람이 인사 권한(예: HR_ADMIN)을 가졌는지 확인합니다. 그다음 PMart 직원 ID OP-<UUID>를 새로 매기고 자기 DB에 직원 기록을 만듭니다.

  3. HR Service→Keycloak

    먼저 자기 자격 증명으로 관리용 토큰을 받습니다. 직원 로그인과는 다른 길입니다.

    POST /realms/pmart-staff/protocol/openid-connect/token
grant_type=client_credentials
client_id=hr-service
client_secret=…
  4. HR Service→Keycloak Admin API
    POST /admin/realms/pmart-staff/users
Authorization: Bearer <관리 토큰>
{
  "username": "gildong@pmart.com",
  "email": "gildong@pmart.com",
  "firstName": "길동", "lastName": "홍",
  "enabled": true,
  "attributes": { "pmart_operator_id": ["OP-7c1d…"] },
  "requiredActions": ["UPDATE_PASSWORD"]
}
→ 201 Created  (Location 머리글에 Keycloak 사용자 ID)
  5. HR Service→Keycloak→메일 서버

    비밀번호 설정 메일을 보내 달라고 요청합니다.

    PUT /admin/realms/pmart-staff/users/{id}/execute-actions-email
["UPDATE_PASSWORD"]

    신입은 메일의 링크로 자기 비밀번호를 직접 정합니다. 메일함이 아직 없다면 인사팀이 Keycloak에 임시 비밀번호(Temporary)를 넣고 직접 전달하는 방법도 있습니다.

  6. HR Service→Employee Auth

    EmployeeRegistered 사건(Kafka)으로 Employee Auth Service가 직원 연결과 상태(ACTIVE), 역할·센터를 등록합니다. PMart 규칙(다른 서비스 DB 직접 접근 금지)에 맞춘 방식입니다. PMart 맞춤

  7. HR Service→인사팀

    "계정 생성 완료: gildong@pmart.com, 비밀번호 설정 메일 발송"을 돌려줍니다.

🚨 강의 필기 정정 ChatGPT 보완
  • "계정 생성은 OAuth 서버와 상관없다" → 로그인 API와는 별개지만, Admin API를 부르려면 HR Service도 Keycloak 기밀 클라이언트로 토큰을 받아 관리 권한을 증명해야 합니다.
  • "xxx@과 초기 패스워드를 Keycloak에서 받아 인사팀에 전달" → Keycloak은 비밀번호를 평문으로 돌려주지 않습니다. 메일 링크로 본인이 정하게 하거나, 임시 비밀번호를 HR이 정해 넣습니다.
  • root 권한 → 필요 없습니다. manage-users만 줍니다.

09흐름 ④ 토큰 갱신 · 로그아웃 · 퇴사

🔄 갱신

Access Token이 만료되면 앱이 POST /api/v1/employee-auth/tokens/refresh에 Refresh Token을 보냅니다. Employee Auth Service가 직원 상태를 다시 확인하고 새 토큰 쌍을 줍니다(1회용 회전). Keycloak에는 다시 가지 않습니다.

🚪 로그아웃

앱 → POST /api/v1/employee-auth/logouts로 PMart 세션을 끝냅니다. 공용 PDA라면 브라우저의 Keycloak 세션도 끝내야(end_session_endpoint) 다음 작업자가 앞사람으로 자동 로그인되지 않습니다.

⏳ 세션 길이

PMart 직원 Access 15분, 세션은 근무 교대 기준(예: 12시간). Keycloak 세션과 PMart 세션은 따로 돕니다. "OpenID 세션 90일" 같은 고정값은 없습니다.

퇴사 · 정지 처리

  1. 인사팀→HR Service

    POST /api/v1/hr/employees/{id}/leave (퇴사 처리)

  2. HR Service→Keycloak

    Admin API로 enabled=false를 설정하고 세션을 로그아웃시킵니다. 이제 새로 로그인할 수 없습니다.

  3. HR Service→Kafka

    EmployeeLeft 사건을 냅니다.

  4. Employee Auth

    사건을 받아 상태를 LEFT로 바꾸고 Refresh Token을 모두 무효로 만든 뒤, SubjectBlocked 사건을 냅니다(PMart에 이미 있는 계약).

  5. Gateway→Redis

    게이트웨이가 Redis 차단 목록에 "이 직원의 이 시각 이전 토큰 거부"를 씁니다. → 이미 나간 15분짜리 토큰도 바로 401

🚨 Keycloak 계정은 지우지 말고 비활성화

지우면 기록 연결(OP-…)이 끊기고 감사 추적이 어려워집니다. 퇴사자는 enabled=false로 둡니다.

✅ 지금 PMart보다 단순해지는 점

지금은 관리자가 Keycloak 화면에서 직접 막기 때문에 auth-service가 Keycloak 관리 기록을 10초마다 읽어 차단 사건을 대신 냅니다(StaffBlockRelay). 이 설계에서는 퇴사 처리를 HR Service가 직접 하므로 그 자리에서 사건을 낼 수 있습니다. 관리 기록을 읽는 중계가 필요 없어집니다(Keycloak 화면에서 직접 막는 경우만 남으면 그때 유지).

10고객 로그인과 나란히 보기

강의에서 함께 다룬 Google 고객 로그인과 비교하면 이 설계의 의도가 잘 보입니다.

고객 (지금 PMart · ADR-0055)

  1. 고객 앱 → Google 로그인 → Google ID 토큰
  2. 앱 → 게이트웨이 → auth-service POST /auth/social-logins
  3. auth-service가 Google 공개키로 검증
  4. Google sub → CU-… 연결
  5. PMart 고객 JWT 발급

직원 (이 적용안)

  1. PDA → 브라우저 → Keycloak 로그인 → Keycloak 토큰(서버로)
  2. 브라우저 → 게이트웨이 → Employee Auth Service 콜백
  3. Employee Auth가 Keycloak 공개키로 검증
  4. Keycloak sub → OP-… 연결
  5. PMart 직원 JWT 발급
🔑 차이점 하나: Google 쪽은 "OAuth 클라이언트"가 아님

고객 쪽 auth-service는 앱이 받아 온 Google ID 토큰을 검증만 합니다. 인가 코드 교환, client_secret, Spring OAuth2 Client를 쓰지 않습니다(ADR-0055). 그래서 강의 질문 "Auth Service가 우리 PMart의 OAuth 클라이언트 서버지?"의 답은 이렇습니다.

  • 직원 쪽 Employee Auth Service: Keycloak의 OAuth 클라이언트가 맞습니다 (이 설계).
  • 고객 쪽 auth-service: 개념상 Google 로그인을 받아 주는 쪽이지만, PMart 구현은 클라이언트 흐름 없이 ID 토큰 검증 방식입니다.
  • 주문·결제 같은 업무 API는 둘 다 리소스 서버입니다.
⚠️ 용어: 직원 로그인은 "소셜 로그인"이 아닙니다

강의 필기에 "Employee Auth Service가 소셜 로그인을 처리"라고 되어 있지만, 회사 IAM 계정(@pmart.com)으로 Keycloak에 로그인하는 것은 사내 IAM 인증입니다. Google·Naver처럼 외부 IdP를 Keycloak에 연동할 때만 소셜 로그인이라고 부릅니다. ChatGPT 보완

11지금 PMart에서 무엇이 바뀌나

PMart 저장소에는 Keycloak이 이미 2026-11-11부터 다른 방식으로 돌고 있습니다(ADR-0054: 백오피스가 Keycloak에 직접 로그인하고 Keycloak 토큰을 그대로 씀). 이 적용안으로 가려면 아래를 바꿔야 합니다.

👍 이 적용안의 장점

  • 고객·라이더·직원 모두 "외부가 신원 확인 → PMart가 토큰 발급"으로 모양이 같아집니다
  • 업무 서비스가 Keycloak 토큰 모양을 몰라도 됩니다. 토큰 형태가 예전 운영자 토큰과 같습니다
  • 앱에 Keycloak 토큰이나 비밀이 전혀 없습니다
  • 퇴사·정지를 HR 업무 흐름 안에서 바로 처리합니다
  • 나중에 IdP를 바꿔도 Employee Auth Service만 고치면 됩니다

👎 감수할 점

  • 서비스가 2개 늘어납니다(운영·배포·모니터링 대상 증가)
  • 앱에 결과를 넘기는 티켓 설계가 추가로 필요합니다
  • Keycloak을 게이트웨이 뒤로 숨기려면 프록시와 iss 설정을 정확히 맞춰야 합니다
  • 이미 배포된 백오피스 Keycloak 로그인을 다시 바꿔야 합니다
  • ChatGPT 의견: 앱이 직접 Keycloak에 붙는 방식(PKCE)이 "비교적 단순"하다. 이 설계도 가능하지만 유일한 정답은 아님

12주의할 점 · 자주 하는 오해

필기 / 오해정확한 설명
Keycloak은 인증만 해 준다Keycloak 자체는 토큰 발급·SSO·계정 관리까지 할 수 있습니다. 이 설계에서는 일부러 신원 확인 용도로만 쓰고 PMart JWT는 백엔드가 만듭니다
Flutter·React 앱은 Keycloak 클라이언트가 될 수 없다될 수는 있습니다(공개 클라이언트 + PKCE). 이 설계는 등록하지 않기로 선택한 것입니다
PDA에서 Keycloak 화면으로 로그인하는 게 맞나?맞습니다. 단, 시스템 브라우저(Custom Tabs)를 쓰고 일반 WebView는 쓰지 않습니다(RFC 8252)
게이트웨이에서 Keycloak으로 갈 수 없다갈 수 있습니다. 문제는 리디렉션과 코드 교환을 누가 맡느냐입니다. 관리 경로(/admin)는 외부에 열지 않습니다
액세스 토큰을 내서 URL 정보를 얻는다URL은 이미 알고 있고, 그 URL의 보호된 API에 접근하려고 토큰을 냅니다. /token은 코드를 토큰으로 바꾸는 곳입니다
Access·Refresh Token을 둘 다 Authorization 헤더에API에는 Access Token만 넣습니다. Refresh Token은 갱신 주소에만 보냅니다
OpenID와 액세스 토큰을 게이트웨이에 주면 회원 테이블에 저장토큰 자체를 회원 테이블에 저장하지 않습니다. 검증 뒤 주체 연결(sub ↔ PMart ID)만 저장합니다
Keycloak SMTP = 자체 메일 서버·메일함아닙니다. 외부 SMTP로 보내기만 합니다. 메일함과 웹메일(Roundcube)은 따로 구성합니다
root만 IAM 계정을 발급manage-users만 가진 서비스 계정이면 됩니다
공개키는 서비스를 쓰려는 앱을 검증토큰의 서명·발급자를 검증합니다
@RestController가 HTTP 응답의 시작점요청은 톰캣 → 필터(SecurityFilterChain) → DispatcherServlet → 컨트롤러 순서로 들어오고, 반환값이 응답으로 변환됩니다
Spring Boot Web = 항상 TomcatMVC 서비스는 Tomcat, WebFlux(PMart 게이트웨이)는 Reactor Netty입니다
⚠️ LAN에서 운영으로 갈 때
  • 지금 LAN은 HTTP입니다. 운영에서는 TLS(HTTPS) 필수입니다. 비밀번호, 코드, 티켓이 오가기 때문입니다
  • client_secret은 .secrets에 원본, pmart-config에는 {cipher}만 둡니다. 로그에 토큰·비밀번호를 남기지 않습니다
  • 게이트웨이에서 /iam/admin/**, /iam/realms/master/**는 반드시 차단합니다

13용어 사전

OAuth 2.0
앱이 사용자 대신 API를 쓸 수 있도록 권한을 위임하는 규칙.
OIDC (OpenID Connect)
OAuth 2.0 위에 "이 사람이 누구인가"를 더한 규칙. ID Token이 여기서 나옵니다.
IAM
Identity and Access Management. 직원 계정과 접근을 관리하는 체계. 여기서는 Keycloak의 xxx@pmart.com 계정.
Realm
Keycloak 안의 독립된 사용자·클라이언트 묶음. 예: pmart-staff.
기밀 / 공개 클라이언트
client_secret을 숨길 수 있는 서버 / 숨길 수 없는 앱·브라우저.
Grant Type
토큰을 받는 방식. authorization_code(사람 로그인), client_credentials(서버끼리, HR Service), refresh_token(갱신).
Redirect URI · 콜백
로그인 뒤 인가 코드를 받는 주소. 이 설계에서는 Employee Auth Service의 /login/oauth2/code/keycloak.
state · PKCE
각각 로그인 요청 위조 방지, 인가 코드 가로채기 방지를 위한 난수.
일회용 로그인 티켓
로그인 결과를 앱에 안전하게 넘기려고 만드는 짧은 수명의 1회용 값. 앱이 이것을 PMart 토큰으로 바꿉니다.
JWT · JWS · JWKS
토큰 형식 · 서명된 JWT · 공개키 목록 주소.
iss · sub · aud · exp · iat
발급자 · 주체 · 대상 · 만료 · 발급 시각.
Resource Server
토큰을 검증하고 API를 제공하는 쪽. PMart 게이트웨이와 업무 서비스.
Admin REST API
Keycloak 관리 기능을 HTTP로 부르는 API. 예: POST /admin/realms/{realm}/users, execute-actions-email.
SMTP · Roundcube
메일을 보내는 규약 · 메일함을 웹으로 보여 주는 PHP 웹메일 프로그램(Apache 위에서 동작).
SSO
한 번 로그인으로 여러 앱을 쓰는 것. 무엇을 할 수 있는지(인가)는 별개입니다.
발급자 표
PMart 설정 pmart.security.issuers. 인정하는 토큰 발급자와 각 발급자가 낼 수 있는 사용자 종류를 적은 표.
