# 상품 사진 축소본: 만들어지고 고객 앱에 쓰이는 흐름

작성 2026-11-20 (PC 1). 고객 앱의 목록과 상품 상세가 느리다는 문제를 분석하고 고친 결과를 정리한다.

관련 문서:
- 상품 추가와 재색인: `product-add-and-reindex.md`
- 상품 검색: `product-search.md`
- 앱 요청서: `docs/handoff/clients/customer-app/2026-11-19-request-detail-image-performance.md`, `…-detail-speed-followup.md`

## 1. 한눈에

```
[백오피스] 사진 올리기 ──► product-content: 원본 저장 + content_image 행
                                 │ 5초 뒤(뒤에서)
                                 ▼
                       축소본 240·480·720 미리 만들기 → 저장소 variants/w<폭>/<sha256>.jpg
                                                          기록 content_image_variant
[승인·게시] DISPLAY 승인 ──► 상세·검색 색인·홈 진열에 사진 주소 /api/v1/content-images/{사진ID}
[고객 앱] 같은 주소 + ?w=240|480|720 ──► 게이트웨이(사진은 처리율 제한 없음) ──► product-content
                                          ├─ 미리 만든 축소본 있음 → 바로 준다(0.1초 안팎)
                                          ├─ 아직 없음 → 그 자리에서 만들고 저장(동시 4장까지)
                                          └─ 원본이 그 폭 이하·WEBP → 원본
응답: Cache-Control max-age=1년, immutable · ETag <sha256>-w<폭> → 앱은 한 번 받은 사진을 다시 받지 않는다
```

## 2. 단계별

### 2-1. 사진 올리기 (백오피스, 운영자)
- product-content-service는 다음 두 가지를 저장한다.
  - 원본: S3 호환 저장소, ADR-0016
  - 사진 정보: `content_image` 행(사진 ID, 내용 해시 sha256, 형식, 폭·높이)
- 같은 내용의 사진(같은 sha256)은 원본을 한 번만 저장한다.
- 올린 지 5초 뒤 `VariantPreparer`가 뒤에서 축소본을 만든다.
  - 커밋을 기다리려고 5초 뒤에 시작한다.
  - 폭은 240·480·720이고, 원본보다 작은 폭만 만든다.
  - 기록은 `content_image_variant` 표에 남긴다(V4, sha256마다 한 줄).
  - 뒤에서 스레드 하나만, 낮은 우선순위로 돈다. 요청 처리와 CPU를 다투지 않게 하려는 것이다.
- 다음 때도 남은 것을 만든다.
  - 서비스가 뜬 지 30초 뒤
  - 그 뒤 2분마다
- 그래서 놓친 사진이나 예전 사진도 차례로 채워진다.
- 이 단계에서는 아직 고객에게 보이지 않는다. 사진이 초안에 붙어 있기 때문이다.

### 2-2. 승인·게시
- DISPLAY 승인이 나면 콘텐츠 버전이 게시된다.
- 상세 응답(`GET /product-contents/{id}`)의 사진 주소는 `/api/v1/content-images/{사진ID}` 하나다.
- 검색 색인(`imageUrl`)과 홈 진열 카드도 같은 대표 사진 주소를 쓴다.
- **축소본 주소는 따로 없다.** 폭은 요청할 때 `?w=`로 고른다. 그래서 축소본이 생겨도 재색인이나 진열 갱신이 필요 없다.

### 2-3. 고객 앱이 부를 때
- 앱은 같은 주소에 폭을 붙인다.
  - 목록 카드: 카드 크기 × 화소 비율에 맞춰 `?w=240` 또는 `?w=480`
  - 상세 대표 사진, 설명·상세정보 사진: `?w=720`
- 앱은 사진을 화면 폭에 맞춰서만 디코딩하고(`cacheWidth`), 상세의 설명 사진은 화면에 보일 때만 받는다(`ListView.builder`).
- 서버(`ImageVariants.variant`)는 다음 순서로 판단한다.
  1. 원본 폭이 요청 폭 이하이거나, 줄일 수 없는 형식(WEBP)이면 원본을 준다.
  2. 저장소에 `variants/w<폭>/<sha256>.jpg`가 있으면 그것을 준다. 미리 만들기가 끝난 사진은 늘 이 경우다.
  3. 없으면 그 자리에서 만들어 저장하고 준다. 동시에 4장까지만 만들고, 다음부터는 2번이 된다.
- 품질은 JPEG 0.82(`JpegResizer.QUALITY`)다.

### 2-4. 캐시
- 응답에 `Cache-Control: max-age=31536000, private, immutable`와 `ETag: "<sha256>-w<폭>"`를 붙인다.
- 사진을 바꾸면 새 사진 ID와 새 sha256이 되어 주소가 달라진다. 그래서 예전 사진이 캐시에 남아 보이는 일이 없다.

### 2-5. 게이트웨이
- `/api/v1/content-images/*`와 `/api/v1/review-photos/*`는 처리율 제한에서 뺐다(pmart-config `50bc343`). 읽기 전용이고 1년 동안 바뀌지 않는 응답이다.
- 리뷰 사진 올리기(`POST /api/v1/review-photos`)는 경로가 달라서 제한을 그대로 받는다.
- API 요청은 이전처럼 제한한다.
  - 비로그인: IP마다 초당 10, 버스트 20
  - 로그인: 사용자마다 초당 20, 버스트 40

## 3. 왜 이렇게 바꿨나 (2026-11-20 측정, LAN)

| 확인 | 결과 |
|---|---|
| 검색 색인 | 이미 대표 정보만 들어 있다(이름·대표 사진 주소·가격·판매 상태·별점·상품 ID). 목록은 한 번 받아 그린다(20개에 8KB). API 응답은 20~140ms |
| 사진 요청 수 제한 | 앱의 사진 요청(`Image.network`)은 토큰 없이 와서 IP 단위 비로그인 한도(버스트 20)에 걸렸다 |
| ↳ 카테고리 화면 들어가기 | 22건 중 2건이 429 |
| ↳ 1초 뒤 스크롤 | 21건 중 11건이 429 |
| ↳ 상세 화면 | API 4건 + 설명 사진 16~20장으로 한도를 넘었다 |
| 상세 API | 상세와 가격을 합쳐 50~90ms. 느린 원인이 아니다 |
| 처음 보는 상품의 설명 사진 | 16~20장이 0.7~1.5초(한 장 최대 0.74초). 그때 줄이고, 동시에 2장까지만 줄였기 때문이다. 다시 보면 0.1초 |
| 용량 | 축소본(w720)으로도 상품 하나에 1.5~1.7MB. 설명 사진은 보통 7장, 많으면 16~20장 |

고친 것:

| 고친 것 | 커밋 |
|---|---|
| 게이트웨이에서 공개 사진을 처리율 제한에서 뺌. 같은 재현에서 429가 0건이 됐다 | pmart-config `50bc343`, 시험 사본 `580f6b04` |
| 축소본 미리 만들기(`VariantPreparer`, V4) | `4460c4d1` |
| 요청 때 만들 때 동시 2장 → 4장(PC 2 논리 CPU 12개) | `4460c4d1` |

하지 않은 것: 화질 낮추기(0.82 → 0.75, 용량 −20~30%). 화질과 바꾸는 일이라 사용자가 원할 때만 한다.

## 4. 운영 메모
- 처음 배포한 뒤 기존 사진 일괄 처리는 product-content-service가 뒤에서 했다(배포 2026-11-20 04:57, PC 2).
  - 도는 동안 CPU를 코어 하나쯤 쓴다.
  - 메모리는 컨테이너 한도 768MiB 가까이 보인다. JVM 힙이 한도의 75%(`MaxRAMPercentage`)까지 쓰기 때문이고, 메모리 초과로 꺼진 적은 없다.
- 일괄 처리가 끝나면 서비스 기록에 `image variants prepared contents=… made=…`가 남는다.
- 한 사진이 실패하면(원본 없음 등) `image variant prep failed`가 경고로 남고, 다음 차례에 다시 해 본다.
- 축소본 폭을 바꾸거나 더하려면 아래 셋을 같이 고친다. 그리고 `content_image_variant`를 비워 다시 만들게 한다.
  - 계약 `w` enum
  - `ImageVariants.WIDTHS`
  - `prepare`의 폭 목록
