# ADR-0034 상품·가격 이벤트 이력 무제한 보관과 검색 재색인 정책 — Kafka 전체 재생, 스냅샷 API 는 도입하지 않음

- 상태: 승인 (2026-11-03, 사용자 최종 승인 "Kafka 이벤트 보관 정책 및 LAN 운영 개선 — 최종 승인")
- 보완: ADR-0031 결정 3("재처리 = 소비 그룹 오프셋 되돌림 — 이벤트는 Kafka 에 보존")·결정 8(LAN 전환 때 새 소비 그룹이 처음부터 읽어 재구축). 두 결정이 전제한 "이벤트가 Kafka 에 남아 있다"를 보관 정책으로 보장한다. 색인을 쓰는 주체가 Logstash 하나라는 결정은 그대로다.
- 관련: ADR-0009(Outbox·Debezium), ADR-0021·0031(검색), ADR-0030(디스크 상한), `deploy/lan/kafka/README.md`(백업·복원·감시 절차), `docs/architecture/search-comparison.md`, `docs/architecture/debezium-usage-vs-eum.md`

## 배경
- 검색 색인(Elasticsearch `products`·`sku-prices`)은 `commerce.product.v1`·`commerce.pricing.v1` 사건으로만 만든다(ADR-0031). 색인이 원천과 어긋나거나 다시 만들어야 할 때 쓸 수 있는 정본 사본은 이 두 토픽의 사건 이력뿐이다.
- 두 토픽에는 보관 설정이 없어 Kafka 기본값 **7일**(`log.retention.hours=168`)이 걸려 있었다. 사람이 정한 값이 아니다. 디스크 때문에 보수적으로 잡은 "7일 또는 2GB"는 Prometheus 설정이다(ADR-0030). 첫 사건이 2026-10-30 이라 이르면 11/6~11 에 첫 구간이 지워질 수 있었다. 그러면 이력만으로는 색인을 다시 만들 수 없다.
- 유한한 보관 기간으로는 전체 재생 재구축이 성립하지 않는다. 2년 동안 바뀌지 않은 상품은 등록 사건 하나뿐이고, 그것이 지워지면 되살릴 수 없다.
- 규모: 상품 29개에 사건 116건이며 상품 토픽 약 103KB, 가격 토픽 약 28KB 이다. 상품 하나를 처음 등록하면 사건 약 4.5KB 가 쌓인다. 400개는 약 2MB, 1만 개에 하루 변경 수천 건이면 1년에 약 1.5GB 다.
- 재생 재구축 검증(2026-11-03):
  - 운영 중인 색인과 새 소비 그룹이 처음부터 다시 만든 색인이 일치했다(통합 시험 실험, LAN 백업 복원 시험 29/29).
  - 예외 두 가지가 있다. 콘텐츠 보강 API 가 실패하면 그 상품이 이름 없이 빠지고, 판매상태는 시각으로 비교해 시계가 어긋나면 틀린다(아래 결정 6).

## 결정
1. **무제한 보관은 두 토픽만**: `commerce.product.v1`·`commerce.pricing.v1` 에 토픽 동적 설정 `retention.ms=-1`, `retention.bytes=-1` 을 건다.
   - `cleanup.policy=delete` 는 그대로다. Log Compaction 은 쓰지 않는다. 같은 키(상품 id)에 사건 종류가 여러 개라, 압축하면 앞 사건(콘텐츠 게시 등)이 지워진다.
   - 다른 토픽의 보관 설정은 바꾸지 않는다(브로커 기본 7일).
2. **설정은 배포가 보장한다(멱등)**: `deploy/lan/kafka/topics-init.sh` 를 Kafka 컨테이너 안에서 실행한다.
   - 토픽이 없으면 파티션 1개로 만들고, 있으면 파티션 수는 그대로 두고 설정만 보정한다.
   - `lan.sh deploy` 는 Kafka 가 있는 PC 에서 `up -d --no-recreate --wait kafka` 로 kafka 를 먼저 올린다. 이어 스크립트를 `compose cp` 로 넣고 `exec` 로 실행한 뒤 나머지를 올린다. PC 는 이름 순서로 배포되므로 pc3 의 Debezium Connect 보다 앞선다.
   - 새 Docker 구성요소는 만들지 않는다. 다른 PC 의 `extra_hosts` 가 바뀌어 그 PC 컨테이너가 모두 재생성되는 것을 피하려는 것이다.
   - 같은 이유로, 다른 PC 가 이름으로 부르지 않는 보조 구성요소(`es-exporter`)도 `extra_hosts` 에서 뺀다(`render.sh` `NO_EXTRA_HOST`).
3. **감시는 기존 체계를 쓴다**:
   - **측정**: PC 1 `watch.sh`(예약 작업, 5분)가 Kafka PC 에서 `topic-metrics.sh` 를 읽기 전용으로 실행한다. 결과는 그 PC 의 `pmart-lan/metrics/kafka_topics.prom` 에 쓴다.
   - **노출·수집·경보**: 같은 PC 의 `host-disk`(node-exporter textfile)가 내보내고, pc4 Prometheus 가 수집하고 경보를 평가한다.
   - **지표**: 토픽 크기, 시작·끝 오프셋, 무제한 보관 여부, 측정 시각.
   - **고정 크기 경보는 두지 않는다**(커지는 것이 정상). 대신 아래를 감시한다: 보관 정책 풀림, 앞 사건 삭제, 1시간 사건 급증, 하루 크기 급증, C: 7일 내 고갈 예측(기존 C: 여유 경보에 더해), 측정 멈춤·없음.
   - PC 2 예약 작업 대신 watch.sh 를 고른 이유: 새 상주 작업이 없고 저장소만 고치면 갱신된다. PC 1 이 꺼져 측정이 멈추는 약점은 멈춤 경보로 드러낸다.
4. **백업·복원**:
   - **백업 형식**: 키·값·헤더·파티션·파티션 안 순서를 그대로 담은 줄 단위 텍스트(`backup.sh` → `backup-topic.sh`)에 MANIFEST(오프셋·건수·sha256)를 붙인다.
   - **백업 위치**: Kafka PC 와 다른 장애 영역이다. 첫 위치는 PC 1 `D:\pmart-backups\kafka`(PC 1 C: 와 같은 물리 디스크라 외부 매체·별도 저장소로 옮길지는 미결).
   - **복원 원칙**: 운영 토픽에 다시 넣지 않는다(모든 구독자에게 한 번 더 간다). Kafka 를 잃었을 때 **빈 복구 환경**에 넣고, 구독 그룹 오프셋을 정한 뒤 소비자를 띄운다.
   - **복원 시험**: 격리된 임시 Kafka 에서 복원한다. 복원한 사건으로 검색 색인을 다시 만들고 원천과 대조한다.
   - **백업 시점**: 이번 변경 전 1회, 상품 대량 등록 뒤 1회. 정기 자동화는 따로 정한다.
5. **재색인은 Kafka 전체 재생**:
   - 새 소비 그룹(또는 오프셋 되돌림)으로 처음부터 읽는다. 스냅샷 API 는 만들지 않고, `GET /internal/reindex` 계열은 501 그대로 둔다.
   - 매핑만 바뀌고 `_source` 로 충분하면 ES `_reindex` 를 쓴다. 이때 Logstash 를 멈춘 상태에서만 하고, 별칭을 옮긴 뒤 다시 띄운다(새 업무 사실을 넣는 주체는 여전히 Logstash 하나).
   - **스냅샷 기반 재색인 재검토 조건**: 전체 재생 시간이 운영상 과도해질 때(예: 수 시간), 운영 출시·규모 확대, 무제한 보관을 유지할 수 없을 때.
6. **선행 조건 — 이 두 버그를 고치기 전에는 전체 재생 재색인을 운영 절차로 실행하지 않는다**(각각 별도 작업):
   - 판매상태 버전 비교를 `rowVersion` 으로 통일한다. 지금은 `effectiveAt` 시각 비교다. `ProductVersionPublished` 에 rowVersion 이 없다. 대상은 product-service 계약, search Logstash 처리, storefront-service.
   - 콘텐츠 보강 API 가 실패하면 그 사건을 건너뛰어(stdout 한 줄) 검색 데이터가 영구히 빠진다. 재시도·DLQ·경보로 고친다.

## 대안
- **유한 보관(30·90일)**: 디스크는 덜 쓰지만 결정 1 배경처럼 전체 재생 재구축이 깨진다. 기간을 늘리는 것은 시간을 버는 것일 뿐이다.
- **Log Compaction**: 키당 마지막 사건만 남아 같은 상품의 다른 종류 사건이 사라진다.
- **스냅샷 API(원천의 현재 상태 조회 + 따라잡기)**:
  - 보관 기간과 무관하다. 대신 상품·가격 두 서비스에 API 를 만들고, 시작 오프셋 기록·병렬 소비 그룹·완료 조건(지연 0·영구 큐·DLQ·건수)을 갖춰야 한다.
  - 지금 규모에 과하다(사용자 판단). 도입 때 유지할 결정: 파티션별 시작 오프셋 확정, 새 소비 그룹 + 새 색인 병렬 운영, 가격 스냅샷은 EFFECTIVE 상태만.
- **원천 서비스가 현재 상태를 사건으로 재발행**: 일어나지 않은 사건이 다른 구독자에게 간다.
- **보관 설정을 kafka-init 컨테이너로**: 다른 PC 의 컨테이너가 모두 재생성된다(`extra_hosts`).

## 결과
- 두 토픽은 지워지지 않고 계속 커진다. 크기·증가 속도·디스크 여유를 감시한다.
- Docker 가상디스크(`docker_data.vhdx`)는 안에서 지워도 자동으로 줄지 않는다. 나중에 정리해도 C: 여유는 압축(Docker 정지)해야 돌아온다.
- Kafka 를 새로 만들면(볼륨 손실) 다음 `lan.sh deploy <Kafka PC>` 까지 브로커 기본 7일이 적용된다. `KafkaEventRetentionNotUnlimited` 경보가 알린다.
- 백업 사이에 Kafka 를 잃으면 마지막 백업 뒤 사건은 복구되지 않는다(RPO = 마지막 백업 시점). 정기 백업을 정할 때 이 간격을 고른다.
- 전체 재생 시간은 이력에 비례해 늘어난다. 지금 파이프라인은 작업자 1·배치 1 이고 콘텐츠 사건마다 HTTP 호출을 한다. 재생 시간을 재검토 조건으로 본다.
