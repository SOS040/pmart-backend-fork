# ADR-0062 직원의 고객 개인정보 원문 열람은 사유를 받고 audit-service 에 기록한 뒤에만 — 기본은 가린 값

- 상태: 승인 (2026-11-15, 사용자 — 결정 9~14 "너추천대로 할게"; — 클라이언트 질문 "원문 열람 기록 API?"(BR 회신 §3-4) → "기록 남긴다면 어느 db 에 남길거야?" → audit-service DB 설명 → "응" → "열람기록 저장에 대한 부분 기록해줘")
- 관련: 업무 원문 BO-25(개인정보 열람·내보내기·감사 증빙), `docs/architecture/service-map.md` audit-service(소유: 개인정보 열람·다운로드 기록), O-6 직원용 주문 검색(`service-requests/order-service.md`), 계약 `audit-service.yaml` 0.2.0·`order-service.yaml` 0.4.0
- 구현: 백엔드 95e8c9ed(2026-11-15, LAN 배포), 클라이언트 요청 `docs/handoff/clients/backoffice/2026-11-15-request-order-pii-reveal.md`

## 배경
- 2026-11-15 백오피스 고객센터·라이더 운영 메뉴용으로 직원 주문 상세(`GET /orders/lookups/{orderId}`)를 만들었다. 처음에는 배송지 사본(수령인·연락처·주소·출입 메모) 원문을 그대로 줬고, 클라이언트가 화면에서 가렸다가 "보기"로 열었다 — **누가 언제 왜 봤는지 기록이 없었다**.
- BO-25 는 "목록 기본 마스킹 → 담당 범위 → 원문 열람의 사유 확인 → 필요한 필드만 → 행위자·대상·범위·시각·결과 기록", "감사 기록을 남길 수 없으면 원문 열람을 보류"를 요구한다.
- 서비스 목록은 개인정보 열람 기록을 audit-service 소유로 두었고, 계약(`/internal/pii-access-logs`)은 있었지만 구현이 비어 있었다(501).

## 결정
1. **저장 위치 = audit-service 의 DB(`audit_service`, LAN PC 4 postgres) 표 `pii_access_log`**(V2). 원문을 가진 서비스(order 등)의 DB 에 두지 않는다 — 열람 기록은 감사 원장 하나에 모아, 원문을 다루는 서비스가 자기 열람 기록을 고칠 수 없게 한다.
2. **추가 전용**: UPDATE·DELETE 를 트리거(`trg_pii_access_log_append_only`)로 거부한다. 잘못 남긴 기록도 고치지 않고 새 기록으로 정정한다(BO-25 §5).
3. **남기는 것**: 행위자(운영자 ID·종류·그때 역할·센터), 대상(subject 종류 CUSTOMER 등·참조 = 고객 accountId, 사건 참조 `ORDER:<orderId>`), 접근 종류(VIEW), 연 항목(NAME·PHONE·ADDRESS·ENTRANCE), **사유(필수 2~200자)**, 화면(`<X-Source-System>:order-lookup-detail`), 시각(occurredAt·recordedAt), 요청 서비스·요청 키, traceId. **원문 개인정보 값은 남기지 않는다.** 사유·원문은 로그에도 남기지 않는다.
4. **기본은 가린 값**: 직원 주문 상세는 이름 첫·끝 글자, 연락처 앞 3·끝 4자리, 상세주소 `***`, 출입 메모·좌표 없음, 도로명주소·우편번호·출입 방법은 그대로(`shippingAddressMasked: true`). 상세 조회 자체는 기록하지 않는다.
5. **원문은 열람 요청으로만**: `POST /orders/lookups/{orderId}/pii-reveals` `{reason, fields?}` — 권한(상세와 같은 역할) → 주문·배송지 확인 → **audit-service 에 동기로 기록** → 기록이 남은 뒤 고른 항목만 원문 응답. 
6. **기록 못 하면 원문도 없다**: audit-service 가 응답하지 않거나 503·500·시간 초과면 order 는 503(`DEPENDENCY_UNAVAILABLE`·`UNKNOWN_RESULT`)으로 원문을 주지 않는다(BO-25 §3). 같은 Idempotency-Key 로 다시 보내면 같은 기록으로 이어진다(키 = 직원·주문·클라이언트 키의 해시 — 다른 직원과 섞이지 않음).
7. **원문 응답을 저장하지 않는다**: 열람 응답은 멱등 기록(`request_record`)에 저장·재생하지 않고 매번 원장에서 다시 읽는다 — 개인정보가 다른 표에 남지 않게.
8. 열람 기록은 서비스 간 내부 경로(`/internal/**`, 게이트웨이 차단)로만 쓴다. 직원 조회는 OPERATOR_ADMIN 만(아래 10).

## 적용 범위
- 지금: order-service 직원 주문 상세 하나. 다른 화면이 고객·라이더 개인정보 원문을 보여 주게 되면(라이더 상세 BOD-3, 문의 연락처 등) **같은 방식**(기본 가림 + 열람 요청 + audit 동기 기록)으로 한다.
- 대량 내보내기(BO-25 "내보내기")는 이 결정에 들어 있지 않다 — 만들 때 따로 정한다.

## 정한 것(2026-11-15 사용자 "너추천대로 할게")
9. **보존 기간 = 2년 뒤 파기**: 개인정보 안전성 확보조치 기준의 접속기록 보관(최소 1년, 민감정보 등 2년)에 맞춰 넉넉히 2년. 정리 작업 구현 2026-11-15(audit V3 `PiiAccessLogPurger` — 6시간마다, 추가 전용 트리거는 정리 작업 트랜잭션의 DELETE 만 예외).
10. **열람 기록을 볼 수 있는 사람 = `OPERATOR_ADMIN` 만**. 본인 기록 보기·별도 감사 역할은 두지 않는다. 조회 API 구현 2026-11-16(사용자 "바로 만들어줘" — audit 0.3.0 `GET /pii-access-logs`(열람한 직원·정보주체·사건 참조·접근 종류·기간, 새 것부터 커서)·`GET /pii-access-logs/{id}`). 화면은 백오피스(PC 2).
11. **배송 요청사항(`deliveryNote`)도 가린다**(order 계약 0.5.0): 직원 상세에서 null + `deliveryNoteMasked`, 원문은 `ENTRANCE` 열람과 같이(공동현관 번호가 들어갈 수 있어서).
12. **도로명주소·우편번호·출입 방법은 그대로**(권역·센터 판단용) — 상세주소·핀만 가림.
13. **열람 때 담당 범위 검사는 나중** — 사건함(case-service)이 생겨 "담당 사건·문의"를 알 수 있을 때. 지금은 역할만.
14. **목록 검색어(연락처 완전 일치)는 기록하지 않는다** — 검색하려면 이미 그 번호를 알고 있고, 결과 목록은 가린 값이다.

## 결과
- 원문 열람마다 "누가·언제·무엇을·왜"가 감사 원장에 남고, 기록을 남길 수 없으면 원문이 나가지 않는다.
- 클라이언트는 "보기" 토글을 사유 입력 → 열람 요청으로 바꿔야 한다(요청서 위). 그 전까지 LAN 백오피스 주문 상세는 가린 값만 보인다.
- audit-service 가 처음으로 실제 쓰기 경로를 갖는다 — 장애가 원문 열람을 막으므로 감시 대상(watch·Prometheus)에 이미 들어 있는지 유지한다.
