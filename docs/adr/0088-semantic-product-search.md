# ADR-0088 상품 검색에 의미 검색 — 벡터 + LLM 꼬리표를 키워드 검색과 섞기

- 상태: **승인** (2026-11-25, 사용자)
- 보탬: ADR-0031(Elasticsearch)·ADR-0073(동의어·오타)·ADR-0051(RAG 묶음 — ollama). 키워드 검색(BM25)은 그대로 두고 더한다.
- 근거(사용자 2026-11-25): "상품 검색에서도 RAG 가 되게 만들고 싶어. 검색창에 '빨간 라면'이라고 쳤을 때 결과물이 나오는 구조를 원해" → 방법 A(의미 검색)+B(LLM 꼬리표) "1번으로 할게", 꼬리표·섞기는 PC 1 추천대로("응 진행해줘").
- 계기: 지금은 상품명 형태소·동의어·설명 낮은 비중만 본다 — "빨간 라면"처럼 이름에 없는 속성(색·맛·쓰임)은 못 찾는다.

## 결정
1. **방법 = 의미 검색(벡터) + LLM 꼬리표, 검색할 때 LLM 생성은 쓰지 않는다.** 검색어를 LLM 으로 바꿔 쓰기(방법 C)는 CPU 에서 수 초라 쓰지 않는다. 검색할 때 늘어나는 일은 검색어 임베딩 한 번(ollama, 수백 ms 상한 — 넘거나 실패하면 키워드만).
2. **모델 = RAG 묶음의 ollama 그대로**(pc2 — search-service 와 같은 PC): 임베딩 `qwen3-embedding:0.6b`(1024차원, CPU), 꼬리표 `qwen3:4b`. 모델·차원은 설정값이고, 바꾸면 벡터를 다시 만든다(문서마다 모델 이름을 남긴다).
3. **꼬리표(B)는 검색 전용 내부 신호** — 상품마다 LLM 이 상품명·카테고리·설명·원산지에서 색·맛·식감·쓰임·대상 같은 짧은 낱말(최대 12개)을 뽑아 색인 `aiTags` 에 둔다. **고객 화면에 표시하지 않는다**(틀려도 순위만 어긋나고 사실과 다른 표시가 나가지 않는다). 사람 검토는 지금 하지 않고, 상품마다 꼬리표·모델·시각을 남겨 문제 상품만 빼거나 다시 뽑는다. 원산지·영양·알레르기처럼 법적 표시는 꼬리표로 만들지 않는다(그 칸은 기존 정본만).
4. **벡터(A)** = 상품명 + 카테고리 경로 + 꼬리표 + 설명(앞부분)을 임베딩해 색인 `semanticVector`(dense_vector, cosine)에.
5. **늘 섞되 키워드 일치를 앞에**: 관련도 정렬일 때 BM25 질의와 kNN 을 한 검색에서 함께(점수 합) — kNN 은 비슷함 기준값(`similarity`) 넘는 것만·가중치 낮게, 키워드로 정확히 맞는 상품("신라면")이 지금처럼 앞에. 꼬리표는 키워드 질의에도 낮은 비중으로 더한다("빨간" → aiTags). 키워드 0건이면 의미 결과만으로 채워진다(지금 0건 비슷한 상품 보충은 그대로 뒤에). 다른 정렬(인기·별점·가격)은 의미 결과도 후보에 넣되 그 정렬로. 거르기(센터 취급·카테고리·가격·필터)는 kNN 에도 같게. 응답 모양은 그대로(앱 변경 없음).
6. **만드는 곳 = search-service 안의 뒤 작업**(Logstash 아님 — Logstash 는 지금처럼 상품 사건을 쓰고, 그 문서에 없는 새 칸은 건드리지 않는다): 주기적으로 상품 문서를 훑어 원문 해시(이름·카테고리·설명·원산지)가 바뀌었거나 벡터가 없는 문서만 꼬리표 → 벡터를 만들어 부분 갱신. 한 번에 몇 개씩, 실패는 다음 주기. 색인 재생(재색인) 뒤에는 이 작업이 다시 채운다.
7. **색인 products-v11**(매핑에 새 칸 — 적용된 매핑은 고치지 않는다 규칙대로 새 판, 재색인 절차 `deploy/lan/elastic/REINDEX.md`).
8. **끌 수 있게**: 설정 `pmart.search.semantic.enabled` 가 false 거나 ollama 가 안 되면 지금 검색 그대로(검색은 실패하지 않는다).

## 결과
- "빨간 라면"·"아이 간식"·"비 오는 날 국물" 같은 속성·상황 검색어가 맞는 상품을 찾는다. 이름 검색은 지금과 같다.
- 검색당 임베딩 한 번이 늘고, 상품이 바뀔 때만 LLM 이 돈다(상품 약 500개).
- LLM 꼬리표는 틀릴 수 있다 — 고객에게 안 보이고, 기록으로 문제 상품을 고친다.
