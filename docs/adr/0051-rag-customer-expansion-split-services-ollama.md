# ADR-0051 RAG 고객앱 확대 — 운영자용·고객용 서비스와 pgvector DB 를 나누고, 모델은 LAN 의 Ollama 로 돌린다

- 상태: 승인 (2026-11-09, 사용자 결정 — 고객용 확대, 서비스·DB 분리 "추천대로 승인", 배치 "일단 PC2", "Ollama 쓰자". 아래 "결정 대기"는 아직 정하지 않았다)
- 대체: ADR-0036 의 결정 11(제공자 모듈 없음 — 이제 Ollama 모듈을 둔다)과 "결정 필요" 1(외부 모델 — LAN Ollama, 외부 전송 없음)·2(LAN pgvector 위치 — 아래 결정 4). ADR-0036 의 결정 1~10(운영자 1차 범위·색인·지위·검색·스냅숏·선점·권한·원문 미저장·기준선)은 운영자용 서비스에 그대로 둔다.
- 관련: ADR-0036, `docs/rag/planning/2026-11-07-references-review.md`(D1·D3·C1~C8), `docs/rag/planning/2026-11-07-report-customer-rag.md`, `docs/architecture/service-map.md` §8, `deploy/lan/placement.conf`

## 배경
- ADR-0036 1차는 내부 운영자 전용이고 외부 모델 없이 발췌 답변(기준선)만 한다. 사용자가 고객앱에도 RAG 를 열기로 했다(2026-11-07 D1, 2026-11-09 재확인).
- 처음 계획은 한 서비스·한 DB 에서 청크별 접근 범위(WHERE)로 고객 공개 문서를 거르는 것이었다. 사용자는 pgvector 를 백오피스용·고객용 따로 두기로 했다(2026-11-09, C7).
- LAN 의 PostgreSQL 세 개(pc2·pc3·pc4, `postgres:17-alpine`)에는 pgvector 확장이 없다(2026-11-09 확인). PC 넷은 같은 사양(i5-11400F·32GB·RTX 2060 6GB)이고, 그날 컨테이너 메모리는 pc2 7.8GB·pc3 11.7GB·pc4 10.2GB, PC 남은 메모리는 pc2 11.1GB·pc3 6.7GB·pc4 4.9GB 였다.

## 결정
1. **고객앱에도 RAG 를 연다.** 1차 범위는 운영자용과 같이 문서 질의응답과 근거 표시까지다.
2. **서비스를 둘로 나눈다** — 서비스 하나가 자기 DB 하나를 갖는다(MSA).
   - `ai-assistant-service`: 운영자용(백오피스). 지금 구현 그대로.
   - `customer-assistant-service`(새로 만듦): 고객앱용. 고객 토큰, 고객 공개 문서만, 요청 제한. 운영자 문서 DB 에 접속할 계정이 없다.
   - 나눈 이유: 고객 부하·장애가 운영자 도구에 번지지 않고, 배포·확장을 따로 하며, 내부 문서가 고객 답에 섞일 길을 서비스 단계에서 없앤다. 문서를 넣는 흐름도 다르다(운영자 = 저장소 명시 목록, 고객 = 승인된 고객 공개 문서).
   - 두 서비스가 같이 쓰는 기술 부분(청크·검색 SQL·임베딩 캐시·모델 호출)은 `libraries/` 로 빼는 것을 먼저 검토한다. 지위 판정처럼 운영자 문서에만 맞는 규칙은 `ai-assistant-service` 에 남긴다(라이브러리에 업무 규칙 금지). 어디까지 뺄지는 고객용 구현 때 정한다.
3. **pgvector 는 백오피스용·고객용 DB 를 따로 둔다**: DB `ai_assistant_service`, `customer_assistant_service`, 계정도 서비스마다 따로(서로의 DB 에 권한 없음).
4. **RAG 전용 pgvector 컨테이너 하나에 두 DB 를 둔다**(`pgvector/pgvector:pg17`, 버전 고정). 공용 PostgreSQL 이미지는 바꾸지 않는다(40여 서비스 DB 가 있어 영향이 크다). 고객 부하가 커지면 고객용 DB 만 다른 컨테이너·PC 로 옮긴다(서비스는 접속 주소만 바뀜).
5. **LAN 배치는 pc2**: pgvector·두 서비스·Ollama. 가장 여유가 있다(위 수치). PC1(빌드·개발 PC)은 빌드·시험과 자원이 겹치고 자주 재시작해서 상시 운영에 두지 않는다 — 임베딩 비교처럼 한 번 돌리는 시험에만 쓴다. pc2 에는 주문·결제가 있어 RAG 컨테이너에 CPU·메모리 상한을 걸고 고객용에 요청 제한을 둔다. PC 를 한 대 더 들일 수 있어(사용자 2026-11-09), 그때 옮기는 것을 다시 본다.
6. **모델은 LAN 의 Ollama 로 돌린다**(사용자 2026-11-09 도입 승인). 외부 유료 모델 API 는 쓰지 않는다 — 질문·문서가 밖으로 나가지 않는다.
   - Ollama 는 Docker 컨테이너로 두고 pc2 GPU 를 쓴다(다른 구성요소처럼 `lan.sh` 로 관리·버전 고정). 컨테이너에서 GPU 가 안 되면 다시 정한다. → 2026-11-09 확인: pc2 Docker 컨테이너(`--gpus all`)에서 RTX 2060 6144MiB 보임(nvidia-smi, CUDA 13.3).
   - 서비스는 Spring AI 의 Ollama 모듈(`spring-ai-ollama`, 기존 `spring-ai-bom` 2.0.2)로 부른다. `libs.versions.toml` 에 등록한다.
   - 임베딩: Qwen3-Embedding-0.6B 와 BGE-M3 를 우리 문서(`RetrievalEvalIT` 질문)로 비교한 뒤 고른다(D3, 사용자 2026-11-09). → **Qwen3-Embedding-0.6B 로 결정**(2026-11-09 사용자, 절 기준 recall@5 0.76 vs 0.68, 639MB — `docs/rag/verification/2026-11-09/embedding-compare/`). 1024차원, 질문에만 지시문. 차원이 바뀌므로 재색인이 따른다.
   - 대화 모델: RTX 2060(6GB)에 임베딩과 같이 올라가는 4B 급으로 시작해 답변 충실도를 평가하고, 부족하면 8B 를 시험한다(시작값 — 평가 뒤 정한다).

## 결과
- 서비스가 하나 늘어 50개가 된다(`service-map.md` §8, `architecture-design.md` 표).
- LAN 에 RAG 전용 pgvector·Ollama 컨테이너가 생긴다. `placement.conf` pc2 줄 끝에 붙인다(앞 구성요소 IP 를 바꾸지 않게).
- 실제 모델로 의미 검색·생성 충실도·환각·주입 방어를 평가해야 운영자용도 기준선 모드를 벗어난다.
