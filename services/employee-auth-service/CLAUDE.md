# employee-auth-service

서비스 책임의 정본은 `docs/architecture/service-map.md` 의 `employee-auth-service` 절이다. 여기에는 **이 서비스 안에서만 적용되는 규칙**을 둔다.
결정: ADR-0056(Keycloak 은 직원 신원만, 직원 토큰은 이 서비스). 설계·구현에서 정한 것: `docs/architecture/auth/employee-auth-structure.md`(진행 절).

## 계약
- REST: `contracts/openapi/employee-auth-service.yaml` → `openApiGenerate` 가 `com.pmart.employeeauth.api.generated` 에 인터페이스·DTO 생성. `api/*Controller` 가 구현한다. 계약을 먼저 고치고 코드를 맞춘다.
- 이벤트(2026-11-13 5-3): **구독** `platform.employee.v1`(hr-service `EmployeeRegistered·Suspended·Reinstated·Left` — `EmployeeEventHandler`, 바인딩 `employeeEvents-in-0`), **발행** `SubjectBlocked`(platform.subject-block.v1 — 직원 정지·퇴사·관리 경로 정지, issuer = 이 서비스). **구독** `platform.approval.v1`(2026-11-13 5-4 — `ApprovalDecided` type GRANT·정본 이 서비스만, `GrantApprovalHandler`, 바인딩 `approvalEvents-in-0`), **발행** `GrantApplied`(platform.auth.v1, 승인 행마다)·`GrantEnded`(platform.auth.v1, 2026-11-17 EA-1 — grant 가 기간 전에 끝날 때 grant 마다: 회수 REVOKED·소속 변경 AFFILIATION_CHANGED, `application/GrantEnds`, 사유 글 없음)·`ApplicationReceiptRecorded`(platform.approval-receipt.v1, 승인마다 — approval 실행 축).

## 패키지
`com.pmart.employeeauth.{api, application, infrastructure}`. Controller 에 업무 규칙 금지.

## 데이터
- 스키마 변경은 `src/main/resources/db/migration/V*.sql` 로만. 적용된 파일 수정 금지.
- Keycloak 토큰·비밀번호·이메일·이름은 저장하지 않는다 — Keycloak `sub` ↔ 운영자 ID 연결만. state·티켓·refresh token 은 SHA-256 만. Keycloak PKCE verifier 는 콜백에서 지운다.
  - **예외(2026-11-12, 백오피스 SSO)**: SSO 앱 세션에만 Keycloak **ID 토큰**을 둔다(`login_ticket`→`employee_session.keycloak_id_token`) — 로그아웃 때 `id_token_hint` 로 확인 화면 없이 Keycloak 세션을 끝내려고. 클라이언트 기본 범위를 `basic` 만 두어 이름·이메일이 없고(시험이 확인), `aud` = 이 서비스라 PMart API 에 쓸 수 없다. 세션이 끝나면(로그아웃·폐기·만료 뒤 하루 정리) 지운다. 만료된 ID 토큰으로도 Keycloak 26.8.1 로그아웃이 된다(2026-11-12 확인).
- `employee_account` 가 직원 상태·역할·권한 센터의 정본(D1). 상태는 hr-service 사건(`hr_version` 으로 늦은 사건 버림, 근무 시작일 `start_date` 전 로그인 거절)과 관리 경로(PUT, 변경 기록)가 바꾼다. 사건으로 새로 생긴 직원은 권한 없음.
- 승인된 권한(2026-11-13 5-4): `employee_grant`(승인 행 하나 = 한 줄, `<approvalId>:<lineId>`, 유효 기간 = 시작일 00:00 ~ 마지막 날 다음 00:00 Asia/Seoul, 모르는 역할 행은 거절 UNKNOWN_ROLE). **토큰 역할·센터 = `employee_account` 값(관리 경로·이전 계정) ∪ 지금 유효한 grant**(`EmployeeAccess` — 로그인·갱신 때마다 계산). 관리 경로 PUT 은 계정 값만 바꾼다. **조회(0.7.0, 2026-11-15 BO-01)** 는 OPERATOR_ADMIN·HR_ADMIN 이 읽고, 응답에 지금 유효한 `effectiveRoles`·`effectiveCenters`(`EmployeeAccess`)와 grant 목록(최근 100)을 싣는다 — 인사팀 앱 "권한 관리". BO-01 결정(추가·변경 = 승인, 회수 = 즉시, 종료일 없으면 근무 기간까지)은 `docs/business/flows/employee-account-provisioning.md` §1. **회수(0.8.0)** `POST /employee-auth/employees/{id}/grant-revocations`(`EmployeeAdminService.revokeGrant`) — OPERATOR_ADMIN·HR_ADMIN, 자기 권한 403, OPERATOR_ADMIN·HR_ADMIN 역할 grant 는 OPERATOR_ADMIN 만, `valid_until = 지금`·`revoked_*`(V6), 모든 세션 끊기 + `SubjectBlocked`(SESSIONS_REVOKED), 이미 회수면 200(멱등).
- **승인자·회수자 이름(0.10.0, 2026-11-17 사용자 결정 — 인사팀 앱 권한 상세 승인 칸이 OP-… 로 보이던 것)**: 직원 응답 `grants[].approverName`·`revokedByName`. 이름은 저장하지 않는다(위 규칙 그대로) — `infrastructure/EmployeeNames` 가 응답마다 hr-service `GET /internal/employee-names?operatorIds=…` 를 **한 번**(ID 묶음, 최대 200, `RULE:…` 자동 승인은 빼서 null) 부르고 캐시하지 않는다. 실패·시간 초과(기본 연결 1초·응답 5초)·모르는 ID 는 이름 null, 응답은 200. 이름·ID 목록은 로그에 남기지 않는다. 주소 `pmart.employee-auth.hr-base-url`(기본 `http://hr-service:8512` — LAN 은 기본값, local 은 설정 저장소에 `http://localhost:8512` 를 넣어야 이름이 나온다). 시험 `RoleCatalogIT.grantsCarryApproverAndRevokerNamesWithNullFallback`(hr 흉내 JDK HttpServer)·`EmployeeNamesTest`.

## 로그인 (Keycloak 기밀 클라이언트)
- Spring OAuth2 Client 를 쓰지 않는다 — 게이트웨이가 Cookie 헤더를 지우므로 세션 쿠키 없이 돌게 직접 구현(`EmployeeLoginService`, `infrastructure/KeycloakClient`).
- 브라우저 주소(authorization-uri)와 서버끼리 주소(token·jwks·logout — 같은 PC 5 Docker 네트워크)를 나눈다. ID 토큰 `iss` 는 `pmart.employee-auth.keycloak.issuer` 와 정확히 같아야 한다(Keycloak KC_HOSTNAME 기준).
- 앱별 SSO(`pmart.employee-auth.apps.<앱>.sso`): **끈 앱(기본, PDA)** 은 콜백에서 코드 교환 직후 Keycloak 세션을 끝내고(`endSession`) 시작 URL 에 `prompt=login`. **켠 앱(backoffice, 2026-11-12 사용자 결정)** 은 Keycloak 세션을 남겨 같은 브라우저의 다음 로그인이 비밀번호 없이 되고, 로그아웃 응답 `idpLogoutUri`(Keycloak end_session + `id_token_hint` + `<로그인한 출처><post-logout-path>`)로 브라우저가 Keycloak 세션을 끝낸다. 거절된 로그인(미등록·정지)은 SSO 앱이어도 Keycloak 세션을 끝낸다. Keycloak 세션 무활동 한도는 Realm 값(12시간, 사용자 결정 — 바꾸지 않음).
- 티켓은 60초·1회, 시작한 기기 + 앱의 code_verifier(S256) 로만. 틀린 시도도 티켓을 태운다.
- 복귀 주소는 설정 허용 목록에서만(열린 리디렉션 금지). 오류는 `?error=코드` 로 앱에 돌려준다(state 를 모르면 400).
- Keycloak 클라이언트 시크릿은 pmart-config `{cipher}`(원본 `deploy/lan/.secrets/keycloak-employee-auth-client-secret`), Keycloak 쪽 값은 Realm 파일 자리표시자(render.sh). 로그에 남기지 않는다.

## 토큰 (자체 JWT)
- access: RS256, 예전 auth-service 운영자 토큰과 같은 모양 — `iss` = `pmart.employee-auth.issuer`(발급자 표 `staff-ea` 줄과 같게), `sub` = 운영자 ID, `typ=OPERATOR`, `aud=pmart-api`, `roles`, `centers`, `sid`, 15분.
- refresh: 한 번만(재사용이면 세션 폐기 `TOKEN_REUSED`), 로그인한 기기에서만. 세션 = min(갱신 + 앱 무활동 한도, 시작 + 12시간).
- 서명키 `pmart.employee-auth.signing.keys`(다른 발급자와 다른 키, LAN `{cipher}`, 원본 `.secrets/employee-auth-signing-key.pem`). local/test 만 `ephemeral=true`.
- **웹 refresh 쿠키(ADR-0059)**: 앱 설정 `refresh-cookie` 를 켠 앱은 refresh token 을 본문 대신 세션별 HttpOnly 쿠키(`api/RefreshCookies` — Path = 갱신 주소/{sessionId})로, CSRF 는 Signed Double-Submit(`application/CsrfTokens` — HMAC 에 sessionId 를 묶음, 서버 저장 없음, 세션 동안 고정, 키 `pmart.employee-auth.refresh-cookie.csrf-key` `{cipher}` — local·시험은 `signing.ephemeral` 이면 임시 키). 갱신 `POST /tokens/refresh/{sessionId}` 는 CSRF(403, 세션 유지) → 소유권(세션·기기·쿠키 앱, 401 — 토큰 안 씀) → 회전 순. 쿠키 앱 세션은 본문 갱신 경로를 못 쓰고, 본문 앱은 쿠키 경로를 못 쓴다. 로그아웃은 그 세션의 쿠키 둘을 지운다. 시험 `RefreshCookieIT`(Keycloak 없이 티켓을 직접 넣음). **LAN 은 2026-11-14 부터 backoffice·hr-backoffice 켬**(키 원본 `deploy/lan/.secrets/employee-auth-csrf-key`, 클라이언트 web/core 05f7933).
- **로그아웃 전파(ADR-0061, 2026-11-14)**: SSO 앱 세션에 Keycloak 세션 ID(`keycloak_sid`, V5 — ID 토큰 `sid`, 티켓을 거쳐 세션으로). 로그아웃(이 세션)은 같은 `keycloak_sid`·같은 직원의 다른 세션도 끝내고(LOGOUT_PROPAGATED) 세션마다 `SubjectBlocked`. Keycloak 백채널 `POST /internal/keycloak-logouts`(form `logout_token` — `KeycloakClient.verifyLogoutToken`: 서명·iss·aud·events·nonce 없음·sid/sub) → 그 sid(또는 sub 의 직원 SSO 세션 전부) 종료(IDP_LOGOUT), 무효 400 `invalid_request`·공개키 불가 503. 이 경로는 `pmart.web.excluded-paths`(Keycloak 이 헤더를 안 보냄). PDA 세션은 `keycloak_sid` 없음 — 영향 없음. Keycloak 클라이언트 `backchannel.logout.url`·`frontchannelLogout=false`(Realm 파일 + LAN 은 관리 API). 시험 `EmployeeLoginIT`(Keycloak 이 `host.testcontainers.internal` 로 시험 앱을 부른다).
- 로그아웃·현재 세션은 이 서비스가 발급한 토큰만(Keycloak 토큰은 403). **현재 세션(0.6.0, 2026-11-15)** 은 지금 기준 `roles`·`centers`(`EmployeeAccess` — 토큰과 같은 계산)를 싣는다 — 화면이 access token 을 풀지 않고 메뉴·센터를 정하게(일반적인 `/me` 방식). **센터 이름(0.9.0, 2026-11-16)** `centerDetails[{centerId, name}]` — `infrastructure/CenterNames` 가 center-master-service `GET /internal/centers/{id}` 를 10분 캐시(실패는 name null·1분 기억, 세션 응답은 실패시키지 않음), 주소 `pmart.employee-auth.center-master-base-url`(기본 `http://center-master-service:8507`). 계정이 정지·퇴사면 401 `SESSION_EXPIRED`. 관리 경로는 발급자 표가 인정하는 OPERATOR + `OPERATOR_ADMIN`.
- **역할 목록(0.5.0, 2026-11-15, BR-57 — EA-2)**: `GET /employee-auth/roles`(`RolesController` → `EmployeeRoleCatalog`) — 발급자 표가 인정하는 OPERATOR 면 역할과 상관없이. 순서 = 설정 `roles`, 이름·센터 지정 = 설정 `role-info` 목록(`{code, name, center-scoped}` — 맵은 Spring 맵 키가 `_` 를 지워서 쓰지 않음, 없으면 이름 = 코드). 역할을 늘리면 `roles`·`role-info` 를 같이 고친다. 인사팀 백오피스가 "요청 권한 역할" 고르기에 쓴다. 시험 `RoleCatalogIT`.
- **권한 요청 검사 내부 조회·중복 반영 안전망(0.11.0, 2026-11-17 HR-2 — `service-requests/hr-service.md`)**: `api/InternalController` — `GET /internal/roles`(`EmployeeRoleCatalog.forService`, 역할 목록 API 와 같은 내용)·`GET /internal/employees/{id}/grants?activeOrFuture=true`(`EmployeeAdminService.grantsForService` — 효력 끝이 없거나 지금보다 뒤인 grant, 시작 순. 플래그 없으면 최근 100. 계정 없으면 빈 목록, 승인자·사유·이름은 싣지 않음). 토큰 없는 내부 호출 — hr-service 가 권한 요청 때 센터 규칙(`role-info` center-scoped)·이미 유효한 같은 권한(409 `GRANT_ALREADY_ACTIVE`)을 검사한다. **안전망**: `GrantApprovalHandler` 는 승인 행이 이미 유효·예정인 같은 권한(`application/GrantOverlap` — 역할 같음 + 센터 겹침(센터 지정이 아닌 역할은 센터와 상관없이) + 기간이 지금 이후로 겹침, 같은 grant ID 재전달은 뺌)과 겹치면 grant 를 만들지 않고 회신 행 `REJECTED`(reasonCode `GRANT_ALREADY_ACTIVE`, domainRef = 기존 grantId)·경고 로그(운영자 ID·역할·grant ID 만), `GrantApplied` 없음. 같은 승인 안의 앞 행도 본다(같은 트랜잭션). 같은 직원 반영은 `EmployeeAuthStore.lockGrantsOf`(트랜잭션 advisory lock)로 한 줄로. 시험 `GrantApprovalIT.duplicateApprovedLineDoesNotCreateSecondGrant`·`GrantOverlapTest`.

## 시험
```bash
./gradlew :services:employee-auth-service:check   # 단위 + 통합(PostgreSQL·Keycloak 26.8.1 컨테이너) + 계약 검증
```
- `EmployeeLoginIT` 는 Keycloak 컨테이너(`src/integrationTest/resources/keycloak/pmart-staff-it-realm.json` → 컨테이너 안 이름 `pmart-staff-realm.json` — 26.8 은 파일 이름 = Realm 이름)를 띄우고 브라우저를 흉내 낸다. Keycloak 쿠키에 Secure 가 붙어 java.net.CookieManager 대신 직접 쿠키를 보관한다.
- 로컬 포트 8511. LAN PC 5. 로컬 프로필에는 Keycloak 이 없어 로그인 시작이 CONFIG_REQUIRED.
- 관리 경로 역할 변경 스위치(2026-11-17, 권한 빈틈 정리 — 사용자 "(가)"): `PUT /employee-auth/employees/{id}` 의 역할·센터 변경은 `pmart.employee-auth.direct-role-edit`(기본 false, LAN true — 시험 도구 `staff_auth.py`·`Seed.java`)일 때만, 꺼지면 상태만. `OPERATOR_ADMIN`·`HR_ADMIN` 을 새로 넣는 것은 항상 403(승인으로만, `EmployeeAdminService.checkRoleEdit`). 시험은 IT 에서 켬.
- **역할·센터 섞임 막기(0.11.1, 2026-11-18 — permissions.md §9 큰 것 2, 사용자 "(가) PC 1 만")**: 토큰은 역할·센터를 따로 싣는다(`EmployeeAccess`, 모양 그대로). 그래서 같은 때 유효한 권한(계정 값 포함) 안에서 센터 지정 역할 하나하나의 센터 = 센터 전체여야 한다(`application/CenterRoleMix` — 새 권한과 기간이 지금 이후로 겹치는 것만 한 묶음, 센터 지정도 센터도 없는 새 권한은 보지 않음). 승인 반영은 섞이는 행을 grant 로 만들지 않고 회신 REJECTED `CENTER_ROLE_MIX`(domainRef = 충돌 grantId 또는 `account`)·경고 로그, 관리 경로 PUT 은 역할·센터를 바꿔 섞이면 409(상태만 바꿀 때는 안 봄). hr-service 가 요청 때 먼저 409. 시험 `CenterRoleMixTest`·`GrantApprovalIT.mixedCenterRolesAreNotApplied`.
- **계정에 직접 둔 역할도 중복(0.12.0, 2026-11-18 HR-2 ③)**: 내부 grant 조회 응답에 `account`(`InternalAccountAccess` — 계정 역할·센터, 계정 없으면 없음, `EmployeeAdminService.accountForService`) — hr-service 가 중복·섞임 검사에 쓴다. 승인 반영 안전망은 계정에 같은 역할(센터 지정 역할은 센터 겹침)이 있으면 grant 를 만들지 않고 REJECTED(`GRANT_ALREADY_ACTIVE`, domainRef `account`) — grant 를 회수해도 계정 값이 남아 권한이 안 빠지므로. 시험 `GrantApprovalIT.accountRolesCountAsDuplicates`.
- **쿠키 Max-Age(0.12.1, 2026-11-18 — clients web-common C1 "CSRF 쿠키가 쌓여 431")**: `api/RefreshCookies` — refresh 쿠키 Max-Age = refresh token 만료까지(티켓 교환·갱신마다 새로), CSRF 쿠키 Max-Age = `session-max-age`(12시간, 세션은 그보다 길지 않음 — `EmployeeSessionService.sessionMaxAge`). 전에는 둘 다 브라우저 세션 쿠키라 로그아웃 없이 끝난 세션의 CSRF 쿠키(Path=/)가 같은 호스트(백오피스 443·8444·8445·8446)의 모든 요청에 쌓였다. 이름·Path·읽는 법 그대로 — 앱 변경 없음. 배포 뒤 이미 쌓인 쿠키는 사이트 데이터 지우기로 한 번. 시험 `RefreshCookieIT`.
- **PDA 무활동 한도 12시간(2026-11-25 ADR-0089 — 사용자 "무활동한도를 근무 길이로 맞춰줘")**: `apps.mfc.session-idle` PT30M → PT12H(세션 최대와 같음). 시험 `EmployeeLoginIT`(refresh 만료 ≈ 12시간).
